# Reading connection path reports

A `ready` capability (`path_reports_v1: true`) lets the instance request `observe_paths_v1`. Neither an older supervisor nor an older sidecar needs to understand the new event. Sampling starts after handshake and admission. Each connection gets a process-local ordinal, not a peer identifier. The logs contain no addresses, URLs, endpoint keys or subjects. Transport uses the existing stderr pipe as a dedicated, negotiated JSON-lines sideband. A stalled diagnostic reader cannot hold the mandatory stdout writer. Change snapshots coalesce per connection (at most one per second). Before queuing the first measurement, the producer reserves a terminal slot. The queue has room for one pending measurement and one close per supported connection. Newer measurements replace a connection’s own pending sample in place. Until its first sample can be queued, later snapshots retry as `open`; replacement preserves that phase until the writer consumes it. The instance also reserves a log line for the close of each sampled open. The total log budget is 60 lines per supervisor window. A broken pipe or process termination is not a delivery guarantee.

With `path_reports_v2: true`, the instance can instead request `observe_paths_v2`. Only this negotiated private sideband adds the authenticated peer key (`peer`), the attribution `epoch` frozen at the connection's admitted handshake, and the selected path's `scope` and `rtt_ms`. These fields are not log fields. A zero epoch permits no device attribution. Local scope covers RFC 1918, IPv4 link-local, shared 100.64/10, IPv6 ULA and link-local; IPv4-mapped IPv6 is classified using its mapped address. Relay scope is null. RTT is a sample from the selected path’s `PathStats`, not an aggregate across candidates. An unchanged v2 connection refreshes approximately every five seconds; path changes remain coalesced to at most one per second. The instance expires a measurement after ten seconds without a fresh report. A v1 request retains its old schema and event-only cadence.

* `selected` refers to the connection's selected application-data path at observation time. It is not proof of HTTP delivery. At close, the last observed selection is used when no path remains. `open` in each family row counts currently open transport paths; it is **not** a count of validated candidates or addresses advertised by the App.
* Rows group noq's path-attributed RX/TX byte and PATH_CHALLENGE/PATH_RESPONSE frame counters by remote transport kind: relay, IPv4, IPv6, other. Closed-path statistics observed since subscription are included. A terminal report reads only final `Closed.last_stats`, never the retained path list. Its open counts are zero. A `partial` report means events were lost or the bounded close drain did not finish. Counts from different reports are snapshots, not deltas to add together.
* Source boundary: iroh 1.4.1 `endpoint/connection.rs` (`paths`, `path_events`) and `socket/remote_map/remote_state/path_watcher.rs` (`Opened`, `Selected`, `Closed.last_stats`, `Lagged`, `Path::stats`). A path exposes its selection, but no per-path validated bit. `Endpoint::remote_info` is a **peer-wide known-address cache** which can contain obsolete addresses; it is not a transcript of what that peer offered this connection. The instance rendezvous log is the source for its own returned candidate summary.
* noq-proto 1.4.0 `connection/stats.rs` exposes path UDP bytes and directional frame counts. `connection/mod.rs` (`poll_transmit_off_path`, `send_off_path_path_response` and NAT traversal challenge handling) handles off-path traffic separately. The counters are attributed to QUIC paths, not a capture of each packet's physical destination or source. In particular a zero IPv6 row does **not** prove no IPv6 probes were sent or no packets returned. A positive RX value means noq attributed traffic to an IPv6 path, not that a specific challenge received a matching reply.
