# Windows Desktop account-cookie storage

**Rule review, not implemented.** Windows only, before the Desktop claim PR. `NativeCredentials` currently stores a whole serialized account jar in one Windows generic credential. The pinned keyring 3.6.3 Windows `set_secret` rejects more than `CRED_MAX_CREDENTIAL_BLOB_SIZE` (2,560 bytes), before `CredWriteW`. The hosted issuer's cookie chunk size alone is 3,180. A network-free run of the pinned issuer SDK with a synthetic email identity produced a 2,766-byte ordinary set of cookie **values**, excluding Rust's serialized attributes; this is not a measurement of anyone's account or an observation on Windows. An ordinary signed-in session must survive restart. No account or sign-in change; no keychain migration on macOS; no new UI strings.

## Store and one commit point

Keep the `Credentials::{read,write,erase}` contract and the released `user.service` WinCred root. For an ordinary jar of **at most 2,560 bytes**, keep the old exact bytes in that entry. For a larger jar, call Windows current-user `CryptProtectData` (integrity protection, UI forbidden, **not** machine-scope) on the complete bounded jar with fresh 32-byte entropy plus version/application/profile/account domain separation. Split the **sealed ciphertext only** into bounded generic-credential blobs in an alternate bank in Credential Manager. There is no plaintext or ciphertext file, other store or Avibe Vault involvement. The last write atomically replaces the old root with a small binary manifest containing a reserved non-UTF-8 magic, version, bank, length/count and the fresh entropy. The entropy required to unprotect that generation lives only inside this WinCred root and native ephemeral memory, never with the ciphertext. Overwriting/removing the root invalidates the previous ciphertext immediately. No custom encryption. Use local-computer persistence for the **new large-format WinCred records** (`CRED_PERSIST_LOCAL_MACHINE`, not DPAPI machine scope); do not introduce a roaming copy of the root or fragments. Released small raw storage retains its existing persistence behavior. Scope and ciphertext integrity are checked before returning the jar.

Two fixed banks per canonical app/profile/account scope bound storage, even if the process repeatedly dies during staging or the released client overwrites the root. Derive bank targets from a length-delimited domain-separated scope, bank and index; never a target specified by stored bytes. Use a target namespace disjoint from released `account.service` roots and from other profiles/app IDs; honor Windows' case-insensitive target naming consistently. The root (not finding chunks, a timestamp or the newest bank) is the **only** commit point. Serialize upgraded readers/writers/erasers across processes through a Windows OS-released lock, including reclamation; use a fixed lock in the application owner’s local data directory, no credential material. Avoid a scope-specific lock name that could alias differently than WinCred. Never take this lock across a network/async account operation. The old writer need not know about the lock: it can replace/delete the same root natively. A fresh read checks the same root again after reading the bank, never returns material after observing replacement. Independent legitimate writers remain last-root-write-wins; no claim of revoking another running App’s memory, hosted sessions or backups.

**Scope of interruption claims.** Storage switches atomically for one OS credential. The existing coordinator separately commits account selection and retires the previous account; a completed sign-out/switch erases its old root. A crash *before the coordinator calls erase* is not proof of credential erasure: e.g. after saving the new connection record and before retiring A, its old root can still exist even in the released format. No new readable copy or old shadow may be left by a successful erase; a failed retirement may leave the new selection committed **with a cleanup error**, not a clean switch. Distinguish `restore prevented` from `old credential physically removed` in tests. Pin the restart behavior: only the account in the durable connection record is eligible for restore, never enumerate a previous account for login. If the requirement also includes guaranteed crash-completion of abandoned **coordinator-level** erasures, an exact-generation retirement intent is needed there (including the already-shipped small format); do not advertise that guarantee on the strength of this storage change.

**Validation gate.** Isolated synthetic credential targets unique to one CI job, cleanup bracketed on every exit, no Developer/owner credentials. Native Windows runner executes the complete `NativeCredentials` roundtrip/overwrite/erase/legacy interop case with genuine WinCred and DPAPI, and a wrapper checks the exact named case ran once, passed, not missing/filtered/ignored. Existing coordinator order/failure tests remain; add a different primary test only for distinct recovery/race risk above. No Mac keychain test, UI build or user service here. Windows exercise, exact-head independent and Codex review, green required CI and Product authorization before lead merges. AV-8 consumes only a landed `Credentials` interface; no stacked PR.
