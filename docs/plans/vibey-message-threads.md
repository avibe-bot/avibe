# Vibey native Anthropic message threads

An upload optimization, never the source of conversation history. Only Vibey conversation requests may create a reusable response ID. Counted side requests, direct CLI backends, and Hub pass-through do not inherit this behavior.

## Acceptance contract

- Pin speculative sends to the selected Source/model. Keep a single-use, five-minute Session parent only after a completed, non-truncated response; compare the rendered history and the assistant reply, route identity, system, tools, settings and betas before omitting anything. If these differ, send full history.
- For an append, previous reported input (including cache read/write) plus output must be at least 20,000 and at least three times the budget for system, tools and the appended messages. Use the first `message_start` to require reported input of at least 90% of the parent total before releasing text, thinking or tool events. **Known by design:** if a relay drops the parent but injects or reports roughly an entire conversation's worth of unrelated input, its answer or tool call can pass the guard without the original context.
- On speculative refusal or failed admission discard the attempt; replay the ordinary full request, without the thread field or beta, once. Ordinary transport retry, terminal failure, cancellation and partial-stream semantics still belong to their existing owners. A failed speculative send does not cool the Source needed for replay.
- All routes try by default. A failed route uses ordinary requests for 24 hours. Creating `state/disable-message-threads` in the instance home disables new thread requests without restart; removing it permits them again. Request cache metadata records attempt mode, wire body bytes, corresponding ordinary full body bytes and the fallback reason.
- Verify usage and cache behavior independently on matched real requests. A mock does not establish provider billing behavior. The owner-route confirmation comes from the first real thread call after update; no historical Session is a test target.

One matched streaming sample measured the parent at 22,368 input tokens (22,365 written for one hour) and 5 output. The plain full follow-up and native continuation each reported 22,389 total prompt tokens in the first `message_start`: full = 3 fresh / 22,365 read / 21 written; continue = 3 fresh / 22,386 read / 0 written. Both produced 5 output. Full ran first, so it could have warmed the last 21 tokens for continue; the evidence is that the long prefix received cache pricing on both, not that the optimization lowers cost. A separate stripped-field control reported 376 versus 4,960 for both true continuation and full replay. These are single-route observations, not universal guarantees.

The read-only `cache_requests.thread_attempts` array reports actual sends, including the cost in bytes of a speculative failure. Each send records `parent_state` (the prior local binding or absence) and `binding` (what this send left for the next request). `no_terminal` is provisional until a terminal is observed. Reason strings contain no provider IDs, tool arguments or response bodies. An explicit `caller: {type: direct}` on a client tool is the ordinary direct call; programmatic callers and unknown fields still prohibit parent binding. To compare actual uploads to ordinary transport, sum `body_bytes` and `ordinary_baseline_bytes` across the observed attempts: a speculative send counts the full baseline once and its replacement counts zero. A settled speculative refusal has its own non-context audit row before full replay starts, so stopping the replacement cannot erase the earlier reported usage. Discarded provider usage is reported separately from the successful response's context size. Missing observations in older records are unknown, not zero.

## Long-history bootstrap

A verified append sends a delta: distant cache markers in the **unsent** ordinary body cannot veto it. Check the actual parent and proposed suffix instead: if its sent terminal message block was marked, the new marker must be able to reach it within the 20-block lookback. Otherwise use full (`terminal_marker_out_of_reach`). An interior parent mark keeps working; only a still-reserved, measured pair may sample an otherwise unreachable terminal lookup. Prior route proof alone is not an exception. Native hosted history, image deltas, session/route/content binding, size checks and the first-event input guard still apply. An ordinary replay sends its original four markers.

A create, by contrast, uploads the history. With two static and two user markers, CPA trims four client markers to three; the relay supports four total. A long history (>20 message blocks) cannot assume that the newest user marker can still look back to the warmed prefix. The ordinary four-marker request runs first. Only its **immediately following** append in that Session can bootstrap, with the same five-minute, exact rendered-prefix, route/model, size, origin and lossless response checks as a server parent. The full must have reported positive cache reads. Its witness is local, single-use and cannot itself authorize a delta. The trial create omits the older user marker; preserving the cache is measured, not guaranteed.

- **Budget:** `AVIBE_MESSAGE_THREAD_BOOTSTRAP_DAILY_LIMIT` in the controller environment defaults to `5`; `0` or an invalid value permits no unproven long creates. This is shared across all Sessions, accounts, Sources and models under the same `AVIBE_HOME`, per UTC calendar day. Not a limit on short/non-risky creates, ordinary sends or verified continuations. A proven route can recheck without spending another slot; it still requires a warm full and fresh paired evidence.
- **Evidence:** at start and completion, require at least 90% of the warm full's reported cache reads on create, then 90% of the larger of the full and create reads on the next accepted continuation. Mark a route proven only after that losslessly completed continuation actually sent fewer HTTP body bytes than its ordinary full would have **and the Agent committed its response**. A provider `Done` can still be rejected, for example a thinking-only silent final. A start with enough *total* input can be a sound answer despite lost *cached* input: deliver it, but do not treat it as proof or make it the next parent. Read loss blocks further risky creates on that route/model for 24 hours, not ordinary traffic.
- **Concurrency/restart:** atomically precharge the slot and reserve the route before handing the create to transport. A cancellation, crash, refusal or missing follow-up cannot refund it or falsely establish proof. Incomplete pairs conservatively block another risky create on the route for up to 24 hours. Session witnesses/IDs never survive restart. The bounded route-hash ledger and daily count persist in `state/message-thread-bootstrap.sqlite`. If the ledger cannot write a measured loss, or its reservation was already evicted, an empty receipt under `state/message-thread-loss/<route hash>` holds exactly that route/model for 24h from its latest loss, including across restart. The table never exceeds 4,096 routes. Active overflow is one file per distinct affected route, **not** a fixed file-count cap: losing evidence to fit the cap would spend cache again. Live writes use a nonblocking maintenance lock **before** the SQLite write transaction (SQLite busy timeout: 200 ms). Only lowercase 64-hex regular receipt files qualify for retirement. Rename an expired active generation, recheck its timestamp, commit any stale-proof revocation, then unlink it. Readers also inspect the retiring generation: a concurrent renewal or a crash cannot erase a live loss. Recording an overflow loss never waits for the maintenance lock. If maintenance or SQLite is busy, admission uses ordinary transport, post-commit proof remains unproven, and loss settlement can still leave a receipt. Preview only reads; it never sweeps, locks for maintenance, or charges. Neither store contains prompts, credentials, message IDs or Session IDs. SQLite work runs off the controller loop and unavailability falls back to full. Preview peeks without admitting, charging, creating a file or consuming a parent; its snapshot can race a later live reservation.
- **Telemetry:** in `cache_requests.thread_attempts`, `bootstrap_trial` / `bootstrap_recheck` identify the create; `bootstrap_baseline_reads` and `bootstrap_observed_reads` expose the comparison. `bootstrap_outcome=awaiting_continuation` is not proof; look for `retained_smaller` and `body_bytes < full_bytes` on a **committed response**, not a discarded attempt. This is evidence, not a transaction receipt: a crash between transcript commit and ledger update leaves the route unproven. `bootstrap_recheck` is direct evidence of a subsequent budget-exempt admission. `bootstrap_read_loss`, `bootstrap_pending`, `bootstrap_daily_limit`, `bootstrap_no_byte_saving`, `bootstrap_stale`, `bootstrap_capacity` and `bootstrap_state_unavailable` distinguish measured loss from lack of evidence or admission. A missing outcome means no completed proof. No claim about provider billing follows from mock traffic.

Claude Code would require its native client and the Hub's native pass-through/error mapping to agree. Codex needs a separate Responses-protocol design. OpenCode would need native client support or a gateway-side history owner; none are changed here.
