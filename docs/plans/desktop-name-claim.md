# Desktop claims this computer (AV-8): rule review

This document defines the intended contract; the native and Runtime implementation status is listed below. The claim changes who can reach the existing local workspace. Signing in to the App, reading the account, opening the account sheet, and restoring a previous session are **not** consent to bind. A hosted grant reserves a name; it is not a local binding.

## End to end: two authorities, one decision

```
Bundled Account / claim sheet Native account coordinator             Local Runtime                      avibe.bot
sign in --------------------> first factor -> existing MFA ------------------------------------------> session
                              discover account A + current Owner catalog <---------------------------+
                              inspect local hint (no preparation); helper verifies binding/ID on its own root
Settings › Devices requests the sheet; shell retains the same Workbench document
claim sheet observes --------> deliver current binding (no ticket, grant or mail)
open once if unbound -------> reserve a short receipt; Read starts worker ------> local admission (*)
                                                                    start desktop, fresh verifier ----> claims
                              native-only ticket + uniform readback ack from worker <----------------+
                              read exact ticket, private jar ---------------------------------------> read
show account email, computer, create/fixed existing target, suggested prefix <-----------------------+
edit -----------------------> read with candidate (not a reservation) -------------------------------> read
confirm displayed decision -> check account epoch, review revision, prefix and target; grant --------> grant
                              if proof owed: email/MFA flow, re-read; confirm again only if the review changed
                              validated grant for same review -> arm private worker for exact name
                                                                    observe grant --------------------> redeem
                                                                    compare subject A + approved name
                                                                    persist accept marker; accept A --> redeem
                                                                    guarded exact pairing journal ----> pairing/redeem
                                                                    apply exact receipt; publish config
bound <--------------------- committed binding/instance ID from helper's root + fresh hosted Owner
                                                                    running service notices publication; starts monitoring
```

**(*) Native channel (proposal).** Use a bounded private stdin/stdout conversation with a helper of the Runtime executable already resolved for this installation (no shell, no PATH re-resolution, no URL/subject/secret from argv, environment, links or WebViews). Implement on the `run_desktop` / `_Flow` side; the helper, not Rust or a browser, is the machine client and keeps the verifier. No HTTP or Harness operation starts, arms, resumes with new inputs, or returns the Desktop ticket. Refuse represented CLI authority. An owned helper is not proof that the listener answering the current port serves that helper's data root. In the helper, create a random one-use challenge; register **only its digest**, fixed expected loopback origin, short deadline and pending phase in one owner-private slot for this root. Return the challenge privately to Rust. Rust POSTs it from its private **local** jar to a fixed versioned admission route on the currently adopted literal loopback origin. The real UI service checks socket peer and Host, no forwarding/direct ingress/delegation, exact literal `Origin`, owner, JSON and CSRF header+cookie, then CAS-marks only that matching slot admitted. Response has no claim capability/data. The helper must see its own admitted slot under the lock before it starts. A synthetic 2xx without that shared-root acknowledgement does not suffice. A listener on the adopted port **can relay** the challenge, cookie and CSRF to the real service; the slot proves the real root saw the challenge, **not** who answered that port. Nothing read from that listener supplies the machine ticket, target, owner or authoritative bound result, or authorizes a mutation. Read source/committed instance and recorded grant from the helper's own protected root/pipe, with the hosted read/Owner independently checked. Fetch the read-only pipe projection for an existing binding too; the HTTP descriptor is only a display hint. No request-supplied file path; one short-lived slot, serial creation/cleanup, no stale helper deleting a successor. Keep secrets off all helper transcripts and existing launcher diagnostic tails. A compatible separately installed Runtime can serve the same root; with no usable local executable/root witness, keep ordinary use, do not guess a home or bind. Reuse OS owner-private file/directory protections (including Windows DACL); no broad daemon IPC bearer in Rust. An ordinary instance WebView cannot own this pipe. **Residual:** this confirmation is in the App, not on an avibe.bot page. Code running locally as this OS user, including a local page script able to open a terminal and run commands, can replace the helper. Such code can substitute its own ticket and machine for this computer; native admission does not attest the human, helper binary or physical machine against it. This is the same-user residual accepted for AV-13.

## Primary acceptance: first sign-in on an unbound computer

Start with no saved account or binding, a reachable Runtime and an account allowed to create a personal Avibe. Sign in and wait for account discovery: zero claim starts, grants, pairing writes or random addresses. Open naming: one helper starts one ticket. The App shows the signed-in account, this computer and the hosted `prefilled_prefix`; editing and closing it allocates nothing. Reopen, choose an available prefix and confirm that exact name. If recent proof or MFA is missing, finish the ceremony and read the session and ticket again. Only an unchanged review and private target on that live ticket can use the original confirmation. A changed review goes back to the person; a different available name is never substituted. With the App still open **or killed just after publication**, verify the new protected local binding and fresh matching hosted Owner, then the running service's monitor and address worker. Once restarted, the App uses the existing Owner and does not allocate or grant again. Control variant: let someone take the proposed name before confirm; the person can edit it, with zero pairing calls and no fallback address. Keep real-account verification separate from fault-injection tests.

## Not implemented

**Replacing an ended legacy Desktop enrollment (estimate: half a day, including tests).** Today `_recover_before_start` returns `local_instance_conflict` when it finds a `prepared` record with `desktop_enrollment`; it does not replace that record. The page directs `legacy_review_required` to support. Neither outcome repairs the record.

On a deliberate native naming start, implement the rule above in `_recover_before_start`: under the same pairing lock, recheck the classification and replace only the exact still-current `prepared` record if it was never dispatched, is terminal, or has proven expiry, and has no sealed receipt. Test all three eligible cases. Also test that a changed record, an in-flight or retryable request, and a sealed or uncertain receipt are preserved. No identity or existing binding is replaced.

## Bundled document contract (semantic, pending review)

Settings › Devices is the single entry. Presenting the sheet is not permission to start a ticket. Only its original claim document, after native observation delivers `no_published_binding` for this generation, may request Open once. Open reserves a short receipt for Read or Cancel; it cannot grant, send mail or start a worker. Close, replacement or reload invalidates the private receipt. Cancel returns to the retained Workbench document, not a fresh navigation. The Account document has only `observe_current_binding` on this interface. The claim document can read or check a prefix, submit the displayed review revision, send/submit its confirmation code, cancel or explicitly resume account recovery. A future one-use D1u preview is limited to the exact qualified `other_account` read. No general reset or abandon command: an eligible terminal legacy operation can be superseded only as part of the one explicit start of naming described above. The bridge may take locale, user-entered prefix, a native non-authorizing opaque review revision, or typed OTP as appropriate. No arbitrary method/URL, subject, claim code/ID, target ID, permission flags, sign-in proof, transaction, session jar, OS/file location, `recovery` or `accepted_subject`. Native owns the grant inputs. Existing account sign-in actions remain separate. No side-effecting interpretation of query strings, clicks from instance pages, normal refresh or status polling.

Show only safe state (`unpaired`, review new/existing, `name_taken`, capacity, `confirmation_required`, second factor owed, waiting/finishing, bound, tunnel unavailable, owner conflict, local recovery or upgrade required), native review revision, sanitized local name, hosted read's `account_email`, applicable prefix/validated hostname, bounded retry information, allowable actions and, only in the qualified D1u preview, the producer-masked holder hint and the helper's Health-impact flags. Never describe a grant as bound, a stopped tunnel as unbound, a missing catalog row as deletion, a reservation as released, or a local abandon/reset as deleting remote resources. No codes or unexpected upstream text to copywriters as strings to display. Claude owns both locales, frames, UI and safety copy with the lead.

## Contract differences and release gates for the lead

1. **Bound-before has two different browser actions.** On AV-13 `_BoundSource.load`/rebind requires local predecessor ID **and secret**; with only the installation UUID it returns `not_bound`. After Desktop gets `paired_installation_loopback_required` the local Runtime is ordinarily *unbound*. ## Admitted helper startup, acceptance and publication

The ordinary pipe carries the registered physical home and directory identity into the worker. The slot lock ends at consumption; the claim and config locks protect their open files, not the home name. Startup checks the home before taking a claim lock, across config acquisition, before recovery or identity initialization, and again before the machine start call. After the ticket is issued, the same worker checks the original home again before accepting a grant, after the accept reply, and across pairing locks, redemption and publication. Matching installation and binding data are still required; they do not substitute for the directory check. Losing admission stops the next action: it does not undo a dispatched request, discard a prepared or sealed journal, or serialize a directory move with every writer.

Four isolated real-child cases use the private pipes and a no-network issuer. On the unchanged home, startup retired a fixture revocation journal, created an installation identity and returned a ticket. Replacing the directory at the same path or running the default home migration before work left the journal intact, with no identity, claim lock or issuer start. Changing the selected home after source acquisition but before dispatch also made no start call and left the successor untouched. The child's environment was fixed before launch in all four cases.
