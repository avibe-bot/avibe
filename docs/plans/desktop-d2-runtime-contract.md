# D2 Runtime contract (R1/R2)

Baseline: `origin/master 3913091383` (2026-11-20). Migration allocation: `20261120_0092` after `20261118_0091`. Scope: local-instance answer authority and system-schedule claim filtering; no native/UI presentation or merge.

## R1 — answer one message

`POST /api/sessions/{session_id}/messages` keeps its existing request and delivery response. Add top-level `operation_id` (nonempty bounded string), `revision` (SHA-256 of UTF-8 compact JSON of the ordered `quick_replies` array, no ASCII escaping), and `in_reply_to` (agent message ID). A choice uses existing `metadata.quick_reply_for`; text uses `in_reply_to` only and remains ordinary user input. Exactly one target is allowed. Native clients supply operation/revision; old Web/iPhone choice requests may omit both and still use the atomic authority. Runtime projects `content.quick_reply_revision` with answerable messages so clients need not reproduce hashing; its absence on old Runtime disables native D2 answer actions. Notification text replies preserve the unsent Web composer draft.

Authorization, active-session and agent-access checks precede replay lookup. Inside one SQLite writer transaction, recheck authorization/lifecycle, find the exact target, validate revision and currentness, and reserve its answer with the existing Delivery. Currentness follows transcript acceptance order (`coalesce(delivered_at, created_at)`, then ID), including pending user Delivery; freshness queries use indexed time ranges and positive live states. A recorded winner takes precedence over stale. Choices must belong to the target's options. Text answers use the same question ownership but never acquire quick-reply input semantics.

Responses add `answer: {operation_id, request_id, outcome, choice, delivery_id}`. Outcomes: `accepted` after controller acknowledgement; `duplicate` for operation replay (with `original_outcome`); `already_handled` with the winner's choice; `stale` for changed revision/conversation; `forbidden`; `not_found`. Refusals use HTTP 409/403/404 respectively; legacy choice duplicates preserve HTTP 200 and `already_answered`. Invalid shape/choice or operation-ID reuse with different input returns HTTP 400 `invalid_answer` / HTTP 409 `operation_conflict`. Original terminal receipts are durable; replay never dispatches again. Revoked access overrides receipt replay. Existing outer authentication/authorization guards retain their coded 401/403/404 responses (no saved receipt disclosed); clients normalize these to forbidden/not_found before interpreting `answer`. Transport uncertainty keeps the existing `dispatch_error: dispatch_pending` and no success outcome; duplicate while pending identifies the original delivery and `original_outcome: null`. `unavailable` remains a client transport result, not an accepted answer.

State: unanswered -> reserved Delivery -> acknowledged (chosen) OR definitively retired (released). Reserve before IPC; only definitive refusal/pre-connect failure may retire/release. Timeout or post-connect error retains ownership and never triggers automatic resubmission. The existing Delivery is the execution authority; no second execution state machine. Persist operation identity/receipt in an additive table; publish `message.updated` after committed acknowledgement. App-only rollback within the current compatibility epoch leaves the new table intact, but an older Runtime does not enforce new operation semantics; native D2 must be disabled on old Runtime. Existing chosen fields remain readable. No destructive migration; recheck revision allocation before final rebase.

Vectors: `tests/fixtures/message_answer_contract_vectors.json`; consuming tests use real SQLite, HTTP routing and controller admission, with only the external agent execution boundary replaced. Cover concurrent choice/text/legacy requests, replay after restart, changed input, stale revision/conversation, revoked access, definite failure and uncertain acceptance.

## R2 — supported new schedule claims

`POST /api/system-schedule/claim` adds optional `kinds: ["alarm", "reminder"]`; omission preserves old clients, `[]` permits no new creates, invalid/duplicate kinds fail HTTP 400 `invalid_kinds`. Filter unbound pending creates in SQL before LIMIT. Existing device-bound recovery and cancellation remain reachable regardless of kinds; `allow_create` retains its existing meaning. No schedule schema or receipt changes. Extend shared `tests/fixtures/system_schedule_contract_vectors.json` with claim-filter vectors; existing Desktop/iOS request/receipt vectors remain canonical.

Forwarder populates kinds from `systemSchedule.capabilities` (iOS 26: alarm; Mac: reminder), approved as a bridge-only scope extension. Old iOS packages omit kinds and retain old behavior; new TestFlight packaging is needed on phones. Unavailable/malformed capabilities yield [] so only bound recovery/cancel continue. Proposed neutral copy: EN “Waiting for your device to return the result.” / ZH “正在等待设备返回结果。” Existing Runtime `status_message` is English; use canonical i18n if localized here. UI waiting copy belongs to U1.
