# D2 Runtime contract (R1/R2)

Baseline: `origin/master 3913091383` (2026-11-20). Migration allocation: `20261120_0092` after `20261118_0091`. Scope: local-instance answer authority and system-schedule claim filtering; no native/UI presentation or merge.

## R1 — answer one message

`POST /api/sessions/{session_id}/messages` keeps its existing request and delivery response. Add top-level `operation_id` (nonempty bounded string), `revision` (SHA-256 of UTF-8 compact JSON of the ordered `quick_replies` array, no ASCII escaping), and `in_reply_to` (agent message ID). A choice uses existing `metadata.quick_reply_for`; text uses `in_reply_to` only and remains ordinary user input. Exactly one target is allowed. Native clients supply operation/revision. Legacy Web/iPhone requests omit both: they retain earlier unanswered groups, skip freshness checks, and keep existing session/access error bodies; valid option selections gain atomic ownership. Missing/non-agent targets, missing options, and non-option input retain ordinary dispatch and its original response without an answer receipt. Legacy refusals are not persisted. Runtime projects `content.quick_reply_revision` with answerable messages so clients need not reproduce hashing; its absence on old Runtime disables native D2 answer actions. Draft effects depend only on the original request action: quick_reply_for, in_reply_to, and retry_for preserve the unsent Web composer draft, including legacy passthrough. Only ordinary composer sends clear it and return draft_advanced: true.

Authorization, active-session and agent-access checks precede replay lookup. Inside one SQLite writer transaction, recheck authorization/lifecycle, find the exact target, validate revision and currentness, and reserve its answer with the existing Delivery. Acceptance is the only conversation order: transcript rows use (`coalesce(delivered_at, created_at)`, then ID), and live user Deliveries precede a new answer regardless of submission time. Exclude only the question-producing turn's own still-claimed initial inputs, using the question's stored turn ID with `MESSAGE_TURN_ID_SQL` semantics. Freshness queries use the transcript time range and positive live-state index ranges; never compare Delivery submission time. Transcript freshness counts user/agent rows; live freshness counts user-authored input only, leaving other system/harness authors outside this contract. A recorded winner takes precedence over stale. Choices must belong to the target's options. Text answers use the same question ownership but never acquire quick-reply input semantics.

Responses add `answer: {operation_id, request_id, outcome, answer_kind, choice, delivery_id}`. `answer_kind` is `choice` or `text`, describing the winner for `already_handled`; text always returns `choice: null`. Clients render text already handled as EN “Already answered on another device.” / ZH “已在其他设备上回复。” without quoting input. Outcomes: `accepted` after controller acknowledgement; `duplicate` for operation replay (with `original_outcome`); `already_handled` with the winner's type/choice; `stale` for changed revision/conversation; `forbidden`; `not_found`. Refusals use HTTP 409/403/404 respectively; legacy choice duplicates preserve HTTP 200 and `already_answered`. For native requests, invalid shape/choice or operation-ID reuse with different input returns HTTP 400 `invalid_answer` / HTTP 409 `operation_conflict`. Original terminal receipts are durable; replay never dispatches again. Revoked access overrides receipt replay. Existing outer authentication/authorization guards retain their coded 401/403/404 responses (no saved receipt disclosed); clients normalize these to forbidden/not_found before interpreting `answer`. Transport uncertainty keeps the existing `dispatch_error: dispatch_pending` and no success outcome; duplicate while pending identifies the original delivery and `original_outcome: null`. `unavailable` remains a client transport result, not an accepted answer.

State: unanswered -> reserved Delivery -> acknowledged (chosen) OR definitively retired (released). Reserve before IPC; only definitive refusal/pre-connect failure may retire/release. Timeout or post-connect error retains ownership and never triggers automatic resubmission. The existing Delivery is the execution authority; no second execution state machine. Persist operation identity/receipt in an additive table. Update only raw JSON answer fields: `quick_reply_answer_kind` plus `quick_reply_chosen` (option, or empty string for text); preserve private model context. Publish `message.updated` after acknowledgement. If the process exits after controller acceptance but before acknowledgement, chosen/SSE remain pending until the original operation replays. App-only rollback within the current compatibility epoch leaves the new table intact, but an older Runtime does not enforce new operation semantics; native D2 must be disabled on old Runtime. Choice markers remain readable. Text answers store an empty chosen string, which older Runtime get/set helpers and pet state treat as unanswered: after App-only rollback, those questions can be answered again and the pet can show them as waiting. A long-lived reserved user Delivery (for example after uncertain dispatch) makes native answers stale until recovery settles it, matching the queue fence it already owns. No destructive migration; recheck revision allocation before final rebase.

Native answer decisions, in order (legacy skips freshness only):

| Existing event/state | Decision |
| --- | --- |
| Archived session or revoked access | stale / forbidden; no receipt disclosure after revocation |
| Same operation | duplicate; no dispatch |
| Non-retired winning answer or chosen marker | already_handled, before freshness |
| Later transcript user/agent row in acceptance order | stale |
| Live queued user input | stale, regardless of submission time |
| reserved / pending_steer / steering / reconciling_steer | stale, including steer targeting the question's turn |
| claimed / interrupt_waiting belonging to another turn | stale |
| claimed initial input belonging to the question's own turn | excluded; already consumed to produce the question |
| interrupt_waiting, even in the question's turn | stale; the claimed-start exception does not apply |
| retired input | excluded |
| No blocker | atomically admit and bind the answer |

Vectors: `tests/fixtures/message_answer_contract_vectors.json`; consuming tests use real SQLite, HTTP routing and controller admission, with only the external agent execution boundary replaced. Cover concurrent choice/text/legacy requests, replay after restart, changed input, stale revision/conversation, revoked access, definite failure and uncertain acceptance.

## R2 — supported new schedule claims

`POST /api/system-schedule/claim` adds optional `kinds: ["alarm", "reminder"]`; omission preserves old clients, `[]` permits no new creates, invalid/duplicate kinds fail HTTP 400 `invalid_kinds`. Filter unbound pending creates before LIMIT using a correlated operation primary-key lookup; empty kinds skips this query. Existing device-bound recovery and cancellation remain reachable regardless of kinds; `allow_create` retains its existing meaning. No schedule schema or receipt changes. Extend shared `tests/fixtures/system_schedule_contract_vectors.json` with claim-filter vectors; existing Desktop/iOS request/receipt vectors remain canonical.

Forwarder populates kinds from `systemSchedule.capabilities` (iOS 26: alarm; Mac: reminder), approved as a bridge-only scope extension. The forwarder is part of the Runtime-served Workbench page; the native capabilities bridge shipped in #3930. Updating Runtime therefore makes existing iPhones with that bridge send kinds, without a new TestFlight package. Actual clients omitting kinds retain unrestricted legacy claims. Unavailable/malformed capabilities yield [] so only bound recovery/cancel continue. There is no authoritative registry of all device capabilities. A kind unsupported by the current device stays pending for another device until expiry (default 300 seconds); the Agent now waits for timeout instead of receiving an immediate unsupported receipt from an incapable device. Early unsupported detection is deferred until an authoritative capability-registration contract exists. Approved neutral copy: EN “Waiting for your device to return the result.” / ZH “正在等待设备返回结果。” Existing Runtime `status_message` is English; use canonical i18n if localized here. UI waiting copy belongs to U1.
