# Device sign-out and the account session

The two Devices actions end this Runtime's selected sessions immediately and, where authorized, ask the issuer to end the associated account sign-in. A device row can represent many Runtime cookies. A provider sign-in can appear on several rows. This extends the [instance device registry](instance-device-registry.md) and consumes `avibe-bot-backend/docs/plans/personal-instance-account-session-sign-out.md`. No page changes in this PR.

## HTTP contract

- Both existing POSTs keep `{ok:true,revoked_sessions:N}` and add `sign_out_results: DeviceSignOut[]`. A device result is `{operation_id,device_id,kind,display_name,group,local_status:"ended",account_results:[{status,reason,count}]}`. Count distinct account refs per device; count unreferenced local sessions separately, or one no-reference result for a push-only row. A `local_status` describes selected local sessions/push, not the whole machine. Bulk cutoff may cover unknown old cookies: they are not enumerable and get no invented receipt. Existing forbidden/not-found/host errors stand.
- `GET /api/devices` adds `recent_sign_outs: DeviceSignOut[]` outside live groups (empty for LAN setup). Return up to 100 newest visible receipts; `operation_id` remains stable across polls. POST reports only committed information, usually `pending` or `not_applicable`; GET reports later outcomes. No provider inventory, SID or reference is returned.
- `group` says whose device it was for the person reading: `"mine"`, `"others"`, or `null` when that is not known. It is worked out at each read from what the registry recorded at sign-out (the receipt's account and the role that account signed in with), by the rule of the live list: for a signed-in viewer, their own account's devices are `mine`; for a viewer on this computer itself, which has no account, the devices that signed in as Owner are `mine`. It is `null` for a device with no proven account (unattributed push) and for every receipt with no recorded role, which is every receipt written before revision 0098. It is never worked out from a name or a kind, and it changes who sees nothing: a member still gets only their own receipts.
- Pairs: `pending/queued|retrying`, `accepted/null`, `not_applicable/no_reference|not_eligible|shared_sign_in|keeper_unknown|binding_changed`, `refused/credential|protocol`, `unconfirmed/retry_exhausted`. `no_reference` cannot distinguish old software from a suppressed optional claim. Errors never assert that a provider session still exists. No `ended` account result.
- Ordinary browser logout (`revoke_browser_session`) remains **local only**. Account revocation cannot invalidate existing Runtime cookies on another Avibe. Those cookies follow that Runtime's own local authorization, sliding renewal and absolute cap. The ended **provider session** can no longer refresh or authorize a fresh OIDC login there; this is not global Runtime-cookie revocation.

## Upgrade, rollback and retention

Revision 0096 follows 0095. Additive, no backfill and no sign-outs on upgrade. Revision 0098 adds one table, `remote_signout_receipt_roles` (`receipt`, `login_role`): a row is written with its receipt, in the sign-out transaction, when the device had a proven account, never updated, and removed with the receipt. It is a table and not a column because a migration here must be a literal operation and also safe to replay on a database that already has the head shape; adding a column cannot be both. No backfill, so earlier receipts keep `group: null` until they expire. An older binary ignores the table: its receipts carry no role, and a role whose receipt it removed is swept by this version's worker. An older binary does not dispatch new work, enforce the digest fence, record account outcomes or collect these new rows. Local SID tombstones continue according to #4080's rollback rules; a cloud logout already committed is not undone. On return to this version, resume verifying the same pairing and budgets and expire terminal receipts. The current version denies generic SQL reads of every table holding references. The predecessor does not know those table names: **if it is run against this DB with ref-bearing rows, its generic query can return the opaque references**. A reference cannot revoke a login without the current device secret (held outside SQLite). Do not silently erase outstanding work or add separate Runtime key handling on downgrade; this predecessor-query exposure is an accepted rollback residual. A host administrator with the pairing secret is inside the accepted trust boundary. If the predecessor's SQLite compatibility gate prevents startup, do not bypass it.

The digest is not a usable revoke target. Keep it after unconfirmed/refused work while this pairing is valid; after acceptance only for the bounded in-flight callback window. Never let a delayed, previously verified token publish after that window. Pairing invalidation retires fences. Erasure refers to live application rows, not retroactive deletion of protected filesystem backups.
