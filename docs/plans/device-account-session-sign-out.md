# Device sign-out and the account session

Agreement checkpoint, before implementation. This extends the [instance device registry](instance-device-registry.md); the issuer contract is `avibe-bot-backend/docs/plans/personal-instance-account-session-sign-out.md`. There is no UI change. A device row can group many Runtime cookies. An account session is a provider sign-in, not a machine: multiple cookies, even on different rows, can derive from the same sign-in.

| Who could do what | What would be lost | Rule | Acceptance check |
|---|---|---|---|
| A remote client supplies or copies a reference | Another instance's or person's sign-in | Only take a well-shaped optional claim from the completed, signature/issuer/audience/nonce-verified ID-token exchange, tied to that subject, pairing generation and newly assigned local SID. Never take it from self-report, cookies, request JSON or renewal. No backfill. | Missing claim leaves login intact and local only. Forged token, wrong nonce and wrong audience cannot create a binding. Renewal preserves the original association and cannot restore one after sign-out. |
| A member or maintenance principal has device-management rights, or an owner removes another account's device | Forced account logout outside the actor's authority | Preserve existing local authorization, origin/CSRF and loopback boundary. For the account operation, a remote actor must have current authenticated owner **source** and owner role, and the target must be their own signed subject. Direct paired loopback acts as the instance under the producer's explicitly accepted host-trust rule. A previously verified owner ref identifies the target, never a display role/email. The issuer makes the final current pairing/workspace/owner decision; no guessed workspace eligibility from local kind. | Member and elevated non-owner, demotion, cross-subject owner removal and missing evidence: local action only where already authorized; zero upstream calls. Unauthorized target remains untouched. 403 from issuer is `not_eligible`. |
| A lost device signs in while the issuer is unavailable | A usable Runtime cookie after apparent sign-out; or a forgotten account action | In the same SQLite transaction select authorized sessions, stop applicable push, write existing SID tombstones/cutoff and enqueue unique account work; publish local events only after commit. Never perform or await network I/O on the route. Keep a binding-scoped, non-redeemable ref digest fence so an already-redeemed callback presenting that ref cannot mint a usable cookie; serialize with fresh enrollment. Never block a genuinely independent fresh sign-in. | Commit failure installs neither half. After successful return old cookie is denied while upstream is hung; kill/restart before send and after accepted send before ack, then finish idempotently. Race callback before/after commit; test duplicate requests and renewal. |
| Remote B signs out others, with several Runtime SIDs derived from the same account session | B itself, even if its SID was excluded | Preserve #4080 local bulk scope (caller's subject minus caller SID; loopback all remote). Account work must exclude every target ref equal to the kept sign-in's ref, even across device IDs. With unknown keeper ref it is impossible to prove disjointness: propose local-only for that subject's bulk account work. A kept logical device may have several SIDs; propose preserving all its known account refs, without claiming its other local SIDs survived. | Two distinct refs A/B: only A sent; A/B sharing a ref, unknown keeper ref, and multi-SID current row: no request targeting a possible keeper. Loopback has no remote keeper. Deduplicate repeated target refs across affected rows. |
| Two visible device rows share a provider sign-in | Signing out one would also sign out the other at the account | For an explicit sign-out propose preserving a ref if another non-target live device still uses it; report `shared_sign_in`, not account success. Explicitly targeting one's current row otherwise retains the existing self-cookie clearing behavior. | Same ref across two rows vs same ref twice within one target row; only the second case sends one upstream request. |
| A worker retries against a new tenant or leaks a capability | Wrong account affected, instance secret disclosed, sign-in inventory exposed | Bind queued work to the enrolled instance and generation; on unbind/transfer discard dispatch authority and purge old raw refs. Recheck before each send; never send old work with replacement credentials. Fixed trusted HTTPS backend, no redirects, bounded timeout, device-secret auth and JSON only. Keep raw refs only in private registry/queue storage, excluded from generic data query/exports, never in request URLs, error diagnostics, events, cookies or API output. Erase on obsolete binding, session expiry/removal (except committed work), or terminal processing. | Re-pair with same instance ID/new generation, redirect, expiry and terminal cleanup; cannot obtain ref via generic SQL API, ordinary responses or error logs. Backend may silently no-op on stale refs. |
| Issuer replies, throttles, stalls or never recovers | False success, infinite retries or silently lost work | Empty 204 means `accepted` (including no-op), **not** proof an existing session was ended. 403 → `not_applicable/not_eligible`; 400/415 → `refused/protocol`; 401 → `refused/credential`. Retry transport failures, 429 (at least 600s across binding), 503 and indeterminate responses with durable deadlines, capped backoff and leased/idempotent dispatch. Propose 24h or 32 charged attempts, whichever first; then terminal `unconfirmed/retry_exhausted`, not `refused` or `ended`. No full response bodies logged. Retain non-secret receipts 7 days after completion. | Fake actual HTTP boundary for all statuses, dropped response, slow response, quota and exhaustion across restarts; no tight loop. Independent requests for distinct refs, bounded concurrency. Unknown success never becomes definite refusal. |
| Viewer refreshes after a partial bulk sign-out or concurrent re-login | Missing status, false all-success, or historical status on a fresh device | Return immutable per-operation device receipts; aggregate **counts per outcome and reason**, not one winning result. Keep completed devices out of the live list. Expose separate recent sign-out receipts with the same device ID; distinguish a new login by operation ID, do not re-create a live row from a receipt. Scope reads to original binding and authorized subject; no account identifiers beyond normal viewer scope, no raw refs/SIDs. | Pending → accepted, 403 and mixed old/new rows persist across reload. Member cannot read another user's receipts; fresh login not mislabeled. Push-only device yields a no-reference result even with zero revoked sessions. |

## Proposed route contract

- Both existing POSTs keep `{ok:true, revoked_sessions:N}` and add `sign_out_results: DeviceSignOut[]`. A device result has `{operation_id,device_id,local_status:"ended",account_results:[{status,reason,count}]}`. Count distinct referenced sign-ins per device; count no-reference local sessions separately, or one no-reference device for a push-only row. A receipt describes the targeted sessions, **not** a new device presence or proof the entire physical device was signed out. Existing bulk cutoff still covers unknown old cookies: they are not enumerable and must not get synthetic device results. Unknown/forbidden/host routes retain existing errors.
- `GET /api/devices` adds `recent_sign_outs: DeviceSignOut[]` outside the live groups (including `[]` for limited setup listing); POST snapshot reflects only committed local information, typically `pending` or `not_applicable`. Read again to see worker outcomes. No UI changes. Read scope, bounded pagination/limits and retention to be agreed before implementation.
- Status/reason pairs: `pending/queued|retrying`, `accepted/null`, `not_applicable/no_reference|not_eligible|shared_sign_in|keeper_unknown|binding_changed`, `refused/credential|protocol`, `unconfirmed/retry_exhausted`. A refused protocol request does not assert the account is still active. Device secret, user tokens and account-session ref never appear in these structures.

## Decisions needed before coding

1. The brief's “account sign-in ended” cannot be proven with #388: valid wrong-scope, replay and success receive identical 204. Use accepted/idempotently processed; no provider inspection from the Runtime. Likewise exhausted retries must remain unconfirmed rather than definitely refused. An absent ref alone cannot distinguish old client, non-owner, and reference issuance failure; say `no_reference` where that is all we know.
2. “Do not guess eligibility locally” is not authorization to send a member's or another subject's account request; #388 requires an honest actor/target gate. Confirm the actor boundary and shared/unknown keeper rules above. A provider sign-in may appear under several local IDs. An optional ref omitted by the issuer also makes absolute protection against re-entry on a no-ref callback impossible; do not widen this into blocking every normal ref-less login. A digest fence after exhausted work needs an explicit retention boundary: propose retaining a digest for the pairing lifetime unless the operation was accepted and the remaining in-flight callback window has passed. This is not a raw ref or a provider lifetime estimate.
3. #4080 deletes signed-out rows, and the view types have no status or tombstone row. Confirm separate scoped receipts, not ghost devices. Confirm retention/retry bounds and the explicit `unconfirmed` state.
4. #4098 already touches selection, activity and models/migration history. Coordinate its landing/base and the minimal transaction seam through the lead; no schema revision claimed here.
