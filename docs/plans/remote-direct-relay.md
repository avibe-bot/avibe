# Phase 2a: an authenticated relay for one owner trial

This implements the relay part of [the direct paths plan](remote-direct-paths.md), not hole punching. The relay is a packet forwarder, not an Avibe origin. One dedicated relay serves **one account, one paired instance and only that owner's App endpoint keys attested by that instance**. It is not a shared service. This contract does not authorize provisioning or enablement.

## Admission: a lease at the backend, not a bearer in the App

The pins in `packaging/iroh-apple/versions.env` are iroh and iroh-relay 1.4.1, noq 1.4.0. The stock relay binary chooses one policy (`iroh-relay/src/main.rs:162–200,216–247,250–287,366`):

| Policy | Decision at connection time | Why or why not |
| --- | --- | --- |
| Everyone (default); denylist | Everyone, or everyone except listed endpoint keys | Neither fails closed for unknown keys. Never start the trial with the default config. |
| Allowlist | Only listed endpoint keys | No native TTL or pairing check. Removing a key does not disconnect it. |
| Shared token | Possession of any configured bearer | Native clients can present a bearer header; the server also accepts a query fallback. The list does not bind a bearer to a key, instance or expiry. Not used. |
| **HTTP** | POST with the handshake-proven endpoint ID; only HTTP 200 with body exactly `true` admits | Chosen. The bearer on this POST is the relay's private service credential, **not** a credential supplied by the App. Errors and any other body deny. |

See `iroh-relay/src/client.rs:236,321`, `src/server.rs:225–231,256–305`, `src/main.rs:298–340` and `src/protos/handshake.rs:488–501`. The handshake proves possession of a key; it says nothing about who owns a pairing. The hook runs once before registration. The disconnect hook is a notification, not reauthorization.

1. The control plane, with a fresh direct permission for the authenticated paired instance, supplies an optional `relay` object containing `version: 1` and one canonical HTTPS relay origin. The origin is operator-configured; no user override, redirects, userinfo, query, fragment or public default relay. Absence means disabled. Both policy switches, current pairing, direct opt-in and sidecar readiness are prerequisites for publication.
2. The paired instance registers **its own** public sidecar key and current rendezvous generation using pairing authentication. For an App lease, the instance additionally attests the App key from the existing [authenticated rendezvous](remote-direct-rendezvous.md), after authorizing the **owner's subject**, not merely any authenticated user. The backend validates the current trial tuple and pairing; the public App cannot self-register. Backend state contains relay identity, account, paired instance, role, endpoint key, generation and expiry, not LAN addresses or session credentials. Refuse ambiguous key reuse across roles, instances or active generations; fence late writes against retirement.
3. Use server-side leases of **at most 300 seconds**, clipped to remaining direct permission and, for the App, remaining local peer admission. Only fresh evidence from the same authority can renew. Delayed retries cannot extend an old grant. Revoke on loss of pairing, generation retirement, removal of owner admission or either switch turning off. Never carry old keys or outstanding work into a new account. A service-authenticated callout mapped to this dedicated relay answers `true` only for a single current matching lease with both switches on; malformed IDs, missing authority, timeouts or uncertain reads deny. Do not cache positive decisions at the HTTP layer. A URL, source network or a public key by itself grants nothing.
4. Configure the sidecar and native App with a custom one-entry relay map (`iroh-relay/src/relay_map.rs:239–260`), not the default relay set. The instance returns `endpoint.relay: {"version":1,"url":"https://relay.example.invalid","expires_at":1800000300}` only after the instance relay is ready and the matching App lease is confirmed. The capability is the server-side lease plus proof of the associated private key, **not** a transferable secret in the answer. The enclosing `instance_id`, hostname, `generation` and echoed `client.endpoint_id` bind this field; the existing request-start monotonic deadline is additionally clipped by `relay.expires_at - issued_at`. A changed relay origin or authority invalidates the old publication. Recheck authority after asynchronous registration and before writing the answer. Failure omits relay (`null`) without suppressing otherwise usable Phase 1 candidates. Old clients may ignore the optional object; old instances return null. Unknown relay versions, expired or malformed objects never select another relay.

## What revocation stops

The HTTP policy refuses **new** connections after revocation. The instance withdraws relay publication and removes affected local peer admissions; the sidecar closes their application connections, and a stopped supervisor closes its relay connection. An App account switch closes the old endpoint and invalidates its probes, cached answers and routes; do not wait for a client logout notice as a security control. If notifications are lost, leases expire without refresh. No peer may enter CONNECT merely by connecting to the relay.

**There is no finite stock relay session lifetime implied by the lease.** The 1.4.1 server has keepalives, not an absolute max-age or built-in periodic restart (`src/server/client.rs` client loop; `src/main.rs` configuration; `src/server.rs` shutdown). An already connected client may keep forwarding ciphertext after lease expiry. Forwarding looks up a destination endpoint key, not a permitted instance–App pair (`src/server/client.rs:500–531`, `src/server/clients.rs:200–212`). Local revocation is not evidence of a relay disconnect.

Before changing account or pairing: **deny all new registrations and handshakes first**, invalidate old leases and pending writes, stop every serving relay process, and verify old connections ended and the replacement started with empty sessions under deny-all. Only then authorize the next cohort. If any step cannot be verified, stay closed. An empty lease table, rolling restart with overlap, or new DNS target is not that proof. The global switch alone stops new admission; for an immediate relay-wide traffic stop the operator must also stop all serving processes. The per-instance relay switch disables only this transport; the existing direct-off switch disables direct as a whole. Neither changes Cloudflare or ordinary auth.

## Paths and probe boundary

2a adds the relay to already-known authorized addresses. No discovery service, port mapping, relay QUIC address-discovery listener, default relay lookup or deliberate punching workflow. Configure relay `enable_quic_addr_discovery = false` and client relay node `quic: None` explicitly, keep minimal endpoint configuration on both sides, and disable observed-address reports in both directions. Do not interpret that as disabling the stock negotiated NAT extension: iroh `src/endpoint/quic.rs:447–460,535–550` ignores limits below eight, whereas noq-proto `src/config/transport.rs:481–482` can represent zero. No fork or zero patch ships in 2a. Ordinary QUIC path validation remains.

The relay **widens who can reach the pre-admission transport window**: a connected relay user need not be on the destination LAN. Refusal by the sidecar protects streams, not everything that precedes the peer check. See [transport §8](remote-direct-transport.md#8-open-risks-to-verify-early). The dedicated trial contains the audience; it does not eliminate this window. Cross-destination forwarding, unbounded live relay connections and pre-admission probes are **gates before opening direct to other users**. Do not admit shared or overlapping cohorts. Before any 2b punching review round, writer and reviewer first agree on one paragraph naming who could abuse probes, what they could do, and the smallest limit that stops that abuse. That agreement is not a 2a gate.

Use the existing App path controller: keep Cloudflare usable while probing; only a verified peer, CONNECT stream and successful inner TLS verification of the selected managed hostname qualify the candidate. A relay socket or a rendezvous answer is not success. `DirectIngress` and ordinary remote auth remain mandatory. The relay sees endpoint and traffic metadata and encrypted transport packets, never inner TLS plaintext or application credentials. A stale probe cannot install a route. Do not replay an uncertain mutation when falling back; change path for subsequent requests. Report relayed versus known-address paths from observed transport state, not URL presence.

## Operations and acceptance

The intended location is Hong Kong; the main operator owns it and the owner selects the provider. Use a valid renewable certificate for the relay hostname, independent of the instance certificate. Keep the admission service credential server-side, use authenticated HTTPS to the fixed callout with no redirect to another service, and keep health/metrics private. Verify loaded HTTP policy before exposing the listener. Configure and exercise finite handshake/concurrency limits, connection and byte rates, bounded callout time and an egress ceiling at the relay or its hosting boundary. On exhaustion reject relay work, not ordinary instance traffic. Record active sessions, allows/denies/errors, bytes in/out, certificate lifetime and fallback health without addresses, endpoint identities, private URLs or credentials in metric labels. Compare measured host/provider egress with relay byte counters; payload bytes are not a bill. Budget and disconnect runbook must be approved before deployment.

| Environment | Evidence required before trial |
| --- | --- |
| Hosted CI, isolated relay and mock authority | Use stock pinned HTTP mode and real endpoint keys. Prove denial for unknown, expired, wrong-generation and revoked keys on **new** connections; callout outage denies. Separately observe a held connection across lease expiry and verify whole-process disconnect and clean restart under deny-all. Exercise stale registrations, owner/account switch and both kill switches. |
| In-CI interop | With direct routes unavailable, prove a real relayed CONNECT, verified inner TLS and authenticated request. Verify wrong peer/certificate/auth rejection, stale answers and fallback without replay. Confirm neither client uses public relays or configured discovery. Also exercise known-address-only, older/null and disabled configurations. |
| Local disposable Incus topology | Repeat with distinct client/instance networks and a controlled relay failure. Inspect the selected path, sidecar stream teardown, absence of stale publication, private metrics and measured egress. Do not infer a production or phone result from this run. |

Delivery order after this contract merges: sidecar, supervisor/rendezvous, backend admission, then hosted interop. App dialing is a separate consumer. Until all relevant components and the operational gates are ready, omit relay; do not turn on a permissive temporary service.
