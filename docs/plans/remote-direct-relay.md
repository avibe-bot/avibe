# Remote direct paths: public-relay owner trial

## Instance preferences and server permission

Ordinary direct access now defaults on. The 3.2.7 config writer stored `direct: false` even for an untouched setting; it cannot be distinguished from a deliberate off. The upgrade treats that unmarked false as the default. New explicit choices are recorded on disk, including an off that survives unrelated settings saves. A preference alone cannot start an endpoint: pairing, a verified binary, fresh authenticated permission, a usable certificate and strict ingress still gate publication. Direct failures leave the ordinary tunnel alone.

A wake from suspend does not renew a receipt: its 15-minute lifetime includes sleep. A definitive credential refusal withdraws the grant; an outage leaves the original deadline unchanged. The automatic installer needs a fresh direct grant before it may run, independently of the manual install command. Heartbeat replies are ordered for the binding, while endpoint and certificate work are fenced by endpoint generation. A failed certificate order in cleanup retains its order ID and backs off; only after the backend reports settlement can a fresh order be requested. An unreadable or invalid legacy enrollment record is not evidence that a pairing was untouched: relay stays off until the record can be interpreted.

The public trial has an additional gate: the same fresh instance receipt must contain Boolean `true` for **both** `direct_access_allowed` and `public_traversal_allowed`. A renewal without the public grant retires the public endpoint; ordinary direct can resume without relays.

**Open to every instance (decided by the owner, 2026-11-26).** The public relay and hole punching open to every user with the release that carries this change, governed by the server. An instance uses the public relay policy when the same fresh receipt carries Boolean `true` for `public_traversal_allowed` **and the user has not turned the relay off**. No host CLI enrollment and no local opt-in is required, and an upgrade alone brings an instance under the server's switch. A false, missing, non-Boolean or expired grant gives no relay; ordinary direct goes on without it.

The user's off is one of two things. A recorded choice (`public_relay_choice: off`, written by `vibe remote direct relay public-trial off` or by the connection page's switch) wins over the server's grant and survives restarts and unrelated saves. A reset of the binding returns it to the default with the pairing's other preferences, as it does the choice for ordinary direct; the relay then follows the server again. For an instance from before choices were recorded, the setting found off **on a pairing the host had enrolled** is an off too: it was once on there, and someone turned it off. The same unrecorded off on a pairing that was never enrolled is the released default and follows the server. The host enrollment no longer gates the lifecycle; it still gates the connection page's relay switch, so the Owner of an instance that was never enrolled turns the relay off from the host shell.

The decision settles the release condition this document carried (an Avibe-operated default-deny relay, a default-off per-instance relay authorization and a control-plane kill switch before the public relay is offered to more users), under the rule to keep only what protects a machine, a key or an account from a named actor:

- **Our own relay is not required.** The public n0 relays are used, with what n0 can observe as described below. What an Avibe relay would add is speed and availability, and a slow or absent relay undoes itself: the path falls back to the tunnel.
- **The default-off per-instance authorization is replaced** by the server's `public_traversal_allowed` together with the user's explicit off.
- **The kill switch exists.** It is the server's `DIRECT_CERT_ENABLED` (direct as a whole) and `DIRECT_PUBLIC_TRAVERSAL` (`all`, or a list of instances). An instance drops the relay at its next status report without the bit (every five minutes), and, with no report answered, when its grant ages out after fifteen.
- **The pre-admission probe residual is accepted** (Probe limit, below): a user of the public relay who knows an instance's endpoint ID can, before the sidecar refuses them, learn its eligible interface addresses and have it send small UDP path challenges to destinations they name. This now holds for every instance that uses the policy, not for the owner's alone.

Unchanged by the decision: while the relay policy is on, every direct admission on that endpoint is Owner-only, so on such an instance a member who is not the Owner gets no direct path, a LAN one included; the installed pin must be a reviewed one that supports the policy, and a traversal grant on a pin that does not leaves that instance without direct (the packaged pin supports it); the relay map is fixed; and the App accepts the policy as described below.

The existing authenticated runtime-status report can include `direct_state`: `off_by_user`, `denied`, `installing`, `install_failed`, `certificate_pending`, `certificate_failed`, or `running`. Only denial and failure may carry `direct_reason`: `download`, `integrity`, `spawn`, `rate_limited`, `provider`, `timeout`, `permission_expired`, or `other`. Omit observations not attributable to this generation. `running` means an endpoint was published, not that a client used it or that a relay is reachable. Neither field reports addresses, identities, or raw errors.

## Current trial (supersedes the dedicated-relay trial below)

**Probe limit agreed before punching review**

A user of the public relay who knows the instance endpoint ID can reach transport registration without Avibe admission. Before the sidecar refuses the peer, stock iroh may disclose eligible interface addresses, including private LAN and IPv6 addresses, and send small UDP path challenges to destinations the peer names. The per-round limits do not bound repeated rounds, and a handshake rate limit does not authorize a destination. The smallest limit that stops this pre-admission exposure is to send neither candidates nor peer-directed probes until the authenticated peer passes admission. After admission, preventing third-party probing is a separate requirement: authorize destinations independently of the peer's nomination and bound probe traffic across rounds. Stock traversal and the late sidecar hook do not enforce those limits. Record the exposure as an explicit owner-trial residual and a gate before admitting other users; neither private rendezvous nor inner TLS closes it. **That gate was lifted by the owner's decision of 2026-11-26 (above): the residual is accepted, as described here and unreduced, for every instance that uses the public relay policy.**

For an instance that uses the policy (the owner's own during the opt-in trial; every instance since 2026-11-26), use the pinned iroh 1.4.1 `defaults::prod::default_relay_map()` (use1, usw1, euc1, aps1) as introducers and fallback. Prefer a verified direct path when stock NAT traversal succeeds; the initial packets may traverse a relay. The public servers are shared, rate-limited development/testing infrastructure; assume no SLA. n0 can observe connection addresses, endpoint keys, timing, volume and ciphertext, not inner TLS plaintext. There is no dedicated-pair boundary or Avibe admission callout on those servers. Do not deploy an Avibe relay for this trial.

Select this fixed map by a versioned trial policy, never by an arbitrary URL override. Use minimal endpoints with no n0 DNS/pkarr address lookup, publishing or discovery; ordinary DNS resolution of relay hostnames is distinct. Only the authenticated instance rendezvous supplies peer identity and starting candidates. A ready answer may have `addresses: []` **only** with a valid, connected relay candidate from the selected map. Publish the observed relay, not the whole map as if connected; bind it to the same instance, peer, generation and authenticated answer lifetime. No backend relay lease is implied. Without a valid relay or direct address the answer remains unavailable. Keep local peer admission, CONNECT, end-to-end TLS, ordinary remote authorization and Cloudflare fallback. The policy requires **all three**: fresh instance grants for both ordinary direct and public traversal, no off by the user, and a verified installed pin that supports this policy. Until 2026-11-26 it also required a host CLI enrollment and an enabled local setting, which kept an upgrade from opting an instance in; since the decision above an upgrade does bring an instance under the server's grant, and nothing local is required. `vibe remote direct relay public-trial on|off` remains a host-shell command: `off` records the user's off, and `on` withdraws it and records the host enrollment. That enrollment now gates only the relay switch of the [connection settings page](devices-connection-settings.md): on an unenrolled pairing the page API omits the relay entirely and rejects both switch values, generic settings writes and CLI invocations carrying remote authority still cannot enroll, both Web off and host CLI off preserve enrollment, and a new pairing needs a new enrollment for the switch to appear. None of this is an access boundary against anyone who can already write the instance configuration or run a shell under the service account. That includes a machine operator and an Owner using Files or Web Terminal. Where those surfaces grant Editors equivalent access, that pre-existing authority applies to configuration generally; this policy does not introduce it. The actual relay publication, not the switch, determines whether it is connected. Updating the binary or granting ordinary direct permission alone never puts an instance on public relays; the server's traversal grant does. Turning the relay off withdraws it, advances generation, and retires the public endpoint; Phase 1 remains available under its existing gates. `direct_access_allowed` is not a relay-specific grant: the relay-specific one is `public_traversal_allowed`.

**Instance admission during the trial.** The authenticated Owner nominates the App endpoint ID through rendezvous, as in Phase 1. No local key pin, CLI enrollment or App ID display is required. This proves an Owner session nominated the key, not that it came from a native App. Viewer and Editor get neither local peer admission nor a relay field. Enforce that restriction for all paths on the trial endpoint, even if the caller already knows the relay and instance ID. Retire prior admissions when entering trial mode; the sidecar still verifies key possession, and every stream still passes strict ingress and ordinary remote auth.

The App validates the enclosing answer and accepts `public-trial-v1` only with an exact URL from its pinned production relay map. Unknown or missing policy, or a nonmember URL, means no relay dialing; never interpret it as the deferred leased mode. Known-address candidates remain independently usable. The public relay field has no independent lease deadline.

Advance the publication generation when the observed relay appears, disappears, changes URL, **or the selected trial policy changes**, even if the endpoint key and IP candidates stay fixed. Fence pending offers and retire the old route; returning to an earlier relay or policy never restores an old generation. With stable key and IPs, test relay A→B, A→null and a policy-only change; in each case a late result for A's old generation cannot install or renew a route.

**Measurement:** the reported Mac trial network carried both UDP and TCP through a Singapore proxy. STUN observed endpoint-independent mapping on that path. This does not establish direct reachability from the phone, inbound filtering behavior or the path used by an application request. In a separate outside-to-home IPv6 check, one unsolicited UDP datagram did not arrive and TCP was refused. Do not rely on unsolicited inbound IPv6 on that path: try relay introduction with both peers sending and retain the relay if direct validation fails. These observations do not prove that punching succeeds. Record the selected path during an authenticated request; separately test fallback with direct UDP isolated. Keep exact egress identifiers in private trial notes.

## Deferred: Avibe-operated relay

Not a precondition for opening the public relay to other users since the owner's decision of 2026-11-26 (top of this document). The following is the dedicated-relay design, not instructions for the public trial. Its backend registration, exact App-key approval, lease/callout fields, operator controls and interop tests are deferred gates. Its single-cohort containment and restart procedures cannot be applied to n0. The earlier relay-first implementation order and no-Avibe-punching assumption below describe that design only.

### Dedicated relay scope

This implements the relay part of [the direct paths plan](remote-direct-paths.md), not hole punching. The relay is a packet forwarder, not an Avibe origin. One dedicated relay serves **one account, one paired instance and only the owner's explicitly approved native App endpoint keys attested by that instance**. It is not a shared service. This contract does not authorize provisioning or enablement.

## Admission: a lease at the backend, not a bearer in the App

The pins in `packaging/iroh-apple/versions.env` are iroh and iroh-relay 1.4.1, noq 1.4.0. The stock relay binary chooses one policy (`iroh-relay/src/main.rs:162–200,216–247,250–287,366`):

| Policy | Decision at connection time | Why or why not |
| --- | --- | --- |
| Everyone (default); denylist | Everyone, or everyone except listed endpoint keys | Neither fails closed for unknown keys. Never start the trial with the default config. |
| Allowlist | Only listed endpoint keys | No native TTL or pairing check. Removing a key does not disconnect it. |
| Shared token | Possession of any configured bearer | Native clients can present a bearer header; the server also accepts a query fallback. The list does not bind a bearer to a key, instance or expiry. Not used. |
| **HTTP** | POST with the handshake-proven endpoint ID; only HTTP 200 with body exactly `true` admits | Chosen. The bearer on this POST is the relay's private service credential, **not** a credential supplied by the App. Errors and any other body deny. |

See `iroh-relay/src/client.rs:236,321`, `src/server.rs:225–231,256–305`, `src/main.rs:298–340` and `src/protos/handshake.rs:488–501`. The handshake proves possession of a key; it says nothing about who owns a pairing. The hook runs once before registration. The disconnect hook is a notification, not reauthorization.

1. The control plane, with a fresh direct permission for the authenticated paired instance, supplies an optional `relay` object containing `version: 1` and one canonical HTTPS relay origin. The origin is operator-configured; no user override, redirects, userinfo, query, fragment or public default relay. Absence means disabled. Both policy switches, current pairing, direct opt-in and sidecar readiness are prerequisites for publication.
2. The paired instance registers **its own** public sidecar key and current rendezvous generation using pairing authentication. An App lease requires two independent records for the same account, pairing and exact key:
   - The native App registers its own locally generated endpoint key through its authenticated mobile control-plane session. The owner explicitly approves that exact key for this trial instance; the backend records the approval. Neither a page, a browser cookie nor a page-accessible native bridge may nominate or approve a key through that channel. A new key needs new approval. Logout, approval withdrawal or pairing retirement invalidates the approval and its leases.
   - The instance attests the same key from an owner-authorized [rendezvous](remote-direct-rendezvous.md) in the current generation. Neither approval nor rendezvous alone grants a lease. The backend validates both records and the current trial tuple before granting or renewing. Backend state contains relay identity, account, paired instance, role, endpoint key, generation and expiry, not LAN addresses or session credentials. Refuse ambiguous key reuse across roles, instances or active generations; fence late writes against retirement.
3. Use server-side leases of **at most 300 seconds**, clipped to remaining direct permission and, for the App, remaining local peer admission. Only fresh evidence from the same authority can renew. Delayed retries cannot extend an old grant. Revoke on loss of pairing, generation retirement, removal of owner admission or either switch turning off. Never carry old keys or outstanding work into a new account. A service-authenticated callout mapped to this dedicated relay answers `true` only for a single current matching lease with both switches on; malformed IDs, missing authority, timeouts or uncertain reads deny. Do not cache positive decisions at the HTTP layer. A URL, source network or a public key by itself grants nothing.
4. Configure the sidecar and native App with a custom one-entry relay map (`iroh-relay/src/relay_map.rs:239–260`), not the default relay set. The instance returns `endpoint.relay: {"version":1,"url":"https://relay.example.invalid","expires_at":1800000300}` only after the instance relay is ready and the matching App lease is confirmed. The capability is the server-side lease plus proof of the associated private key, **not** a transferable secret in the answer. The enclosing `instance_id`, hostname, `generation` and echoed `client.endpoint_id` bind this field. Registration returns a bounded **remaining lease duration** from the backend, not a timestamp to copy. For each required lease anchor the instance-local monotonic deadline to registration **request start** plus the duration (subtract the full round trip on receipt). At answer issuance take the minimum remaining time across both leases and local authority, round down to whole seconds and omit relay if nonpositive. Set `relay.expires_at` to the instance's `issued_at` plus that duration. The App clips its request-start monotonic deadline by `relay.expires_at - issued_at`; both timestamps come from the instance. A changed relay origin or authority invalidates the old publication. Recheck authority after asynchronous registration and before writing the answer. Both instance and App accept a ready authorized relay as the sole candidate (`addresses: []`); neither may reject an empty list before checking relay readiness. An empty list **and** no valid relay stays unavailable. Failure omits relay (`null`) without suppressing otherwise usable Phase 1 candidates. Old clients may ignore the optional object; old instances return null. Unknown relay versions, expired or malformed objects never select another relay.

## What revocation stops

The HTTP policy refuses **new** connections after revocation. The instance withdraws relay publication and removes affected local peer admissions; the sidecar closes their application connections, and a stopped supervisor closes its relay connection. An App account switch closes the old endpoint and invalidates its probes, cached answers and routes; do not wait for a client logout notice as a security control. If notifications are lost, leases expire without refresh. No peer may enter CONNECT merely by connecting to the relay.

**There is no finite stock relay session lifetime implied by the lease.** The 1.4.1 server has keepalives, not an absolute max-age or built-in periodic restart (`src/server/client.rs` client loop; `src/main.rs` configuration; `src/server.rs` shutdown). An already connected client may keep forwarding ciphertext after lease expiry. Forwarding looks up a destination endpoint key, not a permitted instance–App pair (`src/server/client.rs:500–531`, `src/server/clients.rs:200–212`). Local revocation is not evidence of a relay disconnect.

Before changing account or pairing: **deny all new registrations and handshakes first**, invalidate old leases and pending writes, stop every serving relay process, and verify old connections ended and the replacement started with empty sessions under deny-all. Only then authorize the next cohort. If any step cannot be verified, stay closed. An empty lease table, rolling restart with overlap, or new DNS target is not that proof. The global switch alone stops new admission; for an immediate relay-wide traffic stop the operator must also stop all serving processes. The per-instance relay switch disables only this transport; the existing direct-off switch disables direct as a whole. Neither changes Cloudflare or ordinary auth.

## Paths and probe boundary

2a adds the relay to already-known authorized addresses. No discovery service, port mapping, relay QUIC address-discovery listener, default relay lookup or deliberate punching workflow. Configure relay `enable_quic_addr_discovery = false` and client relay node `quic: None` explicitly, keep minimal endpoint configuration on both sides, and disable observed-address reports in both directions. Do not interpret that as disabling the stock negotiated NAT extension: iroh `src/endpoint/quic.rs:447–460,535–550` ignores limits below eight, whereas noq-proto `src/config/transport.rs:481–482` can represent zero. No fork or zero patch ships in 2a. No Avibe-initiated punching in 2a. Stock iroh can itself initiate NAT traversal after registration or address updates and upgrade two honest, admitted peers from relay to an address not in rendezvous (`iroh/src/socket/remote_map/remote_state.rs:289–302,517–532,944–949`). Relay is a candidate, not a wire-path guarantee. Ordinary QUIC path validation also remains.

The relay **widens who can reach the pre-admission transport window**: a connected relay user need not be on the destination LAN. Refusal by the sidecar protects streams, not everything that precedes the peer check. See [transport §8](remote-direct-transport.md#8-open-risks-to-verify-early). The dedicated trial contains the audience; it does not eliminate this window. Cross-destination forwarding, unbounded live relay connections and pre-admission probes are **gates before opening direct to other users**. Do not admit shared or overlapping cohorts. Before any 2b punching review round, writer and reviewer first agree on one paragraph naming who could abuse probes, what they could do, and the smallest limit that stops that abuse. That agreement is not a 2a gate.

Use the existing App path controller: keep Cloudflare usable while probing; only a verified peer, CONNECT stream and successful inner TLS verification of the selected managed hostname qualify the candidate. A relay socket or a rendezvous answer is not success. `DirectIngress` and ordinary remote auth remain mandatory. The relay sees endpoint and traffic metadata and encrypted transport packets, never inner TLS plaintext or application credentials. A stale probe cannot install a route. Do not replay an uncertain mutation when falling back; change path for subsequent requests. Report relayed versus known-address paths from observed transport state, not URL presence.

## Operations and acceptance

The intended location is Hong Kong; the main operator owns it and the owner selects the provider. Use a valid renewable certificate for the relay hostname, independent of the instance certificate. Configure only the exact HTTPS URL of a small trusted callout endpoint. Stock HTTP mode exposes no redirect override and checks the final response (`iroh-relay/src/main.rs:224–233,329–339`); a fixed initial URL alone is insufficient. The endpoint, including its ingress, must never emit 3xx: consult lease state directly or disable redirect following on upstream decision requests and convert every upstream redirect, error or unexpected result to denial. Return `200 true` for allow or 4xx for deny, with no login or canonicalization redirects. Keep its service credential server-side and health/metrics private. Verify loaded HTTP policy before exposing the listener. Configure and exercise finite handshake/concurrency limits, connection and byte rates, bounded callout time and an egress ceiling at the relay or its hosting boundary. On exhaustion reject relay work, not ordinary instance traffic. Record active sessions, allows/denies/errors, bytes in/out, certificate lifetime and fallback health without addresses, endpoint identities, private URLs or credentials in metric labels. Compare measured host/provider egress with relay byte counters; payload bytes are not a bill. Budget and disconnect runbook must be approved before deployment.

| Environment | Evidence required before trial |
| --- | --- |
| Hosted CI, isolated relay and mock authority | Use stock pinned HTTP mode and real endpoint keys. Prove denial for unknown, expired, wrong-generation and revoked keys on **new** connections; callout outage denies. Separately observe a held connection across lease expiry and verify whole-process disconnect and clean restart under deny-all. An otherwise valid owner rendezvous for an unapproved key cannot enroll it. Only the independently approved exact key plus a current matching attestation gets a lease. A redirecting upstream must deny even if the redirect target would return `200 true`; verify that target is never contacted. Exercise stale registrations, owner/account switch and both kill switches. Skew backend and instance wall clocks in both directions and delay registration: the published deadline cannot outlive either lease; exhausting the duration in transit yields no relay. |
| In-CI interop | Isolate direct peer-to-peer UDP throughout the test, including potential stock upgrades. Return `addresses: []` with a ready authorized relay; prove both sides accept it and complete a relayed CONNECT, verified inner TLS and authenticated request. With the same empty list but no valid relay, verify unavailable and Cloudflare fallback. Verify wrong peer/certificate/auth rejection, stale answers and fallback without replay. Confirm neither client uses public relays or configured discovery. Also exercise known-address-only, older/null and disabled configurations. |
| Local disposable Incus topology | Repeat with distinct client/instance networks and a controlled relay failure. Inspect the selected path, sidecar stream teardown, absence of stale publication, private metrics and measured egress. Do not infer a production or phone result from this run. |

Delivery order after this contract merges: sidecar, supervisor/rendezvous, backend admission, then hosted interop. App dialing is a separate consumer. Until all relevant components and the operational gates are ready, omit relay; do not turn on a permissive temporary service.
