# Personal installation claims in the Runtime

**Rule-table review, not merge approval.** Avibe base `9de8182a5` includes #4034. Producer: avibe-backend `564abac` (#387/#389), `docs/plans/personal-installation-claims.md`, `lib/claims/{service,store,http,input}.ts`. Invisible scope: Runtime client, local routes and callable integration functions. No page, public CLI, App sign-in, feature flag, migration, or removal of key-based pairing.

The hosted screen grants a chosen name. The Runtime separately decides whether this machine accepts that account. Neither an installation UUID nor a grant alone proves possession. Match accounts by immutable subject, never email.

Derive return origin from the admitted request, not payload/forwarding claims. | No upstream calls on missing/wrong Origin, CSRF, Host/peer, role, or mode override. Ordinary GETs do not create claims. |

All other admitted origins need link mode. | Literal validation rejects arbitrary DNS, ambiguous IP spellings, userinfo, paths, query/fragment, link-local and unrelated proxy origins. An admitted LAN request gets `link_required` without creating a claim. |
| A code leaks or a server redirects a machine POST. | Account details, verifier, or pairing credentials are exposed. | Independent fresh verifier (32+ random bytes, S256) and redirect state. Verifier stays in memory, sent only to the validated configured TLS peer. Machine requests have no browser credentials, Authorization or Origin and do not follow redirects. | Inspect independent request bodies and all public projections. No URL/terminal/browser/log contains the verifier or key. |

## Journal state and owner exit

Classify under the config lock; resume and replacement decisions revalidate the exact journal operation/request and current binding generation. No forced deletion of credentials, no resetting existing bindings. A **fresh start** means an explicit owner initiation, not a GET, background timer, retry or automatic fallback.

| Existing record | What a fresh start does; how the owner proceeds |
|---|---|
| None | Start only on an unpaired, undamaged data root. Initialize an absent installation ID once; do not rotate it. |
| Legacy `prepared`, no saved redeem request | No exact replay exists. Explicit fresh start may supersede this operation, fenced by its identity/generation; a late old publication loses its CAS. Do not report that no cloud work happened. |
| Desktop-owned `prepared` | Do not steal it. Existing Desktop guard/Resume owns request-bound retry, expired unconsumed grant renewal, or its legacy explicit replacement path. Report an actionable local conflict. |
| Claim-owned `prepared`, exact request saved | Resume that exact request first. Complete → bound; explicit pending or transport/provider failure → retain request and back off, not replacement. If server explicitly returns 409 `registration_indeterminate`, that alone is **not** evidence of consumption or a reason for automatic discard. An explicit fresh owner start may supersede that exact still-prepared operation after replay/revalidation. Confirm expired unconsumed (`pairing_key_expired`) → fresh claim, never another route to the key. |
| `redeemed` / `applied` | Finish existing compare/apply/retire first; never overwrite a sealed success. Failure to apply/retire remains actionable through the existing Resume/repair path. |
| `revoked` / `retirement_pending` | Finish the existing owner revocation/terminal retirement as applicable after checking committed binding state. Never restore revoked credentials or replace a still-referenced record. If inconsistent, report repair required. |
| Unreadable, inconsistent or damaged local credentials | Fail closed without deleting the record or creating a name. Today a fresh legacy key can overwrite an unreadable record; otherwise repair requires explicit operator recovery, not silent file deletion. The later local reset must clear irreparable journals/partial bindings before the legacy exit is removed. |

## Local contracts

- `redirect_origin_allows_auto_accept` owns local redirect eligibility: the actual connection must be direct loopback (`_is_direct_loopback_connection`) and the origin must be canonical under the producer contract. A `409` with `code:"link_required"` means no claim was started: the page should direct the owner to link mode, not resubmit or weaken the origin check. No feature flag or second local confirmation route.
- `POST /api/remote-access/claims` starts redirect only; JSON `{locale}`. Device name/backend come from Runtime. `201 {claim_id,expires_at,form:{method:"POST",action,fields:{user_code,redirect_state},referrer_policy:"strict-origin"}}` plus separate browser cookie. Future page sets **document** policy `strict-origin` and submits a top-level form to the fixed `/api/v1/claims/redirect-entry`; no fetch/iframe or client-supplied destination.
- `GET /api/remote-access/claims/{id}` returns `{state, code?, expires_at?, retry_after_seconds?, account?:{email}, hostname?}`. **`code` is a stable local outcome/error name, never the hosted `user_code`.** No form replay. `POST /api/remote-access/claims/{id}/cancel` with `{}` fences the operation if still eligible. `GET /remote/claim/callback?claim_id=…&state=…` is the fixed return. No confirm endpoint, browser subject override, or form replay. Non-cacheable across success and failure.
- `run_link(*,show_link,expected_subject=None,confirm=None,locale="en") -> dict`: supply exactly one of expected subject or `confirm(email,hostname)->bool`; `show_link(url)` receives public URL only. `run_desktop(*,signed_in_subject,show_link,locale="en") -> dict`: signed-in stable subject required. No visible `vibe remote` change. Machine routes never call session-only `/read` or `/grant`.

## Who can see which decision

| Event | Hosted account screen | Runtime |
|---|---|---|
| Occupied prefix | `taken`, may choose another | Pending unless its own stage/publish actually reports `taken` |
| Another account already granted | Competing screen sees `already_granted`, no other account details/callback | Observes original grant; applies mode gate |
| Existing installation owned by someone else | `other_account`, masked hint only | Pending until local deadline unless owner grants |
| No first-party sign-in proof | Grant 403 `first_factor_reauthentication_required` | Pending; no browser authentication diagnostics |
| Started predecessor with installation hold | Can show `existing` but refuse new grant `binding_unavailable` | New claim pending; old live claimant drives identical accept until terminal/deadline |
| Deleted installation before BE-4, or transferred/otherwise ineligible live target | `binding_unavailable` on read/grant | Start succeeds, observation pending without grant; generic `binding_unavailable` possible after previous grant |
| Same eligible installation/account | `existing`, original hostname only | Normal grant or locally `already_bound` |
| Declined, replaced, expired | Claim may be unavailable | Local successful decline `declined`; known deadline `expired` before accept; 404 before deadline alone proves neither |

Do not rotate the data-root UUID, automatically or manually. BE-4 will allow reclaim after **completed deletion** separately from prefix holds. It does not repair transfer/ownership mismatch, another account's existing installation, or a copied data root (a clone reattaches to the same identity/name, not a second computer). Do not imply these are tombstones or invent recovery for them. Today's fallback for these cases is the existing pairing-key path. Removing it in the later CLI cleanup is conditional on an explicit local unbind/reset action that also discards the installation identity; no online signal in AV-2 does so. Cleartext LAN does not provide confidentiality, traffic integrity or assurance of who chose the hosted account. The on-path risk is not the same as an already-admitted neighbor using the old pairing UI.

## Scope of a later private-network change

Product selected automatic acceptance after a validated return on eligible private-network origins as well; this behavior is **not** in this PR. **Residual risk if that later change ships:** Someone who can read a cleartext local start response and cause a navigation in the initiating browser can bind the machine to their own account. That includes a read-only network observer without owner ingress: the return alone cannot choose a subject, but exposing the form material defeats that separation.
