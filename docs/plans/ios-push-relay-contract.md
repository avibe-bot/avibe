# iOS Push Relay Contract

Status: Phase 1 contract. This document is the shared input for the
`avibe-backend` relay lane and the `avibe` `core/`, `ui/`, and `ios/` lane.

This contract must be merged to `master` before those implementation lanes
split. The implementation lanes may add tests and code, but they must not
silently change a field name, ownership rule, status mapping, or lifecycle
invariant here. A deviation needs an explicit decision from the orchestrator
before implementation.

## 1. Scope

The feature gives the iOS app APNs notifications while preserving the
instance's existing notification decision and encryption path:

```text
Instance
  -> existing Web Push dispatch and authorization gates
  -> RFC 8291 aes128gcm encryption
  -> RFC 8292 VAPID ES256 authorization
  -> authenticated relay registration endpoint
  -> APNs HTTP/2
  -> Notification Service Extension
  -> iOS notification
```

The relay is an opaque ciphertext forwarder. It validates the VAPID
authorization, looks up state, creates the APNs envelope, and forwards the
encrypted Web Push body. It MUST NOT decrypt, inspect application fields,
transform the ciphertext bytes, or persist the Web Push ciphertext or its
plaintext. Base64url encoding the unchanged ciphertext bytes into `avibe.ct`
is the only relay-side representation change. It may store the APNs device
token needed to call Apple, but the token is a protected secret field; logs,
metrics, traces, and audit records contain only its SHA-256 hash.

This contract covers:

- the native `push` bridge and the instance Web Push handoff;
- authenticated installation and registration lifecycle;
- relay delivery validation and APNs mapping;
- payload size and serialization invariants;
- Notification Service Extension decryption and tap routing;
- security, shared crypto fixtures, and end-to-end acceptance;
- Phase 1 prerequisites and lane order.

It does not authorize production deployment, Apple Developer account changes,
production secrets, or merging any implementation PR.

## 2. Fixed decisions

### 2.1 Opaque, stateful endpoint

The endpoint is a stateful random identifier:

```text
https://avibe.bot/api/push/apns/<registration_id>
```

`registration_id` is 32 bytes generated by a cryptographically secure random
number generator, encoded as base64url without padding. Its wire form is
therefore 43 ASCII characters. It is also the `kid` in the APNs `avibe`
envelope and the identifier the Notification Service Extension uses to find
the key record.

The endpoint is stateful because logout, account switching, revocation, and
APNs token invalidation must take effect without waiting for an endpoint
secret to expire. There is no stateless sealing or reversible endpoint
encoding.

### 2.2 Existing instance send path

The instance continues to use `pywebpush` and the current Web Push
subscription path. The instance:

- applies its existing unread, authorization, Project, hidden Session, and
  notification preference gates;
- serializes the notification JSON with `ensure_ascii=False` and compact JSON
  separators;
- encrypts it with RFC 8291 `aes128gcm`;
- signs the Web Push request with RFC 8292 VAPID;
- sends the request to the endpoint returned by `push.subscribe`;
- disables the subscription after a relay `410`, using the existing
  `web_push_service` failure path.

The relay does not become an application server for notification content. The
instance remains the only sender that has the plaintext notification and the
VAPID private key.

### 2.3 Account and installation ownership

The app generates a cryptographically random `installation_id` once per app
installation and keeps it in the native Keychain. The relay creates the
installation only from the account-authenticated login route. That route uses
the existing same-origin `avibe_session` cookie and an exact
`Origin: https://avibe.bot` check. It does not introduce a Supabase bearer
token for push management.

The first login bind creates an installation and returns a
cryptographically-random 32-byte `installation_secret` exactly once. The app
stores the secret in a `ThisDeviceOnly` Keychain item. The relay stores only a
cryptographic hash of the secret. The secret is never exposed to Web content
or the Notification Service Extension, and it is not placed in the App Group
Keychain used by the NSE.

An installation has exactly one current account record and a monotonic
installation `epoch`. `account_id` is retained for audit, abuse controls, and
account-deletion cleanup; it is not the authorization basis for any route other
than the login bind. Each successful login bind uses a fresh random
`sign_in_id`. The first accepted request for a `sign_in_id` advances the epoch
in the same transaction that records the current account and revokes older
registrations. A retry with the same `sign_in_id` returns the durable result
and does not advance the epoch again.

For an existing installation, the login bind requires both the current
same-origin account cookie and the installation credential. This permits the
same device to bind to a different account without requiring the old account
session. The bind transaction:

1. records the account identified by the current login session;
2. increments the installation epoch;
3. revokes every registration with an older epoch by its concrete
   `registration_id`;
4. commits the account record, epoch, and revocations in one transaction.

All routes after login use the installation credential, not the account
session. The exact authorization form is:

```http
Authorization: AvibeInstallation <installation_id>.<installation_secret>
```

The path installation ID and header installation ID must match. The credential
is a device-level bearer: possession permits management of that installation's
registrations, but does not grant access to the account or to any other
installation. A delayed operation remains authorized after logout because its
installation credential survives account-session rotation.

APNs token, environment, and topic changes are a whole-provider-state
replacement through the `PATCH` route in section 5.2.1. That route requires
the current `provider_version`, increments it on a changed replacement, and
never changes the epoch or registrations. A provider update that is identical
to the current state is idempotent and does not increment the version.

### 2.4 Instance identity

One app account may subscribe to multiple instances. The relay identifies an
instance subscription by the SHA-256 hash of that instance's VAPID public key,
not by a client-supplied origin. The app stores the instance origin beside
the native key record for tap routing.

`vapid_key_sha256` is lowercase hexadecimal SHA-256 over the decoded 65-byte
uncompressed P-256 VAPID public key. The delivery request's VAPID `k` value
must hash to this exact value.

## 3. Data model

The logical schema is independent of the backend's storage library. Field
names and constraints are part of the cross-repository contract.

### 3.1 `push_installations`

| Field | Type and wire shape | Owner and invariant |
| --- | --- | --- |
| `installation_id` | Cryptographically random UUID string, primary key | App generates it once and keeps it in the native Keychain. It never changes during the installation lifetime and is not exposed to Web content or the NSE. |
| `account_id` | Supabase subject string | Relay derives it from the same-origin login session. It is audit and cleanup metadata, not a credential for later routes. |
| `epoch` | Positive monotonic integer | Relay increments it exactly once for each accepted login bind. It is the current account-session generation for this installation. |
| `installation_secret_hash` | SHA-256 of the decoded 32-byte installation secret, lowercase hexadecimal | Relay derives and stores it at creation or secret rotation. The raw secret is never stored, logged, or exposed to Web content or the NSE. |
| `device_token` | Nullable opaque APNs token bytes, represented by base64url without padding at the API boundary | App receives it from APNs. Relay stores it as an encrypted-at-rest secret or in an equivalent secret store. It is never written to logs or telemetry. |
| `device_token_sha256` | Nullable lowercase hexadecimal SHA-256 | Relay derives it for redacted diagnostics and responses. It is never used as a CAS value; provider-version CAS covers the complete provider state. |
| `provider_version` | Non-negative monotonic integer | Relay initializes it to `0` and increments it only when a whole provider-state replacement changes `device_token`, `environment`, or `topic`. |
| `device_token_invalid_at` | Nullable UTC timestamp | Relay sets it only after an APNs invalid-token result passes the provider-version CAS rule in section 5.6. A non-null marker applies to the current provider version until a successful provider update. |
| `environment` | `sandbox` or `production` | App supplies it from the build/runtime environment. Debug Xcode builds use `sandbox`; TestFlight uses `production`. It is part of the provider state. |
| `topic` | Bundle identifier string | App supplies `bot.avibe.ios`; relay validates it against its allowlist and uses it as `apns-topic`. It is part of the provider state. |
| `created_at` | UTC timestamp | Relay writes it on first bind. |
| `updated_at` | UTC timestamp | Relay updates it whenever the device token, environment, topic, account record, or epoch changes. |

The provider fields and `provider_version` are read and written as one
versioned state. An APNs delivery captures the version before opening the
upstream request; an invalid-token result may mutate the row only if that
version is still current.

### 3.2 `push_registrations`

| Field | Type and wire shape | Owner and invariant |
| --- | --- | --- |
| `registration_id` | 32 random bytes; 43-character base64url without padding on the wire; primary key | Relay generates it. It is the endpoint path component and the NSE `kid`. |
| `installation_id` | UUID string, foreign key | Relay links it to exactly one installation. |
| `epoch` | Positive integer, foreign-key value by invariant | Relay copies the current installation epoch at creation. A registration can never be created for a stale epoch. |
| `vapid_key_sha256` | Lowercase hexadecimal SHA-256, 64 ASCII characters | App computes it from the instance VAPID public key. Relay stores it and verifies it on every delivery. |
| `created_at` | UTC timestamp | Relay writes it once. |
| `revoked_at` | Nullable UTC timestamp | Relay sets it once when the registration is revoked. A non-null value makes delivery return `410`. |

There is at most one active row for each
`(installation_id, vapid_key_sha256)`. A revoked row is retained for audit
and continues to return `410`; a later subscription creates a new random
`registration_id` rather than updating or reusing the revoked row.

The relay MUST have indexes for `installation_id`, active
`(installation_id, vapid_key_sha256)`, `(installation_id, epoch)`, and
`revoked_at`. It MUST NOT store an instance plaintext origin in this table as
an authorization substitute.

### 3.3 `push_installation_binds`

The bind idempotency record is durable. It prevents a timeout retry from
allocating another epoch or repeating the old-registration revocation.

| Field | Type and wire shape | Owner and invariant |
| --- | --- | --- |
| `sign_in_id` | Cryptographically random UUID string, primary key | Native account coordinator generates it once per login and reuses it only for retries of that login. |
| `installation_id` | UUID string, foreign key | Relay stores the installation bound by that login. |
| `account_id` | Supabase subject string | Relay stores the login-session subject for audit and cleanup; a retry with a different subject is a conflict. |
| `epoch` | Positive integer | Relay stores the epoch allocated by the first accepted bind. |
| `provider_version` | Non-negative integer | Relay stores the provider version returned by the original bind response. |
| `response_device_token_sha256` | Nullable lowercase hexadecimal SHA-256 | Relay stores the hash returned by the original bind response, including `null` when the installation has no APNs token yet. |
| `response_secret_issued` | Boolean | Relay records whether the original bind response carried a newly created or rotated secret; it never stores that raw secret. |
| `registrations_revoked` | Non-negative integer | Relay stores the count returned by the bind transaction. |
| `response_status` | `201` or `200` | Relay stores the original response status so retries return the same result. |
| `response_environment` | `sandbox` or `production` | Relay stores the environment returned by the original bind response. |
| `response_topic` | Bundle identifier string | Relay stores the topic returned by the original bind response. |
| `response_updated_at` | UTC timestamp | Relay stores the timestamp returned by the original bind response. |
| `created_at` | UTC timestamp | Relay writes it once and retains the record for the installation lifetime, or an equivalent tombstone lifetime that covers every permitted client retry. |

The unique `sign_in_id` record is checked before any epoch mutation. Reusing
one for another installation or account returns `409 sign_in_id_reuse` and
does not change either installation. A first-use response contains
`installation_secret` only in the original `201` response. The durable bind
record never stores the raw secret. If that response is lost before the app
stores the secret, the app abandons that installation ID, generates a new one,
and performs a new first-use bind; the old row is eligible for the cleanup
rule in section 9.8.

### 3.4 Deferred mutation invariant

These invariants apply to the relay, native coordinator, instance
subscription handoff, and every retry path. Any new state-changing route must
be added to the route ledger below before implementation:

- A `registration_id` is allocated exactly once from 32 random bytes. Its
  43-character base64url value is immutable, is never reused, and remains
  retained as a revoked row for the audit lifetime.
- A registration has only two states: `active` when `revoked_at` is null and
  `revoked` when `revoked_at` is set. The only transition is
  `active -> revoked`; `revoked_at` is write-once and a revoked row is never
  resurrected.
- Every `push.subscribe` creates a new P-256 key, auth secret, and
  `registration_id`. Its request carries the current `epoch`. In one relay
  transaction, the relay locks the installation and
  `(installation_id, vapid_key_sha256)` scope, rejects a stale epoch, revokes
  the previous active registration by that concrete ID if one exists, and
  inserts the new row with that epoch.
- Every delayed operation carries the exact scope it is allowed to mutate:
  a concrete `registration_id`, an `epoch <= E`, or an expected complete
  `provider_version`. No operation selects "all current registrations" or
  "the current provider state" at execution time.
- An APNs device-token update changes only the installation row. It never
  changes, recreates, or reactivates a registration.
- `push.status()` and token recovery return and re-post an existing public
  subscription. They never call `push.subscribe`, create a registration, or
  rotate a key.
- After any interleaving of login bind, token PATCH, subscribe, unsubscribe,
  pending-revoke retry, account rebind, and APNs token rotation has settled,
  the current epoch's active set for each VAPID combination is exactly the
  registration created by its latest successful subscribe, while every older
  epoch is revoked.
- Token-invalid state can be created only by an APNs invalid result whose
  captured `provider_version` still equals the installation's current
  `provider_version`.

| State-changing route or operation | Fixed scope at request start | Required deferred-mutation rule |
| --- | --- | --- |
| `PUT` login bind | `sign_in_id`, the newly allocated epoch, and an optional one-time secret replacement | Durable idempotency record; one transaction increments epoch, revokes only registrations with `epoch < new_epoch`, and never repeats a secret replacement on retry. |
| `PATCH` provider update | Expected `provider_version` and the complete replacement object | Compare-and-set the whole provider state; a stale update returns `409` without changing epoch or registrations. |
| `POST` registration | Current `epoch` plus installation/VAPID scope | Reject `epoch != current_epoch` with `409 stale_epoch`; revoke the prior active row by its concrete ID. |
| `DELETE` one registration | Concrete `registration_id` | Set `revoked_at` only on that row; retries are idempotent. |
| `DELETE` all registrations for an installation | Explicit `epoch <= E` | Require `E <= current_epoch`; revoke only rows with `epoch <= E`, never a later epoch. |
| Delivery-side APNs invalidation | Captured `provider_version` | Compare-and-set before marking the provider state invalid; a changed version returns retryable `503` and cannot disable the instance subscription. |

## 4. Native bridge contract

The bridge keeps the v1 shape in `docs/plans/ios-app.md` section 4. The
complete push behavior is defined here.

The shell advertises `capabilities.push >= 1` and implements:

| Direction | Method or event | Exact shape |
| --- | --- | --- |
| Web -> native | `push.status()` | Returns `{state: "unavailable" \| "off" \| "on", endpoint?: string, keys?: {p256dh: string, auth: string}}`. For `state: "on"`, `endpoint` and `keys` are present and describe the existing public subscription; for other states they are absent. |
| Web -> native | `push.subscribe({vapidPublicKey})` | Returns `{endpoint: string, keys: {p256dh: string, auth: string}}`. Both key values are base64url without padding. |
| Web -> native | `push.unsubscribe()` | Returns `{revoked: boolean}` after local key removal and a best-effort relay revoke. `revoked: true` means the relay confirmed the registration is revoked or already revoked; `false` means the local key was removed and a pending revoke was queued because the relay could not be confirmed. |
| Native -> Web | `push.opened({url})` | Delivers a same-origin path such as `/chat/ses_123?from=notification`. |

`vapidPublicKey` is the current instance VAPID public key returned by
`GET /api/web-push/vapid-public-key`. The Web UI obtains it from the
instance, passes it to the bridge, and then POSTs the returned
`{endpoint, keys}` to the instance's existing
`POST /api/web-push/subscriptions`.

Inside the native app, the Web UI does not call `PushManager`, register a
service worker for push, or use browser Web Push APIs. Browser and installed
PWA behavior outside the native app keeps its existing `PushManager` path.

The private P-256 key never crosses the bridge. `push.status()` exposes the
existing public subscription without changing its registration. Each
`push.subscribe` instead creates and returns a fresh public `p256dh`, `auth`,
and endpoint; it never reuses an active or revoked registration. The native
account authority uses the same-origin login route once per successful login.
After that bind, the native push coordinator keeps the installation credential
in native memory only long enough to make installation-management requests and
uses it for subscribe, unsubscribe, provider updates, and offline retries.
The credential never enters runtime Web content, the bridge, instance content,
the NSE key record, or logs. The Web UI never receives an account token or an
installation credential for push registration.

The bridge remains available only to an instance-origin main frame, under the
origin checks in `ios/README.md` and `docs/plans/ios-app.md` section 7.

## 5. Relay HTTP API

All JSON is UTF-8. Management requests use
`Content-Type: application/json`. Error responses use:

```json
{
  "ok": false,
  "error": {
    "code": "machine_readable_code",
    "message": "short operator-safe message"
  }
}
```

`message` MUST NOT include account sessions, installation secrets, APNs tokens,
VAPID private material, Web Push ciphertext, notification plaintext, or a full
endpoint.

### 5.1 Authentication

The login bind is the only account-authenticated push route:

```http
Cookie: avibe_session=<current same-origin session>
Origin: https://avibe.bot
```

The backend validates the cookie through the existing same-origin account
session boundary and derives `account_id` from that session. The `Origin` value
is required even when the cookie is present. A bind for an existing
installation also supplies the installation credential from section 2.3.
First-use creation has no credential to supply.

Every management route after login requires:

```http
Authorization: AvibeInstallation <installation_id>.<installation_secret>
```

The backend hashes the presented secret and compares it with
`push_installations.installation_secret_hash`. It rejects a path/header
installation-ID mismatch, an unknown installation, or an invalid secret
without consulting `account_id`. These routes do not accept a Supabase bearer,
an `avibe_session` cookie, or a client-supplied account ID. This keeps logout
retries authorized after the account session and WebKit store rotate.

The delivery route does not accept a Supabase bearer token. It requires the
VAPID authorization described in section 5.4.

### 5.2 Bind an installation at login

```http
PUT /api/push/apns/installations/<installation_id>
Cookie: avibe_session=<current same-origin session>
Origin: https://avibe.bot
Authorization: AvibeInstallation <installation_id>.<installation_secret>
Content-Type: application/json
```

The `Authorization` header is absent when the path does not yet exist. It is
required when the path names an existing installation. The server never
returns the raw secret from a later status or management response.

Request:

```json
{
  "sign_in_id": "00000000-0000-0000-0000-000000000000",
  "initial_provider": {
    "device_token": null,
    "environment": "sandbox",
    "topic": "bot.avibe.ios"
  },
  "rotate_installation_secret": false
}
```

`sign_in_id` is a fresh UUID generated once for this login and reused for
retries of the same request. `initial_provider` is required only when the
installation row does not exist; it supplies the initial environment and topic
and may supply a `null` device token. An existing installation must omit it,
because provider changes use the versioned `PATCH` route. The client cannot
submit `account_id`, `epoch`, `provider_version`, or a secret hash.

`rotate_installation_secret` is accepted only for an existing installation. If
true, the bind atomically replaces the stored secret hash and returns a new
raw secret once in that successful response. The old secret stops working
after commit. This is an optional login-time credential rotation, not an
account-based authorization fallback.

This route is the only route that consumes the account session. The relay locks
the installation row in a transaction. Before that transaction mutates state,
it checks `push_installation_binds` for the `sign_in_id`. If a matching record
exists, the relay returns its stored response without incrementing the epoch,
rotating the secret again, or revoking anything. If the record conflicts with
the installation or authenticated account, it returns `409 sign_in_id_reuse`.

For a new `sign_in_id`, the relay creates the installation with `epoch = 1`
when no row exists, initializes `provider_version = 0`, hashes a new random
installation secret, and records the cookie's account. Otherwise it increments
the current epoch to `E`, records the cookie's account, and revokes every
registration with `epoch < E` by its concrete `registration_id` before
committing. An existing provider state is untouched by the epoch transition;
the app uses `PATCH` when its APNs token, environment, or topic differs.

Success is `201` for first-use creation and `200` for an update or rebind:

```json
{
  "ok": true,
  "installation_id": "00000000-0000-0000-0000-000000000000",
  "sign_in_id": "00000000-0000-0000-0000-000000000000",
  "epoch": 1,
  "provider_version": 0,
  "device_token_sha256": null,
  "environment": "sandbox",
  "topic": "bot.avibe.ios",
  "registrations_revoked": 0,
  "secret_issued": true,
  "installation_secret": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "updated_at": "2026-11-08T00:00:00Z"
}
```

The `installation_secret` field appears only in the original first-use `201`
response or an explicit secret-rotation response. It is a 32-byte random
value encoded as 43 base64url characters without padding. `secret_issued`
records whether that one-time field was issued by the original operation; a
retry may return `secret_issued: true` while omitting the raw secret. An
existing bind without rotation returns `secret_issued: false`. Every bind
response includes `provider_version` and `device_token_sha256`, including a
`null` hash when no token has been registered.

`registrations_revoked` is the number of rows with an older epoch revoked by
this login bind. A retry with the same `sign_in_id` returns the same status,
epoch, provider version, token hash, count, and timestamps as the first
response. It does not issue another secret. If the app loses the one response
that carried a newly created or rotated secret before storing it, it abandons
that installation credential and starts over with a new installation ID.

The route returns:

| Status | `error.code` | Meaning |
| --- | --- | --- |
| `400` | `invalid_installation_id`, `invalid_sign_in_id`, `invalid_initial_provider`, `invalid_environment`, `invalid_topic`, `invalid_json` | The request shape or value is invalid. |
| `401` | `login_unauthenticated`, `installation_credential_required`, `installation_unauthorized` | The account cookie is invalid, an existing installation lacks its credential, or the credential is invalid. |
| `403` | `origin_forbidden` | The request does not carry the exact avibe.bot Origin required by the account route. |
| `409` | `sign_in_id_reuse` | The `sign_in_id` was already committed for another installation or account. |
| `409` | `initial_provider_not_allowed` | An existing installation tried to change provider fields through the login bind. |
| `413` | `request_too_large` | The JSON request exceeds the management body limit. |
| `429` | `rate_limited` | The installation management limit was exceeded. |
| `502` | `auth_unavailable` | The backend could not validate the account session against its configured auth provider. |

### 5.2.1 Update installation provider state

```http
PATCH /api/push/apns/installations/<installation_id>
Authorization: AvibeInstallation <installation_id>.<installation_secret>
Content-Type: application/json
```

Request:

```json
{
  "expected_provider_version": 0,
  "device_token": "<base64url-no-padding-or-null>",
  "environment": "sandbox",
  "topic": "bot.avibe.ios"
}
```

This installation-credential route is the only path for an already-bound
installation to update its APNs token, environment, or topic. The request is a
complete replacement of the provider state. The expected version is a
compare-and-set precondition for the complete row, not just for the token. If
the version is current and the replacement differs, the relay stores all three
fields, increments `provider_version` by one, clears `device_token_invalid_at`,
and updates `updated_at`. It does not change `epoch` or any registration. If
the replacement is identical, the relay returns the current state without
incrementing the version; it still clears `device_token_invalid_at` because
the caller supplied the current complete version as the CAS proof.

Success is `200`:

```json
{
  "ok": true,
  "installation_id": "00000000-0000-0000-0000-000000000000",
  "epoch": 7,
  "provider_version": 1,
  "device_token_sha256": "fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210",
  "environment": "sandbox",
  "topic": "bot.avibe.ios",
  "updated_at": "2026-11-08T00:00:00Z"
}
```

The route returns `404 installation_not_found` for an unknown installation,
`401 installation_credential_required` or `installation_unauthorized` for a
missing or invalid installation credential, `409 stale_provider_version` when
the expected version does not match, `400` for invalid fields,
`413 request_too_large`, and `429 rate_limited`.

### 5.3 Create a new registration

```http
POST /api/push/apns/registrations
Authorization: AvibeInstallation <installation_id>.<installation_secret>
Content-Type: application/json
```

Request:

```json
{
  "installation_id": "00000000-0000-0000-0000-000000000000",
  "epoch": 7,
  "vapid_key_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
```

The relay verifies the installation credential from the header. The request's
`epoch` must equal the installation's current epoch. Otherwise the relay
returns `409 stale_epoch` without creating or revoking anything.
Every accepted request creates a new registration, even when an active row
already exists for the same installation and VAPID hash. In one transaction it
locks the installation and that scope, sets `revoked_at` on the previous
active registration by its concrete `registration_id` if present, and inserts
the new random row with the supplied epoch. A revoked row is never
resurrected, and the old endpoint returns `410` after the transaction
commits.

Success is always `201`:

```json
{
  "ok": true,
  "registration_id": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "endpoint": "https://avibe.bot/api/push/apns/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "epoch": 7,
  "vapid_key_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "created_at": "2026-11-08T00:00:00Z"
}
```

The sample registration ID is illustrative. Implementations MUST generate a
random 32-byte value and MUST NOT use a sequential or account-derived ID.
There is no `200` reuse response.

The route returns:

| Status | `error.code` | Meaning |
| --- | --- | --- |
| `400` | `invalid_installation_id`, `invalid_vapid_key_hash`, `invalid_json` | The request shape or value is invalid. |
| `401` | `installation_credential_required`, `installation_unauthorized` | The installation credential is absent or invalid. |
| `404` | `installation_not_found` | The installation does not exist. |
| `409` | `stale_epoch` | The supplied epoch is not the installation's current epoch. |
| `413` | `request_too_large` | The JSON request exceeds the management body limit. |
| `429` | `rate_limited` | The installation management limit was exceeded. |

### 5.4 Revoke a single registration

```http
DELETE /api/push/apns/registrations/<registration_id>
Authorization: AvibeInstallation <installation_id>.<installation_secret>
```

For an owned registration, the route sets `revoked_at` if needed and returns
`200`:

```json
{
  "ok": true,
  "registration_id": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "revoked": true,
  "revoked_at": "2026-11-08T00:00:00Z"
}
```

The operation is idempotent for an already-revoked row. Unknown registrations
return `404` with `registration_not_found`; a registration belonging to a
different installation is indistinguishable from an unknown one. The route
returns `401` with `installation_credential_required` or
`installation_unauthorized` for a missing or invalid credential and `429` with
`rate_limited` when the installation management bucket is exhausted.

### 5.5 Revoke all registrations for an installation

```http
DELETE /api/push/apns/installations/<installation_id>/registrations?epoch=7
Authorization: AvibeInstallation <installation_id>.<installation_secret>
```

Success is `200`:

```json
{
  "ok": true,
  "installation_id": "00000000-0000-0000-0000-000000000000",
  "epoch": 7,
  "revoked_count": 2
}
```

This is the logout operation for the caller's captured epoch `E`. `E` is a
required positive integer query parameter and must satisfy `E <= current
epoch`; a future value returns `409 future_epoch` without mutation. The
transaction selects only rows with `registration.epoch <= E`, records their
concrete IDs, and sets `revoked_at` on those rows. It is idempotent and cannot
match a registration created in a later epoch. The route returns `404` with
`installation_not_found` for an unknown installation, `400` for an invalid
epoch, `401` with `installation_credential_required` or
`installation_unauthorized` for a missing or invalid credential, `409` with
`future_epoch` for `E > current_epoch`, and `429` with `rate_limited` when the
installation management bucket is exhausted. Because the route is authorized
by the installation credential, a queued logout retry remains valid after
account logout and account-session rotation.

### 5.6 Deliver encrypted Web Push to APNs

```http
POST /api/push/apns/<registration_id>
Authorization: vapid t=<compact-jwt>, k=<base64url-p256-public-key>
Content-Type: application/octet-stream
Content-Encoding: aes128gcm
TTL: 43200
Urgency: normal
Topic: session:ses_123
```

The `Authorization` value follows RFC 8292. The relay verifies:

1. the VAPID JWT is a three-part compact JWT with an ES256 signature;
2. the signature verifies with the public key in `k`;
3. the SHA-256 hash of decoded `k` equals the registration's
   `vapid_key_sha256`;
4. `aud` is exactly `https://avibe.bot`;
5. `exp` is in the future and no more than 24 hours after the relay's current
   time;
6. the request uses `Content-Encoding: aes128gcm`;
7. the body is no larger than 2903 bytes;
8. `TTL` is a non-negative decimal integer no larger than 86400, defaulting to
   43200 when absent;
9. `Urgency`, if supplied, is one of `very-low`, `low`, `normal`, or `high`;
10. `Topic`, if supplied, is valid UTF-8, contains no control characters, and
    is no more than 64 UTF-8 bytes.

The VAPID JWT signature covers the JWT header and claims, including `aud`,
`exp`, and `sub`. It does not cover the request path. The registration ID
selects state, and the VAPID public-key hash binds the request to the
instance key registered for that state. The encrypted body is authenticated
by RFC 8291 AES-GCM; the relay never attempts to decrypt it.

Before opening the APNs request, the relay captures the installation's
complete provider state and `provider_version` under the installation lock. If
the current `device_token` is null or `device_token_invalid_at` is non-null,
it returns `503 apns_token_unavailable` and does not send to APNs. If APNs
returns `410`, `BadDeviceToken`, `DeviceTokenNotForTopic`, or `Unregistered`,
the relay marks the current provider state invalid only with:

```text
UPDATE push_installations
SET device_token_invalid_at = now()
WHERE installation_id = <captured installation_id>
  AND provider_version = <captured provider_version>
```

The relay returns `410 apns_device_gone` only when that compare-and-set
matches. If any provider field changed while APNs was processing the request,
the provider version no longer matches; the relay leaves the installation
untouched and returns retryable `503 apns_provider_changed`. The instance must not
disable its subscription for that result.

Success is `201` after APNs accepts the request:

```json
{
  "ok": true,
  "registration_id": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "apns_status": 200
}
```

Delivery errors are fixed:

| Relay status | `error.code` | Condition and state effect |
| --- | --- | --- |
| `400` | `invalid_vapid`, `vapid_key_mismatch`, `invalid_audience`, `vapid_expired`, `vapid_exp_too_far`, `invalid_content_encoding`, `invalid_ttl`, `invalid_urgency`, `invalid_topic`, `invalid_request` | The request is rejected. The registration remains active. |
| `410` | `registration_not_found`, `registration_revoked` | The registration does not exist or has `revoked_at`. The instance must disable its subscription. |
| `410` | `apns_device_gone` | APNs returned `410`, `BadDeviceToken`, `DeviceTokenNotForTopic`, or `Unregistered`, and the captured `provider_version` still matched the installation. The relay marks the current provider state invalid and the instance disables its subscription. |
| `413` | `encrypted_body_too_large`, `apns_payload_too_large` | The encrypted body or resulting APNs JSON exceeds its bound. The registration remains active. |
| `429` | `relay_rate_limited` | The registration or installation token bucket is exhausted. The response includes `Retry-After` seconds. The registration remains active. |
| `502` | `apns_bad_gateway` | APNs rejected the request because of a relay/provider configuration or protocol error that is not a device invalidation. The registration remains active. |
| `503` | `apns_unavailable`, `apns_timeout`, `apns_upstream_rate_limited`, `apns_provider_changed`, `apns_token_unavailable` | APNs is unavailable, timed out, or returned a transient `429`/`5xx`; the provider version changed during an invalidation race; or the current token is already marked invalid. The response may include `Retry-After`. The registration remains active and the instance must not disable it for these codes. |

All other APNs response bodies are redacted into an operator-safe error
classification. The relay MUST NOT pass APNs response text, the request body,
or a device token to the instance or logs.

### 5.7 APNs request mapping

The relay selects the APNs host from `push_installations.environment`:

| Environment | APNs host |
| --- | --- |
| `sandbox` | `https://api.sandbox.push.apple.com` |
| `production` | `https://api.push.apple.com` |

The provider token is generated from the configured `.p8` key using ES256,
with the configured Key ID and Team ID. It is cached and refreshed every
20-60 minutes, with immediate refresh after an APNs provider-auth failure.
The APNs HTTP client uses HTTP/2.

For every accepted delivery, the relay sends:

| APNs field | Value |
| --- | --- |
| `:path` | `/3/device/<device_token>` from the protected installation record |
| `apns-push-type` | `alert` |
| `apns-topic` | `push_installations.topic` |
| `apns-priority` | `10` for Web Push `Urgency: high` or `normal`; `5` for `low` or `very-low`; `10` when absent |
| `apns-expiration` | Literal `0` when validated `TTL` is `0`; otherwise the current Unix time plus validated `TTL` |
| `apns-collapse-id` | When `Topic` is supplied, `base64url_no_pad(SHA-256(registration_id_bytes || 0x00 || UTF-8(Topic)))`; omit when absent. The decoded 32-byte registration ID is used, and the result is 43 ASCII bytes. |

The APNs JSON body is compact UTF-8 JSON with this exact shape:

```json
{
  "aps": {
    "alert": {
      "loc-key": "AVIBE_PUSH_FALLBACK"
    },
    "mutable-content": 1,
    "sound": "default"
  },
  "avibe": {
    "v": 1,
    "kid": "<registration_id>",
    "ct": "<base64url-no-padding-of-the-original-aes128gcm-body>"
  }
}
```

`AVIBE_PUSH_FALLBACK` is a localization key compiled into the app and the
Notification Service Extension. The outer `aps.alert.loc-key` is safe to show
when the extension cannot decrypt. The relay does not add title, body, URL,
badge, or instance-origin data to the outer payload.

### 5.8 Rate limits

The relay uses token buckets with a one-minute refill period and a separate
burst capacity. Limits are checked before any APNs request:

| Scope | Rate | Burst | Applies to |
| --- | --- | --- | --- |
| Installation management | 30 requests/minute | 10 | Login binds, provider PATCHes, registration creates, and revocations for one installation credential |
| One registration delivery | 60 requests/minute | 10 | Delivery requests for one `registration_id` |
| One installation delivery | 120 requests/minute | 20 | Delivery requests across all registrations for one installation |
| One account delivery | 300 requests/minute | 50 | Delivery requests across the account's installations |

The registration and installation buckets are independent. A request that
exhausts either returns `429` with `Retry-After`; it does not reach APNs.
Successful, invalid, and oversized delivery requests consume the delivery
bucket after the registration has been resolved. Requests for an unknown or
revoked registration return `410` before rate accounting.

These limits are minimum contract values. An environment may use stricter
limits during abuse response, but it must preserve the status and
`Retry-After` behavior.

## 6. Instance payload and size budget

The current instance payload remains the source payload. The canonical
logical fields are:

```json
{
  "title": "Project name",
  "body": "A notification preview",
  "url": "/chat/ses_123?msg=msg_456&from=notification",
  "tag": "session:ses_123",
  "message_id": "msg_456",
  "session_id": "ses_123",
  "badge_count": 3,
  "category": "sessions"
}
```

`category` is optional for compatibility with existing payloads. The sender
may carry additional forward-compatible fields, but the byte invariant
applies to the complete serialized object.

For a relay delivery, the instance sends the Web Push `Topic` header from the
same value as `tag` when `tag` is present. The relay maps that header to a
registration-scoped `apns-collapse-id` by hashing the decoded 32-byte
`registration_id`, a single zero separator byte, and the UTF-8 Topic bytes,
then encoding the SHA-256 digest as base64url without padding. Therefore the
same registration and Topic can collapse, while equal Topics from different
registrations cannot replace one another. A browser subscription may continue
to use the existing service-worker tag behavior; the relay mapping is the
authoritative path for iOS.

The instance MUST:

- use `json.dumps(payload, ensure_ascii=False, separators=(",", ":"))`;
- encode that JSON as UTF-8 before encryption;
- limit `title` to 80 Unicode scalar values;
- limit `body` to 240 Unicode scalar values, preserving the current body
  behavior;
- limit `tag` to 64 UTF-8 bytes with no control characters when it is sent as
  the relay `Topic` header;
- truncate only at a valid Unicode scalar boundary, with a grapheme-safe
  truncation preferred for user-visible text;
- reject or truncate the complete serialized plaintext if it exceeds 2800
  UTF-8 bytes;
- apply this same limit to browser Web Push and iOS relay subscriptions.

The `badge_count` is the existing per-owner unread count. The instance
computes it immediately before each subscription send; it is not supplied by
the relay and is not shared across accounts.

### 6.1 Budget calculation

The adopted invariant is a maximum serialized plaintext of 2800 bytes. For a
single `aes128gcm` record:

| Component | Bytes |
| --- | ---: |
| RFC 8188/8291 encrypted-content header | 86 |
| Padding delimiter | 1 |
| AES-GCM authentication tag | 16 |
| Maximum serialized plaintext | 2800 |
| Maximum encrypted Web Push body | 2903 |
| Base64url without padding of the encrypted body | 3871 |
| Fixed APNs JSON envelope with a 19-byte fallback key and a 43-byte `kid` | 165 |
| Maximum APNs JSON payload | 4036 |
| Margin below the 4096-byte APNs limit | 60 |

The theoretical maximum under this exact outer shape would be 2844 bytes of
plaintext and 4095 bytes of APNs JSON. The contract uses 2800 bytes to keep a
60-byte margin for implementation-level serialization checks. A relay MUST
reject an encrypted body over 2903 bytes and an APNs payload over 4096 bytes.
The browser path also remains below the 4096-byte encrypted-payload limit
because its encrypted body is at most 2903 bytes.

The relay's base64url encoding is without padding, and the outer APNs JSON
uses compact separators. Adding whitespace or a second outer field is not
permitted without recalculating and ratifying the budget.

### 6.2 Instance settings label

The instance settings device list labels any subscription whose endpoint
starts with:

```text
https://avibe.bot/api/push/apns/
```

as `iPhone App`. The label is derived from the endpoint prefix, not from a
user-agent string or a client-supplied display label. Other HTTPS endpoints
keep the existing browser/PWA label behavior.

## 7. Native key and Notification Service Extension contract

### 7.1 Key records

For each new `push.subscribe` call for an `(account_id, instance_origin)` pair,
the app creates:

- one P-256 ECDH key pair;
- one cryptographically random 16-byte Web Push authentication secret;
- one key record in the app-group Keychain.

The main app target and the NSE target MUST both enable the App Group
`group.bot.avibe.ios` and the Keychain Sharing access group
`$(AppIdentifierPrefix)bot.avibe.ios.push`. The App Group provides the shared
container; it does not replace the `keychain-access-groups` entitlement.
Both provisioning profiles MUST include the same Keychain access group.

Every private key and auth secret item MUST use
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`. This allows the NSE to
read the material while the device is locked after the first unlock without
making it eligible for keychain migration to another device. Before the first
unlock after boot, the keychain may be unavailable and the NSE MUST use the
same localized fallback path defined in section 7.2.

The key record contains:

```text
kid: registration_id
instance_origin: configured HTTPS origin
account_id: current phone account
epoch: installation epoch used to create the registration
private_key: native-only P-256 private key
auth_secret: native-only 16-byte secret
state: pending | active | retiring
retire_after: Nullable UTC timestamp; set only after a retiring registration
is confirmed revoked
```

The public key returned as `keys.p256dh` is the uncompressed 65-byte P-256
point encoded as base64url without padding. The `keys.auth` value is the
16-byte authentication secret encoded the same way. The private key and
installation secret never enter Web content.

At most one key record per `(account_id, instance_origin)` is `active` and
visible to the bridge, and at most one older record may be `retiring` while
its already-accepted APNs notifications can still arrive.
`push.status()` reads the current active record and returns its existing
endpoint and public keys without creating a registration.

If the instance VAPID public key changes, the native coordinator performs a
serialized replacement:

1. create the new P-256 key, auth secret, new relay registration, and native
   `pending` candidate;
2. post the new subscription to the instance and wait for the instance to
   store it;
3. make the new record the active bridge record;
4. delete the old instance subscription and explicitly revoke the old relay
   registration by its recorded `registration_id`;
5. mark the old key record `retiring` with
   `retire_after = revoked_at + 86400 seconds` from the relay's successful
   revoke response, then delete it after that time.

The old path remains usable until step 2 succeeds, so a failed replacement
does not leave the instance without a subscription. The old key remains
available through the maximum accepted Web Push TTL window for notifications
that APNs accepted before the old registration was closed. If the old revoke
is offline, the retiring key remains available with a null `retire_after`
while a pending revoke carrying that exact old `registration_id` is retried;
the instance's old subscription deletion stops ordinary sends. A second VAPID
replacement for the same instance waits until the prior retiring record has
been deleted, so there is never more than one retiring record. A failed new
registration is revoked by its own ID and its candidate key is deleted,
leaving the old record active.

### 7.2 NSE processing

The Notification Service Extension:

1. reads `avibe.kid` from the APNs user info;
2. finds the Keychain record by `kid`;
3. base64url-decodes `avibe.ct`;
4. runs the RFC 8291 `aes128gcm` decryption using the stored P-256 private key
   and auth secret;
5. parses the resulting UTF-8 JSON;
6. sets the notification title from `title`;
7. sets the notification body from `body`;
8. sets the application badge from `badge_count`;
9. sets `threadIdentifier` from `tag`;
10. stores `url`, `instance_origin`, and `kid` in `userInfo`.

If lookup, base64url decoding, decryption, UTF-8 decoding, or JSON parsing
fails, the NSE keeps the localized `AVIBE_PUSH_FALLBACK` alert. It MUST NOT
show ciphertext, an exception, a token, or a private key in the notification.
This fallback also applies before the device's first unlock after boot when
the `AfterFirstUnlockThisDeviceOnly` keychain item is unavailable.

The implementation does not request Apple's filtering entitlement. Muted
categories and hidden Sessions are already filtered by the instance before
encryption.

## 8. Tap routing

When a notification is tapped, the native coordinator validates the stored
`account_id` and `instance_origin` against the current account and the
account-scoped instance list.

If the account is current and the instance is available:

1. select that instance;
2. load its instance origin;
3. wait for the primary WebView to finish loading;
4. normalize the stored URL as a same-origin path;
5. dispatch `push.opened({url})` through the bridge.

The Web UI accepts only a URL whose origin equals the currently selected
instance origin. It may navigate to the path, query, and fragment; it MUST
reject absolute URLs, another origin, a different scheme, and control
characters.

If the account does not match, or the instance is missing or unavailable,
  the app opens the instance list and gives the user the existing recovery
  message. It does not send the URL to another instance or to Safari.

The tables below freeze the ownership of every cross-boundary value. The
word "sign" means cryptographic coverage or an authenticated binding, not
that every field has an independent signature.

### 9.2 Enable

1. On every successful account login, the native account coordinator creates a
   `sign_in_id` and calls the same-origin installation bind route with the
   current `avibe_session` cookie and `Origin`. First use also supplies
   `initial_provider`; an existing installation supplies its installation
   credential. The relay returns the new current `epoch`, the complete
   provider version, and the current `device_token_sha256`. Native stores the
   one-time installation secret from a first-use or explicit rotation response
   in the non-App-Group Keychain.
2. The user enables notifications in the instance Web UI.
3. The Web UI calls `push.subscribe({vapidPublicKey})` through the bridge.
4. Native requests notification permission if needed and receives the APNs
   device token. If the complete provider state differs, native calls `PATCH`
   with the last accepted `provider_version` and all replacement fields.
5. Native creates a fresh P-256 key and auth secret, computes
   `vapid_key_sha256`, and calls the relay registration route with the current
   `epoch`.
6. The relay rejects a delayed prior-session request with `409 stale_epoch`;
   otherwise it atomically revokes the previous active registration for that
   installation/VAPID hash by its concrete ID, creates a new registration, and
   returns its endpoint and epoch.
7. Native stores `kid`, instance origin, account ID, epoch, private key, and
   auth secret in the shared App Group and Keychain Sharing access group. The
   installation secret remains in its separate ThisDeviceOnly Keychain item.
8. The bridge returns `{endpoint, keys:{p256dh,auth}}`.
9. The Web UI POSTs that object to the instance's existing
   `/api/web-push/subscriptions` route.
10. The instance stores the subscription and enables the existing delivery
    path.

The registration is usable only when both the relay row and the instance
subscription row exist. A failure after relay registration but before the
instance POST is recoverable by calling `push.subscribe` again; that call
creates another registration and revokes the first one. It never reuses the
first ID. If a pending revoke exists from an earlier unsubscribe, it remains
queued for that explicit old ID and cannot affect the new registration.

### 9.3 Delivery

1. The instance's existing notification path selects an eligible owner and
   computes that owner's `badge_count`.
2. The instance serializes the complete payload under section 6's byte
   invariant.
3. `pywebpush` creates fresh RFC 8291 encryption material, encrypts the
   plaintext, and creates the RFC 8292 VAPID request.
4. The instance POSTs the raw encrypted body to the registration endpoint.
5. The relay resolves the registration. Missing or revoked state returns
   `410`.
6. The relay validates VAPID, content encoding, body size, TTL, urgency, and
   topic. It does not read the body.
7. The relay captures the installation's complete provider state, rejects an
   already-marked invalid token with retryable `503`, and creates the APNs
   request and outer JSON envelope while preserving the original encrypted
   bytes as `avibe.ct`.
8. APNs accepts or rejects the request. On an invalid-token result, the relay
   performs the provider-version compare-and-set from section 5.6 before mapping
   the result.
9. On success, APNs invokes the NSE. The NSE finds the registration `kid`,
   decrypts the original body, and presents the alert.
10. On `410 apns_device_gone`, the instance disables the subscription using the same
    path that currently disables a browser subscription after a 404/410.
    On `503 apns_provider_changed` or `503 apns_token_unavailable`, it keeps the
    subscription enabled and retries after native token recovery.

### 9.4 Tap

The NSE writes the decrypted path and native instance origin into
`userInfo`. The app account coordinator performs the checks in section 8,
loads the instance, and dispatches `push.opened({url})` only after the
instance-origin primary frame is ready.

### 9.5 Disable notifications

1. The Web UI calls `push.unsubscribe()`.
2. Native deletes the `(account_id, instance_origin)` key record and calls
   `DELETE /api/push/apns/registrations/<registration_id>`.
3. The Web UI calls `DELETE /api/web-push/subscriptions` on the instance using
   the endpoint it had posted.
4. The instance disables that subscription row.

If the relay revoke is offline, native captures the current record's exact
`registration_id`, removes the local key immediately, stores that ID in a
bounded pending-revoke set, and still attempts to delete the instance
subscription. The pending operation is retried whenever the installation
credential is available and the network is reachable; it does not require an
account session. This does not guarantee
that no visible alert will appear: a notification already accepted by APNs,
or accepted before the relay observes the pending revoke, may still be
delivered. Because the NSE fallback behavior is part of this contract, a
delivery whose key is already gone shows only the localized
`AVIBE_PUSH_FALLBACK` alert; it cannot reveal the old encrypted title, body,
URL, or instance origin, but the outer `sound: "default"` may still make the
alert audible. The successful instance deletion stops future ordinary sends
from that subscription. The pending revoke MUST be retried until the relay
confirms it; after confirmation, new delivery
requests for that revoked ID return `410`. A later `push.subscribe` always
creates a different ID; retrying this pending revoke cannot select or revoke
the later registration.

### 9.6 Logout and account switch

Logout and account switching enter the existing single native account
authority and WebKit store-rotation lifecycle:

1. native captures the current installation `epoch = E` and retains the
   installation credential in its ThisDeviceOnly Keychain;
2. native attempts
   `DELETE /api/push/apns/installations/<installation_id>/registrations?epoch=E`;
   the relay revokes only registrations whose stored epoch is `<= E`;
3. native deletes all key records for the old account;
4. the native coordinator revokes the old account snapshot and rotates the
   named WebKit store as already specified by the iOS plan;
5. if the request failed offline, native still completes local deletion and
   store rotation and queues only `(installation_id, E)` as a retry marker.
   The retry uses the installation credential and therefore does not depend on
   the old account session or on the next account's session;
6. the next login creates a new `sign_in_id` and uses the same installation
   credential with the new account cookie. Its bind transaction increments the
   installation epoch and revokes every older-epoch registration before
   returning the new epoch. This is the second convergence path;
7. after the revoke succeeds or the new bind succeeds, the old
   `(installation_id, E)` marker is discarded. No previous registration ID,
   key record, or account session credential is used by the new account. The installation
   credential remains available for later device-level lifecycle operations.

Queued notifications may still show the localized fallback until the relay
observes the revoke or the next login bind, but the deleted key prevents old
encrypted content from being displayed. The outer `sound: "default"` can
still make such an already-accepted alert audible.

### 9.7 APNs token rotation

When APNs supplies a new device token, native calls the installation
`PATCH` with the last accepted `provider_version` and the complete replacement
provider state. The relay updates `device_token`, its hash, environment, topic,
and `updated_at` as one replacement; it increments `provider_version`, clears
`device_token_invalid_at`, leaves the current epoch unchanged, and keeps all
active registrations and endpoint IDs valid. A stale callback fails the
whole-state compare-and-set and is discarded without changing relay state. The
next delivery uses the new provider state.

If a delivery using the old token already returned relay `410`, the instance
may already have disabled that subscription row through its existing failure
path. After the installation `PATCH` succeeds, the next instance session MUST
call `push.status()` for each active native record and
POST the unchanged `{endpoint, keys}` object returned by the status call to
the instance. The instance upsert re-enables that row. Native does not call
`push.subscribe`, create a new registration, or rotate a key for an APNs token
rotation. If the recovery POST cannot complete, the native/Web coordinator
retries the status-and-POST operation on the next authenticated instance
session.

### 9.8 Reinstall and App uninstall

On the first launch after reinstall, native detects that its local
installation-initialized marker is absent. Before opening an instance, it
deletes residual NSE key records from the App Group. It does not delete the
native `installation_id` or installation secret before attempting cleanup,
because iOS may have retained those ThisDeviceOnly Keychain items.

After the user next completes account login, native uses the retained
installation credential and a fresh `sign_in_id` on the same-origin bind
route. The bind advances the epoch and revokes all older-epoch registrations
in one transaction; native may also request login-time secret rotation. Only
after that bind succeeds does native set the local initialized marker. If the
retained credential is absent or invalid, native generates a new installation
ID and completes a first-use bind. The old installation is never re-bound or
reused by the new installation.

The relay cleanup job may delete an installation row only after every
registration is revoked, the bind-idempotency retention period has elapsed,
and the audit retention period permits deletion. It never deletes an active
registration or recycles an installation ID. If the old Keychain credential
was lost before cleanup, APNs invalidation remains the eventual cleanup path
for any surviving registration.

Uninstall cannot reliably call the revoke API. The relay keeps the state
until APNs reports `410`, `BadDeviceToken`, `DeviceTokenNotForTopic`, or
`Unregistered`. It maps that result to relay `410`, and the instance disables
the subscription. The retained row can then be cleaned by the backend's
ordinary retention job without reviving it.

## 10. Replay and security invariants

This feature is a new ciphertext forwarding channel through
`avibe.bot`. Under `../avibe-backend/AGENTS.md`, a new content-processing
exception requires product and security review before launch. The relay
cannot decrypt the content, but it still accepts and forwards user-originated
encrypted bytes and therefore needs the same review gate.

### 10.1 Threat model

| Threat | Invariant and control |
| --- | --- |
| Open relay abuse | Every delivery resolves a random stateful registration, validates RFC 8292 VAPID against the bound key hash, enforces the 2903-byte body limit, and consumes registration, installation, and account rate buckets before APNs. No delivery route accepts an arbitrary APNs token or arbitrary topic. |
| Installation credential leakage | The installation credential is a device-level bearer by design: leakage can manage only that installation's push registrations and cannot read the account or another installation. The raw secret is stored only in a `ThisDeviceOnly` Keychain item, the relay stores only its hash, management routes are rate limited, and login-time rotation can invalidate it. |
| Cross-account registration or revocation | Only the login bind uses the same-origin account cookie and Origin guard. Every other management route requires the installation credential and is scoped by the installation ID in the header and path; `account_id` is never accepted as authorization input. A new login advances the epoch and revokes all older-epoch registrations before committing the account record. |
| Cross-instance delivery | The relay binds each registration to `vapid_key_sha256`; the delivery VAPID `k` must hash to it. The endpoint ID is random and never derived from account or origin. |
| Deferred mutation race | Every state-changing route fixes its scope at request start: `sign_in_id`, explicit registration ID, `epoch <= E`, or an expected complete `provider_version`. No delayed operation selects an open-ended current set or compares only one provider field at execution time. |
| APNs provider-state invalidation race | Delivery captures the complete provider state version, and an APNs invalid result can mark the installation invalid only when `provider_version` still matches. A changed version returns retryable `503` and cannot disable a valid instance subscription. |
| Native credential confusion | The account session is used only for the same-origin login bind. The installation credential is kept in native Keychain storage, never enters Web content, the bridge, instance pages, relay storage, or logs, and is not available to the NSE. |
| Exact request replay | The relay keeps an expiring deduplication record keyed by `(registration_id, SHA-256(ciphertext))`, never the ciphertext itself. An already accepted exact body returns the prior result during the VAPID validity window without sending a second APNs request. Fresh `pywebpush` sends use fresh RFC 8291 salt and ephemeral sender keys, so a legitimate resend has a different ciphertext hash. |
| VAPID token reuse | `aud` is exact, `exp` is future and at most 24 hours ahead, and the delivery deduplication cache limits an identical body to one APNs submission per registration. |
| APNs token leakage | The device token is encrypted at rest, excluded from logs and user-visible responses, and represented in diagnostics only by SHA-256. APNs requests are made over HTTP/2 TLS. |
| Registration endpoint leakage | Registration IDs are 32 random bytes, are treated as bearer-like capability material, and are redacted from logs and traces. The endpoint is returned only to the authenticated app and then to the authenticated instance subscription path. |
| Web Push auth-secret leakage | The `auth` secret and native private key stay in the app-group Keychain/native process and the instance subscription store. They never enter the relay or bridge response beyond the required `keys.auth` value to the instance. |
| Log or telemetry disclosure | The relay redacts `Authorization`, `installation_secret`, `device_token`, request body, `avibe.ct`, plaintext, and full endpoints. Metrics use status, environment, topic, and hashed identifiers only. |
| Malformed or oversized input | Content type, content encoding, VAPID fields, TTL, urgency, topic, body length, outer APNs length, and JSON shape are validated before forwarding. |
| Wrong APNs environment or topic | Environment and topic are bound in the installation management transaction and selected by the relay. Delivery cannot override either field. |
| Notification tap injection | Native checks account and instance availability; Web UI accepts only a same-origin path. Absolute URLs and cross-origin URLs are rejected. |
| Category or hidden-session bypass | The relay does not make notification policy decisions. The existing instance path remains authoritative and encrypts only after its read, authorization, Project, hidden-session, and mute gates. |

The deduplication cache may be in memory or a bounded short-lived store. It
must expire entries no later than the VAPID `exp` bound and must contain only
the hash and delivery result metadata, never the ciphertext or plaintext.

### 11.2 Non-ASCII end-to-end scenario

One closed-loop scenario must use this payload before encryption:

```json
{
  "title": "任务完成",
  "body": "已完成：你好，世界 🌏",
  "url": "/chat/ses_123?msg=msg_456&from=notification",
  "tag": "session:ses_123",
  "message_id": "msg_456",
  "session_id": "ses_123",
  "badge_count": 3,
  "category": "sessions"
}
```

The scenario must use real serialized bytes and cross all three boundaries:

1. The instance serializes with `ensure_ascii=False`, encrypts with a real
   RFC 8291 implementation, and sends the raw body to a relay HTTP test
   server.
2. The relay validates the real VAPID request, forwards the exact ciphertext
   to a mock APNs HTTP/2 boundary, and produces the exact outer APNs JSON.
3. The NSE receives that APNs JSON, performs real RFC 8291 decryption with
   the native test key record, and produces the title, body, badge, thread ID,
   URL, and instance origin.

The assertion is a property of the full path: the final NSE values equal the
original Chinese and emoji values byte-for-byte after JSON decoding, the
relay never needed plaintext, and the Web UI receives only the validated
same-origin path after a simulated tap. A test that mocks the relay body
with already-decrypted JSON, or a test that tests only two isolated halves,
does not satisfy this contract.

The same non-ASCII payload must also pass the browser Web Push payload budget
check, so Unicode escaping cannot silently consume the budget or change the
displayed text.

## 13. Lane order and mock boundary

### 13.1 Required order

1. **Contract lane, this PR, `avibe`:** merge the contract to `master`.
2. **Backend relay lane, `avibe-backend`:** implement the same-origin login
   bind, installation-secret verifier, epoch and bind ledger, provider-version
   PATCH and registration/revocation routes, state model, delivery validation
   and provider-version CAS, APNs mapping, rate limits, redaction, and relay
   tests from this document.
3. **Avibe lane, `avibe`:** implement the instance byte budget and label,
   native installation credential storage and login-bind handoff, epoch-aware
   installation/key lifecycle, `push` bridge, NSE, tap routing, and instance
   subscription handoff.
4. **Integration:** run the real non-ASCII path against a mock APNs boundary
   and the shared RFC fixture before any real APNs key or Apple device work.

The backend and Avibe implementation lanes may run in parallel only after
this contract is present on `master`.

### 13.2 Mock boundary

The backend lane owns a mock APNs server that records:

- selected sandbox or production host;
- HTTP/2 request headers;
- APNs provider token metadata without private key material;
- exact outer JSON byte length;
- the base64url `ct` value.

It must not decrypt the Web Push body to make the relay test pass.

The Avibe lane owns a mock relay boundary for native and instance tests. It
must validate the same registration and delivery shapes and return the same
status mappings. The mock relay may use a deterministic in-memory state store,
but it must enforce same-origin login bind, installation-secret authorization,
epoch/provider-version CAS, VAPID hash binding, body size, and revocation.

The closed-loop acceptance test connects:

```text
real instance serializer/encryptor
  -> mock relay HTTP boundary
  -> mock APNs HTTP/2 boundary
  -> real NSE decryptor
  -> real tap-origin validation
```

No lane may replace a boundary with a direct function call in the final
scenario test.

## 14. Acceptance gates

The implementation is ready for orchestrator integration only when every
property below holds:

- the contract has landed on `master` before either implementation lane
  branches;
- the login bind alone uses the same-origin account session and Origin guard;
  every later management route uses the installation credential, and a
  logout retry remains authorized after account-session rotation;
- the bind route creates the first installation and returns a 32-byte secret
  only once, stores a durable `sign_in_id`, increments the epoch exactly once
  per login, revokes all older-epoch registrations, and returns `201`; a retry
  returns the durable result without issuing another secret;
- provider PATCH replaces `device_token`, `environment`, and `topic` as one
  whole state using the expected `provider_version`, increments that version
  only when the replacement changes, preserves the epoch and registrations,
  and clears token-invalid state only for the accepted replacement;
- every subscribe creates a new 43-character registration ID and never
  resurrects or reuses an old row; a stale epoch returns `409` without
  mutation;
- the deferred-mutation invariant suite proves that arbitrary delay, retry,
  duplication, and reordering cannot revoke a registration in a later epoch
  or change a newer provider state;
- installation bulk revoke requires `epoch <= current_epoch` and cannot
  affect a later epoch;
- a device-token, environment, or topic rotation preserves active
  registrations and advances the provider version exactly once;
- token recovery re-posts each active subscription so an instance row
  disabled by an APNs `410` is enabled again;
- a cross-account login bind revokes all older-epoch registrations atomically;
- a reinstall clears residual NSE keys, rebinds a retained installation
  credential before marking initialization complete, and never reuses an old
  installation ID after the credential is unavailable;
- an APNs invalid-token result returns `410` only when its captured provider
  version still matches; a changed version returns retryable `503` and
  preserves the instance subscription;
- every revoked or unknown delivery registration returns `410`;
- the relay verifies ES256 VAPID, exact audience, expiry bound, and VAPID key
  hash before forwarding;
- relay and installation rate limits are independently enforced;
- the relay forwards only the original encrypted body and never logs body
  bytes, plaintext, or a full APNs token;
- the APNs mapping and response table are exact;
- `TTL: 0` maps to APNs `apns-expiration: 0`, and a supplied Topic produces a
  registration-scoped 43-byte collapse identifier;
- both app targets share the App Group and Keychain Sharing access group,
  every push key uses `AfterFirstUnlockThisDeviceOnly`, and the pre-first-
  unlock path shows the defined fallback;
- VAPID rotation has no gap in the active instance subscription, revokes the
  old registration, and retains the old key until `revoked_at + 86400`
  seconds;
- the instance payload serializer enforces 2800 UTF-8 bytes with
  `ensure_ascii=False`;
- the outer APNs JSON remains at most 4036 bytes for the contracted maximum,
  leaving 60 bytes below 4096;
- the RFC 8291 Appendix A vector passes in the instance, relay, and NSE test
  suites;
- the non-ASCII scenario crosses instance, relay, mock APNs, NSE, and tap
  origin boundaries with real encryption and decryption;
- disable, logout, account switch, provider rotation, reinstall, and uninstall
  converge to one of the lifecycle states defined here;
- product and security review has explicitly approved this new ciphertext
  forwarding channel before implementation merge or launch.
