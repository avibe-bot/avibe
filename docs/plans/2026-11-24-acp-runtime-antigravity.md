# A shared ACP runtime, with Antigravity as its first backend

Status: design reviewed with codex-astra, 2026-11-24; five contract clarifications incorporated; no implementation authorized by this document. Scope and parity checklist: [#4244](https://github.com/avibe-bot/avibe/issues/4244), rows A–G. This plan replaces the issue's proposed ownership of transport, sessions and events, not its product scope.

## Outcome and non-goals

A user selects **Antigravity**, uses Google's unmodified `agy acp` and works from the same Web, IM and Harness surfaces as the other native CLI backends. A second built-in ACP backend must not need a second transport, session lifecycle or turn translator. ACP is an implementation protocol, not a backend users select. No public plugin SDK, arbitrary-command registration, migration of other backends, Antigravity Bots, alternate Google client identity, or Antigravity as a model source for Vibey. API-key login is in product scope; it is not required for development or for the manual CLI evidence below.

## Ownership and internal contracts

| Owner | Produces → consumes | Invariant |
|---|---|---|
| Existing core and catalog | Selected backend `antigravity`, `AgentRequest`, resolved model/effort and caller context → backend; normalized output → existing delivery, history, queues and retry | Core owns product policy, turn identity and route selection; no ACP method or vendor tool names in Web/IM/Harness business logic. Only `antigravity`, not `acp`, gets a catalog/config entry. |
| `modules/agents/acp/` | A `BaseAgent`-compatible runtime composed with a provider; asynchronous bidirectional stdio RPC, initialization, capability checks, native session binding, prompts, cancel, standard updates and terminal outcomes | No Google imports, environment names, model IDs or login-method names. One reader dispatches responses, notifications and server requests, including while a prompt is pending. Do not block the controller loop. |
| `modules/agents/antigravity/` | Launch and session settings; native config mapping and optional vendor-specific event interpretation → shared runtime | Own CLI quirks, not process supervision or a second turn state machine. Reuse current auth, lifecycle, model and UI services via their existing seams. |

Internal boundary names below describe the data contract, not a new framework:

1. **Launch:** provider supplies `argv`, `cwd`, session-stable `env` from existing managed-path/caller helpers, and a runtime identity for reuse. Runtime alone starts and reaps its child. One child per **active** Avibe Session; release only when existing ownership checks allow it (no bound Turn, Activity, delivery or durable owner). An idle chat is not sufficient evidence. Retain the backend-scoped `native_session_id` through existing session storage. Resume does not replay into the live conversation; historical import/list/load is separate. A missing native ID on resume must not silently start an empty conversation. On config or credential changes obey current generation/cutover rules.
2. **Session setup:** provider supplies session parameters such as `cwd`, `additionalDirectories`, `mcpServers` and authentication setup when required. Runtime negotiates `agentCapabilities` and declares only client features actually implemented. Core decides tool/permission policy; the vendor translates native options and policy mechanisms without granting authority itself. Do not grant a generic filesystem/terminal service by advertising it casually. A server permission request goes through explicit backend/product policy; an unrecognized method/choice is not blanket approval. Respect native deny rules. Native fork when supported; for agy without fork, use the product's bounded-handoff semantics and label the difference. No hidden unlimited replay.
3. **Model and instructions:** Avibe resolves model and effort; provider maps them to advertised option IDs/values; runtime applies changes before dispatch (model first, then dependent effort). A failed or unsupported selection must not silently infer on the CLI default. For agy, render Avibe's rules into an Avibe-owned per-session directory, respect rule-size limits and use `additionalDirectories`; never modify users' project/global rules as a side effect. No `_meta` prompt injection. If fresh rule/caller context cannot be applied in place, renew at a safe turn boundary and verify the new state; do not interrupt a live turn or fall back to stale identity.
4. **Prepare each turn:** core passes the current `CallerContext` to the runtime. Bind it for this invocation only; the provider must deliver the allowed fields to the actual native tool subprocess through existing caller helpers. A rewritten rule is not evidence of a refreshed tool environment. Test a user turn followed by a delegated run in the same Session; neither can inherit the other's identity or authority. A safe initial fallback is process renewal + native resume when the effective context changes, at the cost of startup latency, subject to generation ownership. If no safe path exists, stop before executing misattributed work. Do not advertise ACP terminal unless execution, environment, cancellation and resource release have an explicit owner.
5. **Native evidence, not product settlement:** runtime maps native updates to existing Avibe events and emits at most one `TurnEnd` for the matching logical turn and runtime generation. `SessionTurnManager` alone settles the product Turn and releases backlog. If a prompt returns with live tools, distinguish genuinely turn-bound work from independently owned Activities using native evidence and existing ownership, not a quiet timer. Coalesce cancel/EOF races into one terminal report; late events from a retired binding cannot settle its successor. Historical `session/load` replay is not a source of live output or terminal events.
6. **Steering:** use `SteerRequest` and `SteerResult` from `core/services/agent_steering.py`. Match logical/native target and attempt ID. A successful write of a second prompt is not an acceptance receipt. Report `ACCEPTED`, `NOT_ACTIVE`, `REFUSED` or `UNKNOWN` according to evidence; reconcile ambiguity read-only. Do not automatically resend ambiguous text, or cancel and replay to simulate steering. Core owns queue disposition; native support requires real provider evidence.
7. **Dependency choice:** prefer the maintained Python ACP client if its supported package/version fits Avibe packaging, async subprocess ownership, server-initiated requests and raw vendor update access. Check these plus cancellation against a tiny scripted peer at implementation start; select one implementation, not parallel SDK and custom paths. Otherwise keep the minimal protocol implementation inside `acp/`; no second general-purpose RPC framework. Do not couple existing native backends to the dependency.

## Delivery slices and parity gates

| Slice | Deliverable and evidence |
|---|---|
| Shared runtime + first real conversation (D/E, part A/C/F/G) | A vendor-neutral scripted stdio peer (no Google fields/credentials) proves session creation, streaming, permission request while prompt pending, cancellation, cross-process resume and exit mid-turn. A thin agy provider + catalog registration then proves a real Web/IM turn, explicit model/effort, stop, resume and one terminal outcome. Review that no shared module imports the provider. Do not expose half-working UI as done. |
| Installation, authentication, model settings (A–C, G8–G12) | One Antigravity backend Settings surface; design frames and owner review before UI build. Reuse an existing CLI login; personal paste-code, Gemini Enterprise, API key/optional base URL and Agent Platform ADC each get their own status and recovery. `AgentAuthService` owns auth status, flow and recovery; the vendor interprets native auth evidence. Distinguish credentials present, catalog available and inference verified. Reading status or saving settings must not trigger inference. Only an explicit connection test or acceptance turn sends a short prompt with an Avibe-selected model. Personal notice as in the issue, no method-based Harness block. Account methods Direct; key-based Hub routing only on verified compatibility. No fabricated quota/cost. Managed install/repair/update and private desktop archive installs use verified releases; disable native auto-update. Include config downgrade-and-save behavior, registration tests and generated UI catalog. |
| Workflow parity and acceptance (remaining D–G) | Native history list/import, fork handoff, attachments, context usage, titles/digests, questions, failure recovery, Activity details, Skills/MCP, subagents, CLI caller identity, Tasks/Watches and delegated runs. Surface unsupported behaviors as the issue specifies. Document effective native MCP/tool policy, not just config intent. For every A–G row track Avibe contract evidence separately from real-provider evidence, marking verified / documented gap with reason / pending evidence; a working chat is not completion. Update both languages of public docs. |

The common runtime and agy owner agree launch/session/turn contracts first. Settings/install can proceed against the existing lifecycle/auth APIs once backend ID, status and catalog contracts are agreed. Extend only the existing services that own those jobs; do not introduce a parallel ACP setup service. No project writes outside the plan during this design discussion.

## Validation and decision gates

- CI: hermetic fake ACP server, temporary home/config/state; registration and auth/setup scenario tests at their existing owner boundaries. Include unsupported capabilities, interruptions, invalid model options, and sibling Session isolation. Verify changes target the correct current turn, not the last run in the same Session.
- Integration: use a held local Incus worktree target for unmerged code; do not restart the live service. This supersedes the issue's API-key requirement for Incus testing, not the product's API-key login option. The owner's authorized, interactive CLI baseline is distinct from automated regression. Do not borrow a personal login for unattended runs; validate orchestration with the fake peer until suitable authorized infrastructure exists. Missing enterprise/platform access is an explicit evidence gap, not an API-key prerequisite. Check desktop install/launch on macOS and Windows and health on Linux.
- Owner acceptance: select an Antigravity Agent in Web/IM; inspect model choice; send and steer a turn; stop a second turn; resume without losing its history; check an attachment and tool activity. Inspect sign-in/recovery and the personal automation notice. Separately verify a scheduled task and a delegated run under an appropriate account/fixture, with correct Session and Run identity. Do not equate an active process with a functioning backend.
- Defer implementation details (in-place reread, hook discovery, SDK selection, per-process footprint) to the owning slice. Escalate only if a result changes user-visible scope, requires writing to the user's project/global profile, weakens policy or invalidates the process/identity model. Login/security boundary changes retain the project's owner approval gate.
