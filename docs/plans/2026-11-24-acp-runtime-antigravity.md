# A shared ACP client, with Antigravity as its first backend

Design specification, 2026-11-24. Scope and parity checklist: [#4244](https://github.com/avibe-bot/avibe/issues/4244), rows A–G. This plan replaces the issue's proposed ownership of transport, sessions and events, not its product scope.

## Outcome and non-goals

A user selects **Antigravity**, uses Google's unmodified `agy acp` and works from the same Web, IM and Harness surfaces as the other native CLI backends. A second built-in ACP backend can reuse the transport, ACP session protocol operations and standard update mapping. ACP is an implementation protocol, not a backend users select. No public plugin SDK, arbitrary-command registration, migration of other backends, Antigravity Bots, alternate Google client identity, or Antigravity as a model source for Vibey. API-key login is in product scope; it is not required for development or for the manual CLI evidence below.

## Ownership and internal contracts

- **Existing core:** owns routing, admission, queues, Turn identity, settlement and runtime ownership. Only `antigravity` receives a backend/catalog entry; ACP is not a public backend or plugin system.
- **`modules/agents/acp/`:** a controller-independent stdlib asyncio stdio NDJSON RPC client and pure mapping of standard session updates. One reader dispatches responses, notifications and server requests asynchronously, including requests received during a prompt. It provides initialize, authentication, session and capability operations, and uses existing process-isolation/cleanup helpers for process-tree mechanics.
- **Three consumers:** the controller's adapter, UI/auth status operations, and native session history use that client without constructing a controller. ACP does not implement `BaseAgent`, own Avibe lifecycle decisions, or define a provider SPI.
- **`AntigravityAgent(BaseAgent)`:** composes the client and owns runtime hooks, launch/session binding, reuse/release decisions, model/effort translation, vendor tools and permissions, and native differences. Authentication and installation retain their existing service owners.

### Launch, identity and instructions

- Key the runtime by `BaseAgent.runtime_turn_key`. Build the launch spec from CLI arguments (including `--agent`), working directory, managed paths, and `caller_env_for_platform_payload(..., session_stable_only=True)` using the existing `MessageContext`, as Claude does. `AgentRequest` has no `caller_context` field.
- Compare the effective environment/launch spec and renewal epoch before reuse. Exclude ordinary IM author, message and turn identity; retain relevant Run, source and remote authority. Never reuse stale authority. Do not introduce a full-context diff, per-turn SPI or `RuntimeGenerationSet`.
- Keep at most one child for a runtime key. Replace at a safe boundary when effective launch inputs change, resuming the stored native session ID. Existing core ownership must permit release: no bound Turn, Activity, delivery or durable owner may still require the resource. An idle chat alone is insufficient. Respect config generations, backend disablement and credential cutover through existing hooks.
- Avibe resolves model and effort. Map them to advertised native options, applying model before dependent effort. Unsupported or failed selection must not fall back to the CLI default.
- Render rules into an Avibe-owned per-session directory supplied through `additionalDirectories`; respect rule-size limits. Do not modify user project/global rules or inject through `_meta`. Refresh changed instructions at a safe boundary, renewing and resuming if needed. Verify effective rules and caller environment in integration, without per-prompt inference preflights or hidden runtime-check inference.
- Resume preserves native history without replay into the live conversation. Missing or failed resume must not silently create an empty session. Keep historical list/load separate from live output. Use native fork when advertised; otherwise use the existing bounded handoff and explain that it preserves a summary rather than full native history.

### Turns, tools and steering

- By default, one primary prompt maps to one Avibe Turn. Map native terminal evidence to one `TurnEnd` for core settlement, bound to the correct logical Turn and runtime. Coalesce cancel/EOF terminal reports; late updates cannot settle a successor. Do not add a second product state machine.
- Verify real CLI completion of non-daemon work. Do not assume every tool always finishes, invent `SessionActivity`, or use quiet timers to infer completion. Revisit ownership only on a concrete native counterexample.
- For a known `session/request_permission`, select an offered allow choice, preferring a one-off allow. Respect user/native allow-deny policy; unknown RPC methods or choices are not approved. Do not default to blanket `--dangerously-skip-permissions`. Apply session-only background-tool policy through `core/agent_tool_policy.py`, with vendor translation rather than a new generic policy layer.
- Advertise only implemented client capabilities. ACP terminal execution, environment, cancellation and cleanup must have an explicit owner before advertising terminal support; standard tool updates alone do not confer that capability.
- The generic ACP v1 client baseline does not guarantee steering. Google documents concurrent-prompt steering for agy; verify native behavior and Avibe acceptance receipts in Slice 3 (see below). Use existing `SteerRequest`/`SteerResult`: unsupported before any write returns `REFUSED` for the core active-session queue; ambiguity after sending returns `UNKNOWN` with no automatic resend. Do not fabricate a read-only reconcile API or simulate steer through cancel/replay. Historical load updates never enter live Turn output.

### Dependency and authentication

- Default to stdlib asyncio, without a target line count or forced buffer size. Adopt an SDK only if it materially simplifies the implementation and demonstrates process-isolation compatibility, Python >=3.10 packaging including CI bands, raw-field access, cancellation and bidirectional requests. Choose one path, not SDK and custom implementations in parallel.
- `AgentAuthService` owns sign-in/status/recovery; the vendor interprets native evidence. Passive checks should prefer `session/list`, minimize returned data, and never expose or log existing session listings. Do not create empty conversations or trigger inference to read status or save settings.
- An explicit connection test distinguishes authentication, catalog availability and successful inference with an Avibe-selected model. A successful `session/list` is not evidence that a model can answer.

## Delivery slices and parity gates

1. **Reusable client only:** unregistered ACP client, pure standard-update mapping and a hermetic vendor-neutral scripted peer. Prove bidirectional dispatch while prompting, initialization/capability handling, cancellation, session operations and exit mid-request. No backend registration or release exposure in this slice. Fake-peer evidence establishes client contracts, not agy behavior.
2. **Coherent registered Antigravity backend:** deliver the working adapter with catalog/config registration, persistence downgrade-and-save behavior, literal/schema inventories, generated TypeScript projection, registration contract tests and minimum Direct-only supply wiring as one mergeable registration change. The backend must work when exposed. Installation, auth and Settings use their existing owners, with product-component design frames and review before UI build. Include managed install/repair/update, verified private desktop archives and native auto-update disablement. Support existing CLI login plus all four methods: personal paste-code, Gemini Enterprise, API key/optional base URL, and Agent Platform ADC, with status and recovery. Keep the issue's personal automation notice without a method-based Harness block.
3. **Remaining parity:** real CLI validation, explicitly including steering, history list/import, fork handoff, attachments, context usage, titles/digests, questions, failure recovery, Activity details, Skills/MCP, subagents, caller environment, Tasks/Watches and delegated runs. Verify effective native tool/MCP policy. Account methods use Direct; key-based Hub routing remains conditional on verified compatibility. Do not fabricate quota or cost. Complete platform acceptance and both languages of public docs.

Retain every A–G row of #4244. Track Avibe contract evidence separately from real-provider evidence, marking verified, documented gap with reason, or pending evidence. A working chat is not completion, and a staged delivery does not establish permanently reduced parity. A second built-in ACP consumer must reuse the client/session operations and standard mapping without a plugin framework.

## Validation and decision gates

- **CI:** temporary home/config/state and a fake peer; exercise unsupported capabilities, auth failures, cancellation, invalid model options, process exit and sibling runtime isolation. Use existing registration and auth/setup scenario boundaries. Runtime identity checks cover effective environment changes and remote authority without turning ordinary IM author/message changes into renewal triggers.
- **Integration:** use a held local Incus worktree target for unmerged code; never restart the live service. Verify the real native tool environment and rules, stop, resume, non-daemon completion, and model/effort behavior. No API key is required to develop or test the basic path. This supersedes the issue's API-key requirement for Incus testing, not API-key product support.
- **Evidence limits:** the owner's authorized interactive CLI baseline is separate from automated regression. Do not borrow a personal login for unattended runs; use the fake peer until suitable authorized infrastructure exists. Missing enterprise/platform access is an explicit evidence gap. Check desktop install/launch on macOS and Windows and health on Linux.
- **Acceptance:** Web/IM selection, explicit model, reply, stop and resume; attachments and tool activity; sign-in/recovery and personal notice; real steering behavior or its documented gap. Separately verify a scheduled task and delegated run under an appropriate account/fixture with the correct Session and Run identity. An active process is not a functioning backend.
- **Decisions:** SDK suitability, native rule refresh, hook discovery and process footprint are implementation checks. Escalate evidence that changes product scope, requires writes to user project/global profiles, weakens policy or invalidates the identity model. Login/security changes retain owner approval.
