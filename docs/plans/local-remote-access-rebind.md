## Reset branch of the rebind flow (never a separate entry)

| Who could do what | What would be lost | Rule | Acceptance check |
|---|---|---|---|
| A failed rebind, a remote Owner, a marked Agent, a hostile page, or an old confirmation tries to reset this computer. | Pairing **and** installation identity; all remote devices’ sessions. | No implicit reset. Only a definite, issuer-authenticated **reset-eligible refusal of this very constrained claim** may unlock the reset branch; neither `binding_rejected`, an arbitrary 409/422, missing ack, proof expiry, network error nor account mismatch qualifies. The machine must observe exact HTTP `409 {"error":"installation_unverified","recovery":"reset_as_new"}` on the constrained verifier-only `/redeem` call, bound to the real hosted session, redirect proof and completed one-time return for this attempt. A browser-supplied result is not evidence. The producer records this terminal refusal only if no external work was admitted; once issued, the same machine verifier can read it again until expiry after a lost response. Never reinterpret an accepted, ambiguous or published operation as refused. Reset must never be offered merely because the caller says the prior account was erased. Only exact direct loopback, no direct ingress, no delegated caller markers, exact Origin, JSON and CSRF. Separate preview and explicit confirmation, short-lived single-use nonce bound to this local initiator and the complete generation (including UUID and pending records). Authenticated owner presence on avibe.bot is not applicable: this action is local only. | Forged, foreign, marked, malformed, expired, replayed and stale-generation confirmations: no state change and zero upstream calls. Dismissing the preview costs nothing. Race two confirms; only one owns the transition. |
| Local operator deliberately detaches a machine **after the qualified rejection**, even if connectivity subsequently fails. | This computer stops serving the old Avibe. If still present on avibe.bot the record and name remain there, unreachable **through this computer**. The cloud account, fences and other machines are not modified. | Clear the local binding and forget its installation UUID; stop the old connector and direct ingress; invalidate old local session authority, registry, remote push, cleaning permissions and pending account/Health authority. Explicit unpair follows Health's revoke-and-purge policy; warn before a connected phone's synced days are lost. Keep local pages and workspace; do not wipe `AVIBE_HOME`. No claim is started. Only a later ordinary, independently authorized enrollment gets a new UUID. A reset is not credential rotation: a copied device secret or tunnel token may remain valid elsewhere. | After reset, local UI remains usable, old remote sessions/transports cannot reach this computer, no old push or stale job acts, no old Health days reach the next owner. New ordinary claim has a different UUID and no prior permissions; after account erasure it cannot recover the erased instance. No cloud delete, revoke, sign-out or lookup is needed. |
| Crash during reset, in-flight claim/rename, obsolete or damaged pairing journal/UUID. | A stale writer restores old credentials, or repeated cleanup erases a fresh pairing. | Shared admission with rename/claim/pairing. Fence live writers before reset; if still actively committing, return `operation_in_progress`. Write nonsecret durable reset intent first; on crash finish that generation only, fail closed until done. A stale/irreparable journal is retireable **only** by the explicit confirmed reset after fencing old replay (including enrolled Desktop/key resume paths). Unreadable evidence is not a successful unbind. Never preserve an old UUID via claim recovery after reset, or rotate an existing one on ordinary bind. Do not require a successful cloud call to abandon local authority; never mark a cloud mutation undone. | Kill on either side of config clear, journal retirement, UUID deletion, and ancillary cleanup. New process finishes the same intent or reports repair; an old completion cannot restore anything; delayed reset cleanup cannot touch a new binding. Test damaged identity/journal, Off mode, and both orderings with rename/claim. |

**Reset order under the shared fence:** (1) Seal the verified-refusal/confirmed-generation reset intent, block every publisher/resume, fence and drain old rename and ingress workers. (2) Retire old remote sessions/transports and remote push against the captured generation, clear config identity and dependent direct secrets/permissions. Never clear unrelated workspace or local pages. (3) Remove all sources that might resurrect the old installation: clear or retire the exact guarded pairing record, including damaged ones isolated by the reset fence, then personal-claim outcome and rejection state. Only then remove the installation-ID file. (4) Remove `instance-address.json` roles/journal and the old instance's persistent clearing lists/receipts, including device and account metadata. (5) Under the same fence run the existing all-device Health revoke-and-purge, even offline; no subsequent pairing may start before it succeeds or reports actionable recovery. Only then finish the reset marker and re-open ordinary enrollment. Each step records completion or is safe to repeat; a newer binding must never be cleaned by old work. A new independent binding does not preserve Health even for the same human. Fixtures: unreadable pending pairing, damaged installation identity, partial config, stale `personal-claim-outcome.json`, stale rejection state, fault between each step. Local damage alone does not unlock reset: when a qualified refusal cannot be obtained for that generation, report repair, not reset eligibility.

Reset branch API proposed for the page: after that specific qualified rejection only, `POST /api/remote-access/rebind/claims/{id}/reset/preview` `{}` → `{confirmation_id,expires_at,health_connected}`; `POST /api/remote-access/rebind/claims/{id}/reset` `{confirmation_id}` → local `200 {state:"unpaired"}` only after completion, otherwise `202 {state:"resetting"}` if durable recovery owns the transition. Same no-store/local-only guards on both; consume only an unexpired server-side refusal record tied to this attempt, initiating browser and still-current complete pairing generation. Expire it on superseding claim/binding or confirmation expiry. Without that record return `409 reset_not_eligible`; no separate row, CLI or unscoped reset route. Other errors: `409 confirmation_expired`, `local_binding_changed`, `operation_in_progress`, or repair error. Never accept an installation ID, secret, account or remote endpoint in these requests. Page confirmation must distinguish *detach this computer* from *delete the Avibe*, disclose sign-outs, data effects and name retention, and never promise that a copied key is revoked. No UX or public CLI implementation in this PR.

## Proposed page contract (not shipped)

- `GET /api/remote-access/rebind` (local, no-store) returns `{binding_state: "unpaired"|"bound"|"binding_rejected"|"pairing_recovery_required", connector_still_running, can_start, unavailable_reason, attempt, next_action: "rebind"|"confirm_as_new"|null, reason_code}`. Only an authenticated qualifying refusal yields `confirm_as_new` with its safe local reason code; status is not itself a reset capability. `binding_state` is separate from the persisted `paired` flag and connector status. Cause-specific values are **not** contracted until producer evidence exists. Return only an allowlisted reason, never upstream body, UUID proof, secrets or session values. Owner away from the machine may receive an action hint in existing authorized status, not the local form, account details or a mutation capability. No state change on GET.
- Proposed `POST /api/remote-access/rebind/claims` with JSON `{locale}` after the page confirmation. Use the stable delegated-caller refusal above; no new presence issuer. On success use the existing `201` redirect-entry form, separate browser cookie and same fixed callback with one-time return proof. Inspect and cancel using local-only `GET /api/remote-access/rebind/claims/{id}` and `POST .../{id}/cancel` `{}`. Existing claims endpoints must **not** expose or cancel a rebind via their weaker admission; ordinary claim modes remain unchanged. Callback must establish direct loopback for this flow (browser navigation does not carry the POST Origin). Status/cancel forms do not regenerate the original proof. Inherit the claim `state`/`code` allowlist, expiry and retry hints. Both the machine claim-success response and the pairing response must carry the same `binding_disposition: "existing"|"new"`; persist it in the protected journal through recovery and project it only on committed success. Never infer it from a local/returned ID comparison. A recovered successor can have a different ID from the stale local predecessor and still be `existing`.
- `400 invalid_request`; `403 direct_loopback_required` / failed CSRF or Origin / `local_operator_required`; `404` unknown claim; `409 not_bound`, `installation_unverified`, `claim_in_progress`, `operation_in_progress`, `already_started`, `local_binding_changed`, `pairing_recovery_required`; protocol/transport failures use existing safe claim codes and bounded backoff. A definite terminal repair is not reported as success. A pre-accept cancellation is distinct from an ambiguous commit.
- Before consent: every remotely signed-in device must sign in again; pages **opened at the local address** are unaffected, not remote tabs merely running on the same computer. Hosted screen shows the actual account and target. If the old Avibe is gone the account can choose a new name and gain access to this machine’s existing workspace. Do not promise the old address stays unless it is a verified reattachment. For a new identity distinguish Health loss from simple sign-out. After durable success: show actual authorized account/hostname, which result occurred, sign devices in again; avibe.bot decides whether the signed-in account can take back a waiting name, including after creating a new instance. Issuer account login is not revoked. Do not show success/old-key assurances until their issuer gate is real. No tunnel credential rotation in this release. On the outside-rename notice and rebind confirmation use Product's approved warning: “If someone may have copied this computer's Avibe data as a whole, delete this Avibe at avibe.bot, bind it again, then take your name back.” No page or copy changes in this PR.

## Decisions and handoff to adjacent writers

1. **Old device retirement belongs to BE-4b N3** (`docs/plans/personal-hostname-release.md`). It promises all predecessor rows revoked at pairing commit, not just the latest old key. The Runtime must not claim this result until that producer is deployed and independently exercised. Fresh randomness, invalidated OAuth consents and queued sign-out refs alone are not revocation.
2. **Detection:** one neutral rejection plus reversible suppression as specified above. No reason-specific diagnosis.
3. **Local caller:** reject marked invocation authority; accept residual unmarked same-user code. No separate human-presence factor. The hosted owner's affirmative confirmation is mandatory on every live reattachment, independent of who is at the computer.
4. **BE-4c predecessor contract, producer review round 2.** Always send machine-only `predecessor:{instance_id,instance_secret}` from protected config to the validated original pairing authority. No raw proof in storage, logs, browser, or redirects. Require explicit protocol acknowledgement (`predecessor_constrained:true`); it attests the constraint cannot be ignored, not that an old secret is still valid. Begin uniformly to avoid exposing instance existence to anonymous probes. At authenticated grant and locked final publication the producer distinguishes:
   - Exact ID live and eligible: existing only, same current Owner must confirm; reject a conflicting UUID mapping. For a live Console instance without a UUID mapping, require the current device-row proof plus fresh Owner consent; rotate in place without attaching any UUID or changing the class of instance. A replaced key must never authorize creation while the old ID exists. If ID and UUID match an already established, eligible mapping, the existing-owner route can proceed even with a replaced key: authority comes from fresh first-party confirmation by that instance’s current Owner, not from the key or UUID. Any binding change invalidates outstanding approval.
   - Exact immutable ID strictly released **or physically absent** (old console-key instances hard-deleted without retaining a row, per `hardDeleteInstance`): use authoritative state, not an active-only lookup or a bad key. Require no erasure fences, unsafe/incomplete retirement or conflicting UUID bindings. With no eligible mapping or veto, permit a separate freshly confirmed new instance with no old resources/permissions. If the UUID now maps to an eligible live successor, only the successor's present Owner can reauthorize that existing instance after fresh consent; never create another or inherit the predecessor's ownership. Revalidate absence/fences/UUID at commit. This is not proof the operator previously owned a missing ID and grants no access to that ID. An existing UUID stays; a genuine pre-UUID data root may receive its first UUID without operator file edits. The old key need not still authenticate a deleted instance.
   - Ambiguous, ineligible or unsupported: fail `installation_unverified` without unconstrained retry. Never discard an associated UUID or publish a different account over a live predecessor. A retained, pre-0087 deleted Desktop tombstone with no provable completed release cannot be treated as physically absent. This historical class is outside the self-service guarantee; Operations verified on November 21, 2026 that Production had zero such records for non-test users. No exception or repair tool. Exercise ordinary console-key and Desktop upgrades in addition to new-style enrollment. Unbound flows unchanged. Preserve a prior Off choice on rebind; ordinary pairing enables and starts access.
5. **Integration seam:** #4114 owns connection control and `_quality_monitor_loop`/`_restart_exited_connector`; central effective-eligibility check must cover these without changing page settings. #4116 owns rename start/replay/journal, cleaning permissions and state-read invalidation. Its current `change()` tests its own journal under `_LOCK`, not a shared claim reservation. The writer whose PR lands second implements **both** admissions with one common reservation; if #4116 lands first, AV-13 owns that integration on latest master. AV-13 owns claim coordinator, protected pairing publication and local routes; do not independently rewrite either sibling’s files. No PR should claim atomic exclusion from a one-sided check.

## Producer review: required before enabling this path

- The constrained flow must be **redirect-only with a literal loopback return** at the producer as well as at the Runtime. A link, Desktop invocation or private-network redirect remains available only to its existing, ordinary flow. The signed-in Owner’s approval must identify the target, the computer requesting control and the consequence for the current computer’s remote access. It cannot prove an untrusted machine name is true. No previous device secret in a browser request or claim record; persist at most the predecessor ID and matched device-row ID (or no match), not a derivative of the secret.
- The acknowledgement alone is insufficient across a mixed deployment or rollback. Even after a new-version 201, an older grant/stage/publish/replay worker must be structurally incapable of consuming the constrained claim as ordinary. The producer’s v2 start schema must enforce `mode=redirect` and canonical literal loopback; the Runtime’s local admission alone does not constrain another HTTP client. The producer isolates constrained claims in a separate v2 lookup domain with no v1 mirror: grant, stage, publish, pairing and exact replay must all enforce the original constraints, including after deployment rollback. The Runtime never resubmits without the constraint. Verify old key redemption cannot consume a v2 handoff in either legacy or request-bound mode.
- Losing a claim-success reply **after the producer created a successor but before local handoff** can leave local predecessor A and UUID now mapped to live B. A new guarded claim must permit a safe recovery: never create C, disclose B to another owner, or treat the absence of A as proof that arbitrary live B is the intended successor. Round 2 permits B only through normal UUID-based eligibility plus the current Owner’s explicit confirmation; return the producer-approved outcome rather than inferring 'created' from different local and returned IDs. Rollback protection also covers this pairing key, and user codes must resolve unambiguously across v1 and v2. For any redeem that also updates the tunnel, failure before publish must leave the prior credential effective; exact replay after publish must never revoke the winner. For in-place Console rotation the key also belongs exclusively to the v2 redemption domain. The protected Runtime journal supplies one stable `redeem_request_id`. First publication atomically seals one response; identical replay while its pairing and receipt remain current returns the same secret and disposition, never a second issuance or a revocation. Changed request tuple, superseded pairing, erasure or retired receipt cannot recover it. Losing the one-time claim success *before* obtaining a pairing key instead requires a new first-party confirmation; no journal exists to replay. If A still exists and the supplied UUID maps to B, always refuse. Test lost reply followed by recovery, as well as a deliberate unrelated UUID/predecessor mismatch.
- N3 must define how the authoritative device is identified among *historical* unrevoked rows, including timestamp/commit order differences. BE-4c rotates in place for a live legacy Console without a mapping; no synthetic enrollment, UUID adoption or class change. The N3 migration is conservative for active instances: do not retire an old device with unknown last-seen time, or on the strength of a newer but never-used device. For a remaining ambiguous set, sensitive secret-only mutations stay blocked. For a constrained rebind the lead proposes proof of any still-valid device row plus fresh current Owner approval with the loopback redirect bridge, then atomically retire all predecessor rows. This recovers users without a pasted key. The bridge proves consent in the **initiating browser**, not that it is the originally paired physical machine; the first-party Owner’s specific informed approval, not loopback by itself, is the trust boundary. Neither concerns ordinary unbound claim requests. Two competing adoption attempts on different UUIDs must not both commit; recheck erasure appearing between grant and publish and races with deletion (installation lock before instance row).
- Historical non-test tombstones were zero in the cited check; an **ineligible or unproved future teardown** can still retain its UUID under #394. Its 401 never authorizes reuse. Account-erasure fences are not ordinary delete release, including on old key-only instances. The operator may **explicitly reset this computer’s remote access** to start a new installation, even if account erasure fenced a predecessor without a UUID. The cloud veto and old identity remain intact; a rejection never triggers reset automatically. Only authenticated, terminal *reset-eligible* refusals for a predecessor that cannot return (such as that exact predecessor’s erasure or its retained completed-deletion veto) unlock reset. The UUID’s own historical tombstone/erasure alone is never evidence against a currently live predecessor; never offer reset for a live predecessor. Wrong logged-in account, a live predecessor with a superseded key, a frozen instance, pending teardown, missing support and transport failure do **not** unlock it. Positive wire evidence must be scoped to the machine verifier, initiating redirect browser and exact attempt; hosted error text cannot qualify. No finer reason goes to an unproven caller. A headless installation without a local browser cannot complete the constrained flow in this version; do not present reset as a headless escape. Do not tell users to clear files.
