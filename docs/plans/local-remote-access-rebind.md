# Bind this computer again (AV-13): proposed Runtime contract

**For rule review, not implemented.** Runtime base `9f3d17451`, avibe-backend `e6e88e1`, address PR #4116 `c9fc071b5`, connection PR #4114 `d7b2fe3a8`. No page changes. Ordinary claim modes and Desktop enrollment stay available. AV-13 adds the equivalent interactive CLI flow; the user-facing terminal adapter, SSH documentation and wording need a Claude writer. This backend contract covers its admission and state transitions. No migration allocated. Producer dependencies are not shipped promises. Decisions from the Devices lead on November 21 are incorporated below.

## Reset branch of the rebind flow (never a separate entry)

| Who could do what | What would be lost | Rule | Acceptance check |
|---|---|---|---|
| A failed rebind, a remote Owner, a marked Agent, a hostile page, or an old confirmation tries to reset this computer. | Pairing **and** installation identity; all remote devices’ sessions. | No implicit reset. Only the claim-scoped evidence described below, or the explicit interactive headless CLI branch, may unlock resetting; neither a generic 401, 409/422, missing ack, expired proof nor outage qualifies. A different account may **not reattach** a live predecessor; a separately authorized, explicit local reset may leave it behind instead (handover branch below). The machine must observe exact HTTP `409 {"error":"installation_unverified","recovery":"reset_as_new"}` on the constrained verifier-only `/redeem` call, bound to the real hosted session, redirect proof and completed one-time return for this attempt. A browser-supplied result is not evidence. The producer records this terminal refusal only if no external work was admitted; once issued, the same machine verifier can read it again until expiry after a lost response. Never reinterpret an accepted, ambiguous or published operation as refused. Reset must never be offered merely because the caller says the prior account was erased. Only exact direct loopback, no direct ingress, no delegated caller markers, exact Origin, JSON and CSRF. Once a qualifying refusal exists, these checks also admit script on a local same-origin Show Page; they do not attest that Settings displayed a confirmation. Separate preview and explicit confirmation, short-lived single-use nonce bound to this local initiator and the complete generation (including UUID and pending records). Authenticated owner presence on avibe.bot is not applicable: this action is local only. | Forged, foreign, marked, malformed, expired, replayed and stale-generation confirmations: no state change and zero upstream calls. Dismissing the preview costs nothing. Race two confirms; only one owns the transition. |
| Local operator deliberately detaches a machine **after the qualified rejection**, even if connectivity subsequently fails. | This computer stops serving the old Avibe. If still present on avibe.bot the record and name remain there, unreachable **through this computer**. The cloud account, fences and other machines are not modified. | Clear the local binding and forget its installation UUID; stop the old connector and direct ingress; invalidate old local session authority, registry, remote push, cleaning permissions and pending account/Health authority. Explicit unpair follows Health's revoke-and-purge policy; warn before a connected phone's synced days are lost. Keep local pages and workspace; do not wipe `AVIBE_HOME`. No claim is started. Only a later ordinary, independently authorized enrollment gets a new UUID. A reset is not credential rotation: a copied device secret or tunnel token may remain valid elsewhere. | After reset, local UI remains usable, old remote sessions/transports cannot reach this computer, no old push or stale job acts, no old Health days reach the next owner. New ordinary claim has a different UUID and no prior permissions; after account erasure it cannot recover the erased instance. No cloud delete, revoke, sign-out or lookup is needed. |
| Crash during reset, in-flight claim/rename, obsolete or damaged pairing journal/UUID. | A stale writer restores old credentials, or repeated cleanup erases a fresh pairing. | Shared admission with rename/claim/pairing. Fence live writers before reset; if still actively committing, return `operation_in_progress`. Write nonsecret durable reset intent first; on crash finish that generation only, fail closed until done. A stale/irreparable journal is retireable **only** by the explicit confirmed reset after fencing old replay (including enrolled Desktop/key resume paths). Unreadable evidence is not a successful unbind. Never preserve an old UUID via claim recovery after reset, or rotate an existing one on ordinary bind. Do not require a successful cloud call to abandon local authority; never mark a cloud mutation undone. | Kill on either side of config clear, journal retirement, UUID deletion, and ancillary cleanup. New process finishes the same intent or reports repair; an old completion cannot restore anything; delayed reset cleanup cannot touch a new binding. Test damaged identity/journal, Off mode, and both orderings with rename/claim. |

Before adding another CLI question, first describe in one sentence how a real person would reach it. For a state reachable only through file damage plus an interruption, give one plain explanation and the single safe command instead of adding a dialogue. Fresh reset authorization reuses the existing reset confirmation.

**Reset order under the shared fence:** (1) Seal the verified-refusal/confirmed-generation reset intent, block every publisher/resume, fence and drain old rename and ingress workers. (2) Retire old remote sessions/transports and remote push against the captured generation, clear config identity and dependent direct secrets/permissions. Never clear unrelated workspace or local pages. (3) Remove all sources that might resurrect the old installation: clear or retire the exact guarded pairing record, including damaged ones isolated by the reset fence, then personal-claim outcome and rejection state. Only then remove the installation-ID file. (4) Remove `instance-address.json` roles/journal and the old instance's persistent clearing lists/receipts, including device and account metadata. (5) Under the same fence run the existing all-device Health revoke-and-purge, even offline; no subsequent pairing may start before it succeeds or reports actionable recovery. Only then finish the reset marker and re-open ordinary enrollment. Each step records completion or is safe to repeat; a newer binding must never be cleaned by old work. A new independent binding does not preserve Health even for the same human. Fixtures: unreadable pending pairing, damaged installation identity, partial config, stale `personal-claim-outcome.json`, stale rejection state, fault between each step. Local damage alone does not unlock reset: if a qualified browser refusal cannot be obtained for the damaged generation, the page points to the interactive local CLI flow. That flow can explicitly reset each listed damaged fixture without inferring deletion, requiring a cloud lookup, or making the user edit files.

Reset branch API proposed for the page: after that specific qualified rejection only, `POST /api/remote-access/rebind/claims/{id}/reset/preview` `{}` → `{confirmation_id,expires_at,health_connected}`; `POST /api/remote-access/rebind/claims/{id}/reset` `{confirmation_id}` → local `200 {state:"unpaired"}` only after completion, otherwise `202 {state:"resetting"}` if durable recovery owns the transition. Same no-store/local-only guards on both; consume only an unexpired server-side refusal record tied to this attempt, initiating browser and still-current complete pairing generation. Expire it on superseding claim/binding or confirmation expiry. Without that record return `409 reset_not_eligible`; no separate row, standalone reset command or unscoped reset HTTP route. Other errors: `409 confirmation_expired`, `local_binding_changed`, `operation_in_progress`, or repair error. Never accept an installation ID, secret, account or remote endpoint in these requests. Page confirmation must distinguish *detach this computer* from *delete the Avibe*, disclose sign-outs, data effects and name retention, and never promise that a copied key is revoked. UI rendering is owned by the Devices page writer.

### Two explicit reset branches in addition to terminal predecessor refusal

- **Computer has changed hands.** A hosted, attempt-bound `other_account` decision can offer an explicit local detach only after the supplied key matched a device row for this exact predecessor (valid or revoked) and the initiating browser has the required proof. An ID alone is never an email-hint or reset oracle. Require a distinct private outcome and producer-sanitized masked hint; never pass through an untrusted raw email. Do not extend this handover branch to organization, frozen, or deleting instances without an explicit producer eligibility decision. First show only the producer-authorized masked holder hint and suggest signing into that account. Then, separately, the operator may confirm treating the computer as new: the prior account’s Avibe will no longer reach this computer and that account will **not** be notified. Never show an arbitrary account’s email or free its assets; no pretending to attach its live Avibe. No hint or eligibility from a query parameter, local account guess, or generic failure. The proved machine response uses `recovery:reset_as_new` in both cases. `reason:other_account` requires an `owner_hint` matching one ASCII alphanumeric on each side with literal stars (`a***@b***`), or exactly `***`; `reason:predecessor_unrecoverable` forbids a hint. Treat each as a closed field combination, not independent flags. `reason:active_pairing_recent` has no recovery or hint; it never permits reset.
- **Headless interactive CLI.** Bound reattachment still requires the browser path; do not translate it into link mode. If that proof cannot be provided, an unmarked local interactive invocation can instead present the same explicit loss confirmation, reset this data root as a new computer, then start an **ordinary** link claim with independent first-party login and local confirmation of actual account and hostname. Require interactive input and output; default No, EOF/failure/automation → no mutation. No generic unscoped HTTP reset for this exception. Noninteractive/marked processes must not gain an alternate command; same-OS-user code remains the admitted residual. Document SSH forwarding separately, not as proof of physical presence. The CLI removal lane cannot retire legacy console key entry before an actual headless Incus exercise (reset → link → local confirmation → regain the waiting name). The dedicated recovery journal and Health/push cleanup are shared with web reset.

## Proposed page contract (not shipped)

- `GET /api/remote-access/rebind` (local, no-store) returns `{binding_state: "unpaired"|"bound"|"binding_rejected"|"pairing_recovery_required", connector_still_running, can_start, unavailable_reason, attempt, next_action: "rebind"|"confirm_as_new"|null, reason_code}`. Only an authenticated qualifying refusal yields `confirm_as_new` with its safe local reason code; status is not itself a reset capability. `binding_state` is separate from the persisted `paired` flag and connector status. Cause-specific values are **not** contracted until producer evidence exists. Return only an allowlisted reason, never upstream body, UUID proof, secrets or session values. Owner away from the machine may receive an action hint in existing authorized status, not the local form, account details or a mutation capability. No state change on GET.
- Proposed `POST /api/remote-access/rebind/claims` with JSON `{locale}` after the page confirmation. Use the stable delegated-caller refusal above; no new presence issuer. On success use the existing `201` redirect-entry form, separate browser cookie and same fixed callback with one-time return proof. The page submits only the `user_code` and `redirect_state` fields returned by its own local start request, never values from the address bar, a URL fragment, navigation state or external input. Inspect and cancel using local-only `GET /api/remote-access/rebind/claims/{id}` and `POST .../{id}/cancel` `{}`. Existing claims endpoints must **not** expose or cancel a rebind via their weaker admission; ordinary claim modes remain unchanged. Callback must establish direct loopback for this flow (browser navigation does not carry the POST Origin). Look up the claim's flow first, then validate its exact query: v1 requires `claim_id,state`; v2 requires `claim_id,state,callback_token`, each exactly once. A v1 return with a token and a v2 return without it are both rejected; neither tries the other handler. Invalid returns do not consume the valid initiating cookie or proof. Status/cancel forms do not regenerate the original proof. Inherit the claim `state`/`code` allowlist, expiry and retry hints. Both the machine claim-success response and the pairing response must carry the same `binding_disposition: "existing"|"new"`; persist it in the protected journal through recovery and project it only on committed success. Never infer it from a local/returned ID comparison. A recovered successor can have a different ID from the stale local predecessor and still be `existing`.
- `400 invalid_request`; `403 direct_loopback_required` / failed CSRF or Origin / `local_operator_required`; `404` unknown claim; `409 not_bound`, `installation_unverified`, `claim_in_progress`, `operation_in_progress`, `already_started`, `local_binding_changed`, `pairing_recovery_required`; protocol/transport failures use existing safe claim codes and bounded backoff. - Before consent: every remotely signed-in device must sign in again; pages **opened at the local address** are unaffected, not remote tabs merely running on the same computer. ## Callback authority: under independent review

The v2 accept must carry the producer’s unpredictable single-use callback token as well as the machine verifier and confirmed subject. Retain it only in the originating Runtime flow’s memory after validating the claim-bound initiating cookie, fixed callback, origin and state. Exclude it from logs, persisted state, browser continuation, referrers and ordinary status. An exact admitted operation may retry idempotently, never mint new authority. This token improves on a return HMAC the initiating client can compute but is not a proof of hardware or physical co-location. The normal workbench intentionally serves same-origin Show content; do not assume it is a dedicated trusted pairing origin. A live transfer requires the current Owner’s explicit authorization on the trusted first-party screen: actual account, actual target Avibe, requesting computer’s **self-reported** name, and what the original computer loses. The instance ID selects a target but proves nothing. The redirect is an additional browser-flow proof, not proof of the physical machine or immunity to deception.
