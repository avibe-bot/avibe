# Bind this computer again (AV-13): proposed Runtime contract

**For rule review, not implemented.** Runtime base `9f3d17451`, avibe-backend `e6e88e1`, address PR #4116 `c9fc071b5`, connection PR #4114 `d7b2fe3a8`. No change to the page, public CLI, ordinary claim modes or Desktop enrollment. No migration allocated. Producer dependencies are not shipped promises. Decisions from the Devices lead on November 21 are incorporated below.

## What each actor can do

| Who could do what | What would be lost | Rule | Acceptance check |
|---|---|---|---|
| Remote Owner, member, LAN neighbor, direct/relay/proxy client, foreign page, or Agent acting for one of them starts or cancels. | Owner’s control of their computer; everyone’s sessions. | Separate local-only operation, not an `allow_bound` parameter on an existing claim route. Require direct loopback socket and Host, no forwarded metadata or direct ingress, exact Origin and CSRF for JSON mutations. Do not expose a CLI/Harness method. Reject all delegated/Agent invocations, regardless of the originating role (same invocation authority classification as #4114 `vibe remote direct on|off`; its HTTP adapter marks `X-Vibe-Delegated-Change`). Treat a supplied delegation marker as narrowing authority; malformed or duplicates do not broaden it. Fail `403 local_operator_required`. A same-OS-user process without any invocation markers is accepted by design, as in #4116 A4. This is not human presence attestation. | Remote Owner/member, LAN, proxy, direct ingress, wrong/missing Origin, bad CSRF: no upstream call/record. Agent-marked loopback with correct Host, Origin and CSRF is also refused without a call. Unmarked direct local invocation is admitted, but only the real current Owner can confirm a live target on avibe.bot. |
| Local operator picks an account; live installation belongs to a different account, was transferred, or has been deleted. | Replacement of another Owner’s binding; unexpected access to **all the existing local workspace**. | Preserve the data-root installation UUID. Backend read/grant alone decides existing versus new, requires explicit first-party account consent and rejects a different account for a live target. `existing_instance_id` is a **screen grant** field, not a Runtime start or verifier observation field. An ordinary completed, released deletion permits a new name, new instance ID and potentially a different account; not transfer of the old Avibe or its members. Never create a UUID to escape a conflict. Never revive a held name. | Existing owner → same ID and current hosted name even if local URL stale. Other-account/transfer → no local binding change or secret issuance. After completed release → same UUID, new ID, available chosen name. Held old prefix remains unavailable. |
| Previously key-paired computer has no installation association, or its file belongs to another binding. | Even with the original instance still alive, a new claim could switch the whole machine to a different account. | Do not infer cloud association from presence of a UUID, absence of a file, or `invalid_device_secret`. For every bound rebind, constrain machine `POST /api/v1/claims` to the predecessor in protected config (decision 4); never rely on the old marker/file to prove correspondence. No unsupported predecessor can fall through to an unconstrained start. Do not block legacy key pairing or ordinary Desktop enrollment. | Legacy unverified source → no unconstrained start, name hold, or local replacement; supported proof + live authorized Owner → same ID. Test absent UUID, unrelated UUID, copied stale outcome, and an older producer that returns a ticket without recognizing the proof. Existing claim-completed, Desktop-associated and previously renamed fixtures need a trustworthy positive association; absence of evidence is not consent to create. |
| A copied device key remains usable after replacing the local config. | Another holder could still act for this Avibe after the promised recovery. | The cutover must revoke **all predecessor device credentials** atomically at cloud pairing redeem commit, not grant/start/local save. Before commit a stolen live key may still work. Do not claim revocation covers separately issued access tokens, a copied tunnel token, or a compromised host. **Producer dependency:** `completePairingReceipt` in both stores inserts a device, but does not revoke predecessors. `getInstanceByDeviceSecret` checks *any* unrevoked matching row, not latest. Issuance alone is insufficient. | First verify old key on a harmless protected read, reattach, then the exact same read with old key must refuse while new key succeeds. Also check authoritative rename authentication, non-latest older key and exact-request replay in producer tests. No testing real stolen keys. |
| Cancel before grant, close tab, timeout, lost response, crash, two starts, pending key/claim/Desktop journal. | Half-unbound computer, duplicate pairing, or accidental rollback over a newer owner. | Never blank config or call revocation as preflight. One claim lock per root. Snapshot old identity, settings and exact pending op; CAS before accept and journal handoff, and at publication. While merely starting leave connector, cookie secret, Off choice and peripherals alone. Pre-accept cancel fences callback then attempts decline; no promise that a remote name hold was freed without acknowledgment. From accept dispatch onward cancel is `already_started`. Before pairing dispatch persist same protected request/redeem ID; replay sealed target, never roll cloud back or publish over a new generation. After lost one-time claim response before handoff, fresh claim may be needed; this is not a lost successful **pairing** reply. | Race double-start/cancel/callback/key/desktop. Restart at accept dispatch, prepared before POST, lost pairing reply, sealed credentials, config saved before retirement. Old binding untouched on pre-commit failure. Once backend commits, local failure means **finishing/recovery required**, not “nothing changed”; all durable replay uses same ID and secret. No ordinary start/status probe silently starts another rebind. |
| Network outage, stale DNS, proxy, misleading HTML 401, cached or out-of-order response. | Healthy tunnel is stopped or healthy access called deleted. | Proposed authoritative signal: two **consecutive, separately scheduled** completed live reads of the current binding’s `GET /api/v1/instances/{id}/authorization-revision`, at least 15 s apart, each exact HTTP 401 JSON `error: invalid_device_secret` from the validated configured HTTPS authority, redirects disabled, no cache. Track only this scheduler’s observations, never arbitrary caller input or dozens of concurrent device calls. Reset candidate on any other result, restart or binding change. Check pairing generation after I/O. A valid 200 with nonnegative integer revision for the same binding restores normal operation. Do not use plain HTTP test backends as public evidence. | One 401, two simultaneous replies, redirect, 404, 403, `429`, 5xx, malformed/HTML, TLS/DNS/timeout, stale old-pair reply: no new suppression. 401/timeout/401 does not trip it. Two qualifying 401s do. With trusted TLS compromised or a repeatedly lying control plane even two answers can be wrong; suppression is reversible. |
| Removed instance vs key replaced elsewhere. | Wrong diagnosis, repeated connector restarts, destruction based on ambiguous evidence. | The two cases return the **same 401**. Repetition establishes only `binding_rejected`; not `removed` or `key_replaced`. Do not infer cause from DNS, public URL, tunnel exit, claim result alone, or a generic 404. Keep config and requested On/Off; persist only generation-bound suppression and safe reason. Gate connector start/restart, repair and candidate promotion at the lifecycle owner; keep local UI and a low-frequency validation read running (proposed once per 5 minutes while suppressed; no poll per status GET). A healthy validation clears it and reconciles only if still requested; publication of a new pairing also clears it. A healthy running connector is not torn down on the first refusal. Reason-specific text needs separately authenticated producer evidence, ideally matched to the old credential without making instance IDs an existence oracle. | Simulate rejection → restart process → no start loop, local page and rebind still available. 200 under old generation cannot clear suppression for new generation. Good fresh 200 recovers an On binding, never starts an Off one. Label is neutral unless producer can actually disambiguate. |
| Rename overlaps rebind or late hostname-state reply arrives. | Wrong hostname or cleaning someone else’s browser. | Require a common cross-process exclusion/admission decision with #4116, from durable rename intent through completion and from rebind start through terminal handoff/recovery. Simultaneous loser gets `operation_in_progress` before cloud mutation. No file-exists check as substitute for atomic mutual exclusion. Crash leaves durable owner; interrupted rename must reach a terminal issuer result or explicit recovery, not silently discarded. All pairing writes invalidate cleaning grants and late reads; same ID retains eligible history but requires fresh state under new key, different ID inherits nothing. Lost-key/indefinitely pending rename must have a safe operator exit; do not invent a committed receipt. | Race in both orders, process restart with each journal, delayed old state across config switch; no second issuer writer, no stale clearing. New-key state then allows taking back a still-held old name for the same instance. |
| Browser, phone, or delayed worker carries old authority across local cutover. | Old sessions, push, or account sign-outs reach the next owner. | New pairing gets fresh session secret and registry binding. All remote sessions including unregistered cookies and long-lived authenticated streams lose access; local-origin pages/storage remain intact. Registry must not show the former binding as current. Disable prior remote push subscriptions (including unattested and native relay rows), not local subscriptions; no assumption that changing session secret disables push sends. Prevent stale writes and avoid disabling new-generation subscriptions when replaying. #4107 account queue uses issuer pairing epoch, so old queued refs retire as `not_applicable/binding_changed`, never re-signed with new credentials; no new account sign-outs. Already accepted effects cannot be recalled. | Old remote cookie/stream and push endpoint cannot read/receive after publication; new sign-in and new registration work. Simulated late writer/worker, crash before/after effects, retry after new subscription; local subscription and local tab unaffected. Prequeued account work never sent with new key. |
| iPhone Health pairing or pending owner proof crosses cutover. | Synced days deleted on a mere 401 or disclosed to a different owner. | `core/handlers/mobile_health.current_identity` binds to live instance ID and owner, not browser cookie; same ID/owner retains Health and data, although browser and device-registry association changes. Confirmed different identity follows existing revoke-and-purge, never a background sign-out based on an outage or old check; ensure no prior owner's days are served to new owner during cutover. Old #4107 Health check is epoch + registry bound. | Same owner+ID rebind preserves phone credential/data; new ID (even same account) refuses it and enforces current identity before Health reads; rejected/outage/cancel alone never purges. Queued old check cannot purge fresh pairing. |

## Proposed page contract (not shipped)

- `GET /api/remote-access/rebind` (local, no-store) returns `{binding_state: "unpaired"|"bound"|"binding_rejected", can_start, unavailable_reason, attempt}`. `binding_state` is separate from the persisted `paired` flag and connector status. Cause-specific values are **not** contracted until producer evidence exists. Return only an allowlisted reason, never upstream body, UUID proof, secrets or session values. Owner away from the machine may receive an action hint in existing authorized status, not the local form, account details or a mutation capability. No state change on GET.
- Proposed `POST /api/remote-access/rebind/claims` with JSON `{locale}` after the page confirmation. Use the stable delegated-caller refusal above; no new presence issuer. On success use the existing `201` redirect-entry form, separate browser cookie and same fixed callback with one-time return proof. Inspect and cancel using local-only `GET /api/remote-access/rebind/claims/{id}` and `POST .../{id}/cancel` `{}`. Existing claims endpoints must **not** expose or cancel a rebind via their weaker admission; ordinary claim modes remain unchanged. Callback must establish direct loopback for this flow (browser navigation does not carry the POST Origin). Status/cancel forms do not regenerate the original proof. Inherit the claim `state`/`code` allowlist, expiry and retry hints; completed result records `result: reattached|created_after_release` only with verified provenance.
- `400 invalid_request`; `403 direct_loopback_required` / failed CSRF or Origin / `local_operator_required`; `404` unknown claim; `409 not_bound`, `installation_unverified`, `claim_in_progress`, `operation_in_progress`, `already_started`, `local_binding_changed`, `pairing_recovery_required`; protocol/transport failures use existing safe claim codes and bounded backoff. A definite terminal repair is not reported as success. A pre-accept cancellation is distinct from an ambiguous commit.
- Before consent: every remotely signed-in device must sign in again; pages **opened at the local address** are unaffected, not remote tabs merely running on the same computer. Hosted screen shows the actual account and target. If the old Avibe is gone the account can choose a new name and gain access to this machine’s existing workspace. Do not promise the old address stays unless it is a verified reattachment. For a new identity distinguish Health loss from simple sign-out. After durable success: show actual authorized account/hostname, which result occurred, sign devices in again; only live reattachment can take back a held name. Issuer account login is not revoked. Do not show success/old-key assurances until their issuer gate is real. No page or copy changes in this PR.

## Decisions and handoff to adjacent writers

1. **Old device retirement belongs to BE-4b N3** (`docs/plans/personal-hostname-release.md`). It promises all predecessor rows revoked at pairing commit, not just the latest old key. The Runtime must not claim this result until that producer is deployed and independently exercised. Fresh randomness, invalidated OAuth consents and queued sign-out refs alone are not revocation.
2. **Detection:** one neutral rejection plus reversible suppression as specified above. No reason-specific diagnosis.
3. **Local caller:** reject marked invocation authority; accept residual unmarked same-user code. No separate human-presence factor. The hosted owner's affirmative confirmation is mandatory on every live reattachment, independent of who is at the computer.
4. **BE-4c predecessor contract, proposed to the producer and both reviewers.** Always send machine-only `predecessor:{instance_id,instance_secret}` from protected config to the validated original pairing authority. No raw proof in storage, logs, browser, or redirects. Ask for explicit protocol acknowledgement (`predecessor_constrained:true` proposed); it attests the constraint cannot be ignored, not that an old secret is still valid. Begin uniformly to avoid exposing instance existence to anonymous probes. At authenticated grant and locked final publication the producer distinguishes:
   - Exact ID live and eligible: existing only, same current Owner must confirm; reject a conflicting UUID mapping. Legacy adoption of an unassociated UUID also requires the current device proof. A replaced key must never authorize creation while the old ID exists.
   - Exact immutable ID strictly released **or physically absent** (old console-key instances hard-deleted without retaining a row, per `hardDeleteInstance`): use authoritative state, not an active-only lookup or a bad key. Require no erasure fences, unsafe/incomplete retirement or conflicting UUID bindings. Permit only a separate freshly confirmed new instance, with no old resources/permissions. Revalidate absence/fences/UUID at commit. This is not proof the operator previously owned a missing ID and grants no access to that ID. An existing UUID stays; a genuine pre-UUID data root may receive its first UUID without operator file edits. The old key need not still authenticate a deleted instance.
   - Ambiguous, ineligible or unsupported: fail `installation_unverified` without unconstrained retry. Never discard an associated UUID or publish a different account over a live predecessor. Producer wire and validation of a replaced key on exactly-correlated existing UUID are under review. Exercise ordinary console-key and Desktop upgrades in addition to new-style enrollment. Unbound flows unchanged. Preserve a prior Off choice on rebind; ordinary pairing enables and starts access.
5. **Integration seam:** #4114 owns connection control and `_quality_monitor_loop`/`_restart_exited_connector`; central effective-eligibility check must cover these without changing page settings. #4116 owns rename start/replay/journal, cleaning permissions and state-read invalidation. Its current `change()` tests its own journal under `_LOCK`, not a shared claim reservation. Coordinate both sides of interlock; land shared contract before the consumer. AV-13 owns claim coordinator, protected pairing publication and local routes; do not independently rewrite either sibling’s files. No PR should claim atomic exclusion from a one-sided check.

**Verification gate:** focused hermetic tests at actual admission, producer-client, pairing publication, transport and worker boundaries. Then a clean exact head on a temporary local Incus worktree, fresh test-account bind → console delete → explicit observation → fresh bind with unchanged installation ID, separately same-ID live reattach → old device credential rejected and new accepted. Operations owns account, environment turn and cleanup; no production calls from a developer checkout. No merge by the writer.
