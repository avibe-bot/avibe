# Bind this computer again (AV-13): proposed Runtime contract

**For rule review, not implemented.** Runtime base `9f3d17451`, avibe-backend `e6e88e1`, address PR #4116 `c9fc071b5`, connection PR #4114 `d7b2fe3a8`. No change to the page, public CLI, ordinary claim modes or Desktop enrollment. No migration allocated. Three promises require decisions outside this Runtime PR; do not enable a weaker operation under this name.

|---|---|---|---|
| Remote Owner, member, LAN neighbor, direct/relay/proxy client, foreign page, or Agent acting for one of them starts or cancels. | Owner’s control of their computer; everyone’s sessions. | Separate local-only operation, not an `allow_bound` parameter on an existing claim route. Require direct loopback socket and Host, no forwarded metadata or direct ingress, exact Origin and CSRF for JSON mutations. Do not expose a CLI/Harness method. These checks establish a local **connection**, not a person. A same-user shell can construct a local request. If “never by a remote-user Agent” includes that shell, require separate trusted user-presence approval before cloud start; no approved issuer for this action exists on master. Fail closed pending decision. | Remote Owner/member, LAN, proxy, direct ingress, wrong/missing Origin, bad CSRF: no upstream call/record. For an actual presence requirement, an ordinary local process with no verified approval must also make zero starts; checking a request header, cookie, terminal or HTML click is not this test. |
| Local operator picks an account; live installation belongs to a different account, was transferred, or has been deleted. | Replacement of another Owner’s binding; unexpected access to **all the existing local workspace**. | Preserve the data-root installation UUID. Backend read/grant alone decides existing versus new, requires explicit first-party account consent and rejects a different account for a live target. `existing_instance_id` is a **screen grant** field, not a Runtime start or verifier observation field. An ordinary completed, released deletion permits a new name, new instance ID and potentially a different account; not transfer of the old Avibe or its members. Never create a UUID to escape a conflict. Never revive a held name. | Existing owner → same ID and current hosted name even if local URL stale. Other-account/transfer → no local binding change or secret issuance. After completed release → same UUID, new ID, available chosen name. Held old prefix remains unavailable. |
| Previously key-paired computer has no installation association, or its file belongs to another binding. | Even with the original instance still alive, a new claim could switch the whole machine to a different account. | Do not infer cloud association from presence of a UUID, absence of a file, or `invalid_device_secret`. Otherwise `installation_unverified` and no cloud start. Do not block legacy key pairing or ordinary Desktop enrollment. Pre-accept cancel fences callback then attempts decline; no promise that a remote name hold was freed without acknowledgment. From accept dispatch onward cancel is `already_started`. Once backend commits, local failure means **finishing/recovery required**, not “nothing changed”; all durable replay uses same ID and secret. No ordinary start/status probe silently starts another rebind. |

Track only this scheduler’s observations, never arbitrary caller input or dozens of concurrent device calls. Reset candidate on any other result, restart or binding change. ## Proposed page contract (not shipped)

- `GET /api/remote-access/rebind` (local, no-store) returns `{binding_state: "unpaired"|"bound"|"binding_rejected", can_start, unavailable_reason, attempt}`. `binding_state` is separate from the persisted `paired` flag and connector status. Cause-specific values are **not** contracted until producer evidence exists. Return only an allowlisted reason, never upstream body, UUID proof, secrets or session values. Owner away from the machine may receive an action hint in existing authorized status, not the local form, account details or a mutation capability. No state change on GET.
- Proposed `POST /api/remote-access/rebind/claims` with JSON `{locale}` after the page confirmation; presence mechanism unresolved. On success use the existing `201` redirect-entry form, separate browser cookie and same fixed callback with one-time return proof. Inspect and cancel using local-only `GET /api/remote-access/rebind/claims/{id}` and `POST .../{id}/cancel` `{}`. Existing claims endpoints must **not** expose or cancel a rebind via their weaker admission; ordinary claim modes remain unchanged. Callback must establish direct loopback for this flow (browser navigation does not carry the POST Origin). Status/cancel forms do not regenerate the original proof. Inherit the claim `state`/`code` allowlist, expiry and retry hints; completed result records `result: reattached|created_after_release` only with verified provenance.
- `400 invalid_request`; `403 direct_loopback_required` / failed CSRF or Origin / `local_approval_required`; `404` unknown claim; `409 not_bound`, `installation_unverified`, `claim_in_progress`, `operation_in_progress`, `already_started`, `local_binding_changed`, `pairing_recovery_required`; protocol/transport failures use existing safe claim codes and bounded backoff. A definite terminal repair is not reported as success. A pre-accept cancellation is distinct from an ambiguous commit.
- Before consent: every remotely signed-in device must sign in again; pages **opened at the local address** are unaffected, not remote tabs merely running on the same computer. Hosted screen shows the actual account and target. If the old Avibe is gone the account can choose a new name and gain access to this machine’s existing workspace. Do not promise the old address stays unless it is a verified reattachment. For a new identity distinguish Health loss from simple sign-out. After durable success: show actual authorized account/hostname, which result occurred, sign devices in again; only live reattachment can take back a held name. Issuer account login is not revoked. Do not show success/old-key assurances until their issuer gate is real. No page or copy changes in this PR.

## Decisions and handoff to adjacent writers

1. **Security release blocker:** producer must establish predecessor invalidation at actual paired-credential use sites. Fresh random keys and invalidated OAuth consents/queued sign-out refs do not revoke an old device row. A Runtime-only fix cannot make the advertised key guarantee.
2. **Detection:** ship neutral rejection plus reversible suppression, or extend producer with private reason-specific credential results. Exact delete/replaced promises cannot be met with the current error. Avoid a public instance-existence oracle.
3. **Local human:** accept local OS-user code as owner (as #4116 A4 explicitly does), or provision independent, transaction-bound presence not available to the Agent. Recommend the latter if the literal exclusion is required. A pair of HTTP requests, nonces issued over loopback, or a custom header is not physical proof. Where an Agent has unrestricted same-user file/code access, preventing all equivalent actions also requires process isolation, beyond one route.
4. **Provenance/legacy:** the backend does not take the currently bound ID at claim start; key-paired legacy instances can have no cloud installation association. Fail closed on unknown predecessor rather than silently creating a new remote owner while a different live Avibe still exists. Needs an explicit support boundary or producer work. Preserve a prior Off choice; existing ordinary pairing enables and starts access, so this rebind path must specify otherwise.
5. **Integration seam:** #4114 owns connection control and `_quality_monitor_loop`/`_restart_exited_connector`; central effective-eligibility check must cover these without changing page settings. #4116 owns rename start/replay/journal, cleaning permissions and state-read invalidation. Its current `change()` tests its own journal under `_LOCK`, not a shared claim reservation. Coordinate both sides of interlock; land shared contract before the consumer. AV-13 owns claim coordinator, protected pairing publication and local routes; do not independently rewrite either sibling’s files. No PR should claim atomic exclusion from a one-sided check.

**Verification gate:** focused hermetic tests at actual admission, producer-client, pairing publication, transport and worker boundaries. Then a clean exact head on a temporary local Incus worktree, fresh test-account bind → console delete → explicit observation → fresh bind with unchanged installation ID, separately same-ID live reattach → old device credential rejected and new accepted. Operations owns account, environment turn and cleanup; no production calls from a developer checkout. No merge by the writer.
