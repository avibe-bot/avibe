# Connection settings: admission, confirmation and recovery

**Rule-table review, before implementation.** Scope: the instance's new Devices → Connection methods API. Not the App path selector, certificate flow, remote master switch or relay transport. The proposals marked **decision** affect what the owner can do; they are not implemented behavior.

## Rules and acceptance

| Who / event | What could be lost | Enforcement | Acceptance at the owning boundary |
| --- | --- | --- | --- |
| Member, Editor, Viewer, unauthenticated caller, agent invocation or LAN setup client | Owner's control of exposure; privacy of switch state | Admit only a verified current instance Owner browser session on this pairing, or the trusted host on strict direct loopback. Apply normal mutation origin/CSRF checks. Never infer Owner from an installation ID, request-supplied role or path metadata. All new reads, writes, proof, keep, and put-back use the same gate. | For each role hit each route, including reads and stale IDs; denials contain no state and cause no mutation. Direct ingress, forwarded loopback and setup LAN never qualify for the local exception. Test the Member legacy projections too (decision below). |
| Owner changes one of direct, public relay, tunnel protocol, edge family or outbound address | This device's route to the instance | Direct loopback commits immediately. Otherwise persist recovery intent before the first effect, apply **one** change, and permit a keep for 30 s from activation. No trial/clock on a no-op. Direct/relay are preferences: no grants, new relay URLs, or certificate/provisioning API; relay is off unless explicitly opted in. Direct off never changes the saved relay preference. | With an injected clock: all five settings, both directions, including a pin → automatic. Verify no keep by default, a local update has no trial, and failure before activation leaves the original in effect. Fresh and upgraded install without relay consent stays off. |
| Owner arriving via direct changes an endpoint-affecting switch while their tunnel is down | Their only reachable path **even after rollback** | **Decision A: preflight before tearing down the only known way back.** For an active direct endpoint, a direct or relay policy change can retire the endpoint, including relay *on*. Require a fresh same-session round trip through the tunnel before the destructive cutover; simplest: require the mutation on that tunnel, otherwise return `alternate_path_required` without writing. Instance-side health is not evidence of this device's reachability. | With tunnel unusable by the initiating device but a working direct session, direct off and relay transitions leave current streams, generation, admissions and disk state intact. Via a working tunnel, enact the actual switch and trial. Never ask the user to copy keys or go home. |
| A second device of the same Owner, signed-out/replaced session, another account, old request, or old connector presses keep | A broken route gets committed permanently | Bind trial to the server-verified pairing + subject + browser **session**, not a reported device/install identifier. Read proof only after cutover via an admissible route; consume a short-lived trial-scoped unpredictable challenge on the same admissible route at keep, with current authorization, exact trial/generation and deadline rechecked. Never give the challenge in the mutation response. Signed-in Owner sessions are the device boundary, not hardware attestation. | New sign-in on the same account, copied display ID, revoked SID, old challenge, different trial, proof via correct route then keep via retired route, and a keep at t=30 all fail. Two simultaneous keeps have at most one effect; another observer reading status cannot keep. |
| Old tunnel is draining, sidecar hasn't observed a write yet, or client falls back | An old route is mistaken for proof of a new one | **Decision B:** for a tunnel change require a request carried by the promoted connector for these settings. Verify server-side ingress (e.g. match the live origin socket tuple to the active managed connector process identity); a host, CF header, PID alone, or a health sample isn't enough. For a switch, accept a fresh round trip on a route that remains available after the old endpoint is retired and lifecycle has acknowledged the new configuration. A browser may keep an enable via the surviving tunnel; this proves continued access, **not** that it used direct/relay. If proof is unavailable, do not accept keep. | Delayed apply-response, old direct stream/old connector, unknown proxy/ambiguous attribution, proof from the apply request, guessed proof, and same-session polls before activation can't keep. A fresh request on the new connector can. On a switch, a fresh request on the surviving tunnel can even when relay is not connected; report it honestly. |
| Owner changes route optimisation or its policy, or intentionally stops remote access | Needless delay; automatic restart against explicit stop | Optimisation fields commit immediately; the master switch remains the existing explicit action. Trial/revert/automatic operations write allow-listed connection fields only, never `enabled`, credentials, pairing, request marker or another setting. Runtime reconciliation respects explicit stop. | Optimisation changes during a trial survive rollback; stop during a trial or automatic recovery stays stopped; a previously enabled service is not stopped. Neither remote nor local generic Web config may be a permanent direct/relay write escape. Host CLI remains the existing host facility. |
| UI crashes, clock changes, system sleeps, timer callback is delayed | Unconfirmed candidate survives indefinitely | One recoverable record per instance; persist previous and proposed value and pairing before applying. On process startup recover any nonterminal change **before** starting remote workers or accepting keep. Use a suspend-aware elapsed deadline, or conservatively expire on an unaccounted gap; never extend on wall-clock rollback. Check expiry on mutation/keep as well as in an independent worker. | Crash before/after config write, after activation, and during reversal; reopen the real journal. No crash or clock direction produces a kept outcome. Long resume rejects an immediate keep even before a periodic tick. No real waits in clock tests. |
| Two trials, a competing CLI/legacy write, or re-pair during recovery | Revert overwrites newer intent or another pairing | One active/reverting trial across the five settings. CAS against the owned field **and** its ownership/generation at write; serialize with the config writer. Superseding local/legacy field writes retire the reservation (ABA included); do not restore a whole config snapshot. Do not apply old state to a different pairing. | Second trial yields conflict without resetting the first clock. Simulate A→B→A by another writer, re-pair, and unrelated edits mid-trial; no later intent is undone. Duplicated keep/put-back/expiry cannot change an unrelated value. |
| Revert can't write or can't reconcile the runtime | False “restored” message; unowned live settings | Once expired/put back, keep is impossible. Persist `reverting` debt, retry with bounded backoff, retain last safe field value, distinguish storage restoration from runtime reconciliation. Continue independently of a browser; report trouble, not success. Do not require an old bind address to still exist to restore its saved value; let pin protection address an actual outage. | Inject write failure, connector-busy and reconciliation failure, then restart. No `reverted` success while work remains. Retry when available, preserve unrelated state and never stop/restart the whole service. |
| Tunnel with one or more pins can't connect for three consecutive minutes | Owner stranded by a once-good pin; or loss of an intentional egress constraint | Observe only local, identity-fenced connector evidence while tunnel is enabled **and requested**. Count zero registered connections or verified absence/exit while requested; one registered connection suffices for recovery. Partial HA, slow requests, failed public probes, unreadable metrics/PID and missing samples aren't evidence of a continuous outage. Reset observation on success, discontinuity, restart/sleep, pin tuple or pairing change. At 180 s release the still-matching pins to `auto`, `auto`, `""` together, recording each; don't guess which pin is at fault. Respect trial ownership and recheck eligible fields under lock; never undo a concurrently applied pin from stale evidence. | At 179.9 s no change; at 180 s reset just the unchanged pins. At 179 s + success + 179 s no change. Test unknown evidence, intentional stop, wake, reboot, missing interface, multiple pins and competing trial. Exercise an actual new connector picking automatic settings, not just a JSON rewrite. |
| Network operator can make the connection fail | A forced switch of IP family or egress interface, potentially outside the owner's preferred network | The 3-minute reset **can change egress**, not just performance. It can only remove pins. It cannot change credentials, relay consent, direct permission, authorization, destination, or enable/disable remote access. It cannot promise a working network. | Compare non-pin fields, requested state and relay publication before/after an outage. Return a durable reason for each pin actually reset; do not silently re-pin later. |

## Proposed page contract

Under `/api/devices/connection`, `GET` returns an Owner projection (`Cache-Control: no-store`). `PATCH` accepts exactly `{setting,to}` from the existing `ConnectionChange` vocabulary (`protocol`, `ipFamily`, `outbound`, `direct`, `relay`, `autoRecovery`, `profile`). Backend owns `from`, time, actor, connection evidence and outcome. Direct returns `off | awaiting-permission | denied | awaiting-certificate | not-running | ready`. Relay returns `{enabled,connected}`; `connected` requires a valid current-generation observed relay publication, not the direct ready bit. Do not publish endpoint IDs/addresses, certificate paths, process metadata, session IDs or session secrets.

`trial` is null or `{id, phase: applying|pending|reverting, change:{setting,from,to}, startedBy:{deviceId}, isMine, secondsLeft, canKeep}`. `deviceId` is the existing device list's public ID; not authority. The current owner can navigate away and recover this state even if the initiating HTTP response was lost. `secondsLeft` is server-derived, zero in reverting, and absent before activation. A post-activation proof operation and `POST .../trials/{id}/keep` are bound as above; `POST .../trials/{id}/revert` by the initiating Owner need not prove the candidate works. Not sending either requires no browser timer. A status read is not a confirmation. `outcome` includes id, change, starter's public ID, result (`kept`, `reverted`, or superseded by an explicit change), time and reason (`owner`, `timeout`, `restart`, `apply_failed`, `superseded`). Expose the latest trial outcome separately from the latest `returnedToAutomatic:{at, reason:tunnel_unreachable, changes:[...]}` so simultaneous recovery does not erase it. Scope and bound the records to this pairing. Distinguish `reverting` with a retryable error from a completed `reverted` outcome.

Errors: 400 invalid shape/value; 401 authentication; 403 non-owner, non-bound caller or different initiator; 404 stale/unknown trial; 409 busy/conflicting ownership, alternate path required or new path not proven; 410 expired; 503 unavailable storage/runtime/recovery. Deny before disclosing trial identity/state. A busy/error result must never implicitly apply or reset a trial.

## Discrepancies for the lead

1. Direct isn't a reversible socket toggle: `DirectAccessLifecycle._observe_config` invalidates the generation and clears permission, `_reconcile` stops its supervisor/ingress, and `DirectRendezvous.publish(None)` revokes admissions. A new sidecar has a new ephemeral endpoint. The App bootstraps new rendezvous via the public path (`remote-direct-ios.md`, §12). Restoring JSON while the tunnel stays down cannot restore the original App connection. **Decision A is a precondition, not a warning.** An unconditional apply-first alternative needs a separate recoverable transport/bootstrap design agreed by the direct lane; do not retain revoked admissions or change certificates.
2. `remote_access.apply_settings` preflights a candidate (up to 30 s per attempt), persists/promotes it, then synchronously drains the previous connector (up to 35 s); it can also persist with no running connector. Its return, including `previous_connector_drained:false`, is not cutover proof. Start the trial at activation rather than the end of this call, and don't stall the 30 s recovery timer behind candidate/drain work. Record apply intent beforehand. The main listener and the direct peer label have no connector-generation proof on their own. A platform/ingress where the backend can't establish provenance must decline the keep; it must not infer it from the Host header.
3. The existing `/api/remote-access/status` is Member-readable and includes `direct`; Member also receives full `client_config_payload` on `/api/config`. Legacy `/api/remote-access/settings` admits Member at route policy and today's page has no keep action. Thus preserving **all** legacy behavior and making the switches invisible to Member / all remote pin writes conditional cannot both be true. Proposal: redact only the direct/relay fields from non-Owner settings/status projections, including operation results. Keep the old tunnel page/CLI workflow for its existing settings, protect pins from later outages regardless of writer; guard legacy writes against trampling a trial, and restrict generic direct/relay Web changes to the new route. **Decision:** if all remote tunnel writes must be trials even on the legacy page, that page needs a confirmation affordance; don't retrofit a silent 30 s revert.
4. The shipped edge-family default is `"4"` (`VibeCloudConfig`), not automatic. The stored value does not distinguish default from explicit IPv4. Treat effective `4` as a pin for the 180 s rule; automatic fallback writes explicit `"auto"`, without changing fresh-install defaults in this PR. The direct plan's host-shell-only opt-in is superseded **only** for this Owner web operation: default off, permission, installed pin, owner-only relay admission, operator/cohort gates, and trial residuals remain. No change to certificate handling or pairing suspend.
5. The view's `relay:boolean` renders an enabled relay from *direct* readiness; its `trial` prop has no initiator, and it has no kept/returned-to-automatic props. Backend must report truth, not overload `direct` or fake `reverted`. The routing/consumer PR must adapt these props; no UI change here.

## Verification and release gates

Focused route/admission tests, injected-clock failure/atomicity tests, and a test with real disposable process/socket identities for confirmation. Then obtain the lead's local Incus turn. Use the repository runner on an isolated **worktree** target, preserving pairing, credentials, requested state and saved settings. Demonstrate remote keep, timeout, restart mid-trial and automatic recovery after an observed outage. Repeat direct-only/no-tunnel case and relay off/on with an admitted real App if that topology is available; otherwise name the missing setup and give steps, not a simulated success. No migrations allocated or created. Only the lead merges after exact-head review (including direct lane), CI and runtime exercise.
