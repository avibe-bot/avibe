# Devices → Connection methods: instance contract

A bad tunnel setting must not strand the Owner until they can get back to the computer. The instance checks the change; the browser is not the verifier. This API does not select the App's path, enroll a machine in a trial, change certificates, or replace the master remote-access switch.

## Rules and acceptance

| Event | Rule | What to verify |
| --- | --- | --- |
| Reading or changing settings | Only the current paired Owner session or the trusted host on strict direct loopback can use the new page API. Enforce mutation origin/CSRF checks. Neither a LAN setup request, forwarded address, direct peer, client-supplied ID nor agent invocation is local-host authority. Same-origin content the Owner opens can act with the same browser session: this is not proof of a human gesture. | Non-Owner gets 403 with no state; unauthenticated remote request gets 401. Members cannot read or write the **two settings** through `/api/config`, old settings/status projections or mutation responses. Their own `POST /api/direct/rendezvous`, native handover and header path (stream `via` + App path) are unchanged. They can infer whether a path is offered. Members still read tunnel state at `/api/remote-access/status`. |
| Owner changes protocol, IP family or outbound interface with a connector running | Require a fresh successful public-path baseline for this pairing and active connector. Reserve one change durably and reply before touching settings. Register and promote the replacement, **wait for the former connector to exit, then probe the instance via its public address** with the new connector the sole active one. Check identity before and after. Only a successful fresh probe commits the result. Otherwise restore the previous value and reconcile the runtime. Same behavior from direct, tunnel and host; independent of browser, device, session and continued polling. | Old connector may drain for 35 s; a successful public probe during overlap is not evidence. No device confirmation, proof, keep or undo endpoint. UI shows *verifying* with no timer: readiness, drain, verification and recovery take time (on the order of a minute, not a deadline for the user). Closing the page cannot turn failure into success or success into failure. |
| No connector running | With verified absence of a running connector and no conflicting lifecycle work, save the pin change immediately without verification, rollback or starting the tunnel. An unverified process identity is not “stopped”. The 180 s rule applies subsequently if enabled and requested. | An Owner on direct can change a broken pin back to automatic with the tunnel stopped and without a baseline. Deliberately stopped access stays stopped. |
| Owner switches direct or changes relay policy | Both directions require a fresh successful instance public tunnel health sample (at most 60 s, same active generation). Busy while another connector is taking over/draining or observation is paused; otherwise refuse missing, stale or unsuccessful evidence with `tunnel_unhealthy`. An HTTP request, Cloudflare header or connector metrics alone do not replace the baseline. An unenrolled relay write is refused first. Reserve the intent, send the final response body, **then** write the setting and notify lifecycle. Neither switch is provisional; no timeout or automatic re-opening. Direct off preserves the saved relay preference. | Accept an App on direct without a prior path change. On refusal no setting, admission or stream changes. After a lost response reread after reconnection; never replay an uncertain mutation. No claims about the route now in use. **Residual for the page next to direct:** a phone whose network cannot reach Cloudflare will disconnect when it turns off its working direct path, until it moves to a network that can reach Cloudflare. The instance cannot test that phone's network. |
| Public relay availability | Eligibility is host-controlled (`state/public-relay-host-enrollment.json`), separate from the saved `public_relay_trial` switch. Adopt a released host-only `true` once; no evidence in an old off value. Only the host CLI, with no invocation authority, can enroll. CLI off and Web off leave enrollment intact; no unenroll operation in this version. It belongs to the **current pairing**: re-pair requires a new local CLI opt-in; changing a domain prefix on the **same** instance is not a re-pair and must preserve it (also a contract for rename). Web and lifecycle consult the same eligibility. | Without enrollment omit the relay row entirely and reject *either* value, even a no-op, with `403 relay_not_enrolled` before health or readiness checks (after authorization). No Web/automatic operation creates enrollment. On enrolled instances existing direct permission and compatible transport still apply. When enabled, **all direct admissions on that endpoint are Owner-only**, including non-relayed paths. |
| Other entry points | Existing remote master-off confirmation and legacy tunnel form semantics stay unchanged. Route optimisation and its profile remain immediate. Pure host-shell direct CLI remains immediate. Owner-authorized agent invocation of `remote direct on/off` is remote: ask the UI process on authenticated/trusted loopback to check its own health observation and record the mutation; never read health from a CLI-process global or treat failed IPC as evidence the service is gone. Verified absence of the UI lifecycle means no endpoint is live: allow and record. Relay enrollment CLI remains host-shell only. | Neither generic Web writes nor invocation CLI bypass enrollment. Simulate active UI / down tunnel, UI proven stopped, and ambiguous UI liveness separately. No operation here writes the total enabled setting, secrets, certificate configuration, tunnel request marker or pairing. |
| Crash, re-pair or competing edit | Persist old and new values, operation ID and pairing **before** effect. On startup repair interrupted tunnel verification before starting lifecycle workers. Never undo a switch. Compare the owned field and write generation while serialized with config writers, including legacy/CLI ABA. Own just the relevant fields; never restore a full snapshot. A stale worker cannot affect a new pairing or a superseding intent. | Restart before or after configuration write, promotion, probe, or restoration. An unresolved switch reservation can be abandoned before effect, or recognized as saved; no automatic reverse write. Unrelated settings survive. |
| Restore cannot complete | Use bounded attempts/backoff. Distinguish old value saved but runtime not restored (`saved_restored_runtime_pending`) from failing to restore storage. End the foreground operation, keep durable recovery evidence and allow an explicit new Owner change to this same setting to supersede it, including during recovery. Never report “restored” just because old JSON was written. | Restart with an unavailable old interface or busy connector; slot does not stay busy forever, and late old work cannot overwrite the repair. Respect an explicit stop. |
| Fixed values, enabled/requested tunnel, continuous zero connections for 180 s | Count observed zero registrations or verified connector exit, not latency, incomplete HA, failed public probes, uncertain PID or missing samples. Reset the window across success, sleep/gaps, new pins, stop, restart or re-pair. After 180 s **first retry the saved pins**; only immediately after that attempt fails try a new connector with all still-matching pins set to automatic **in memory**. Persist `auto` (protocol), `auto` (edge IP), `""` (outbound address) and record actual changes only if that connector registers. If both fail, keep pins and continue observation with bounded retries. | One registered connection ends the outage. If the network has already recovered, the saved-pin attempt wins. Selective blocking can release a pin and change egress; complete loss of connectivity cannot on its own rewrite even the factory IPv4 pin (`edge_ip_version: "4"`). No credential, permission or direct/relay changes. Concurrent edits, requested-stop and generation changes cancel stale work. |

## Page API

`GET /api/devices/connection` is a no-store Owner projection. `PATCH` there accepts exactly `{setting,to}`; settings are `protocol`, `ipFamily`, `outbound`, `direct`, `relay`, `autoRecovery`, `profile`. The server owns all evidence, previous values, results and times. For operations requiring background work, `202` means **accepted, not applied**. A no-op or immediate save returns `200`. No browser-bound action, countdown, device identity or challenge. After a lost response or page reopen, read `GET`, do not replay. After authorization, absent enrollment is checked even before checking for a relay no-op.

- `settings`: tunnel settings; `direct`: `off` when disabled; `ready` for enabled/running; `denied` for waiting-permission/permission_denied; otherwise `awaiting-permission` for waiting-permission; `awaiting-certificate` for waiting-certificate. All other enabled states are `not-running`, including installing, starting, stopping, missing transport and errors. Readiness is not evidence a request traveled over that path.
- `relay` (enrolled Owner only): `{enabled, connected, canEnable, unavailableReason, ownerOnlyDirectWhenEnabled:true}`. Map only a current-generation observed relay publication to `connected`; enabled does not mean connected. Tell the Owner the effect on members **before** enabling. No grant, enrollment or URL choice is provided on this page.
- `operation`: null or `{id,setting,state}` (`applying`, `verifying`, `restoring`). No action and no promised number of seconds. `outcome`: latest `{id,setting,result,reason,at}` for the pairing; `applied`, `restored`, `failed` or `superseded`. Render success or restoration as a single line; distinguish failed/incomplete restoration from success. `returnedToAutomatic` is independent: `{at,reason:"tunnel_unreachable",changes:[{setting,from,to}]}` or null. Do not expose secrets, raw host identifiers, socket addresses or process metadata.
- `400 invalid_connection_change`; `401` unauthenticated; `403 connection_owner_required` or `relay_not_enrolled`; `409 connection_change_busy` for competing/paused work, `tunnel_unhealthy` for a missing healthy baseline, and a specific reason if direct permission/transport is unavailable. `503 connection_state_unavailable` when storage or observation cannot be trusted. Rejection is before mutation. Terminal failure after 202 is read from state, not a second HTTP response.

## Release and evidence

Ordinary direct permission is not a relay trial grant. Before expanding the direct allowlist, require our own relay with default-deny admission, a default-off per-instance relay permission and a control-plane kill switch; this change authorizes none of that. See `remote-direct-relay.md`. No certificate/rendezvous or App path-selection change, migration, or feature flag.

Separate focused fixture results from reviewed-head Incus results on a real isolated paired tunnel: successful public verification, actual failure and restoration, restart, and selective vs total outage. A stock iroh client exercises the instance, not an iPhone. The existing hosted simulator `DirectPathAppTests` cover path loss/public-only rebuild; no authorized isolated physical App or live relay is available for this exercise. Mark these E2E cells **not run** and leave the real-device cases to the Owner, not automated changes on their production instance.
