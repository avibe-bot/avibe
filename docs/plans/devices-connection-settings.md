# Devices → Connection methods: instance contract

A bad tunnel setting must not strand the Owner until they can get back to the computer. The instance checks the change; the browser is not the verifier. This API does not select the App's path, enroll a machine in a trial, change certificates, or replace the master remote-access switch.

## Rules and acceptance

| Event | Rule | What to verify |
| --- | --- | --- |
| Reading or changing settings | Only the current paired Owner session or the trusted host on strict direct loopback can use the new page API. Enforce mutation origin/CSRF checks. Neither a LAN setup request, forwarded address, direct peer, client-supplied ID nor agent invocation is local-host authority. Same-origin content the Owner opens can act with the same browser session: this is not proof of a human gesture. | Non-Owner gets 403 with no state; unauthenticated remote request gets 401. Members cannot read or write the **two settings** through `/api/config`, old settings/status projections or mutation responses. Their own `POST /api/direct/rendezvous`, native handover and header path (stream `via` + App path) are unchanged. They can infer whether a path is offered. Members still read tunnel state at `/api/remote-access/status`. |
| Owner changes protocol, IP family or outbound interface with a connector running | No healthy baseline is required: a running but unhealthy tunnel may be the reason for changing a pin. Record whether a fresh baseline exists only to describe a later failure. Reserve one change durably and hold the managed connector lane from reservation through outcome (including the gap after drain); do not hold the config mutex across network I/O. Reply before touching settings. Register and promote the replacement, **wait for the former connector to exit, then probe the instance via its public address** with the new connector the sole active one. Check identity before and after. First successful public `/health` response (HTTP 2xx, no redirects, up to three attempts within a single 12 s elapsed budget) commits the result. Late responses never commit. Otherwise restore the previous value and reconcile the runtime; report `verification_unavailable` if the previous route lacked a healthy baseline, not that the new pin caused the outage. Same behavior from direct, tunnel and host; independent of browser, device, session and continued polling. | Old connector may drain for 35 s; a successful public probe during overlap is not evidence. No device confirmation, proof, keep or undo endpoint. UI shows *verifying* with no timer: readiness, drain, verification and recovery take time (on the order of a minute, not a deadline for the user). Closing the page cannot turn failure into success or success into failure. |
| No connector running | With verified absence of a running connector and no conflicting lifecycle work, save the pin change immediately without verification, rollback or starting the tunnel. An unverified process identity is not “stopped”. The 180 s rule applies subsequently if enabled and requested. | An Owner on direct can change a broken pin back to automatic with the tunnel stopped and without a baseline. Deliberately stopped access stays stopped. |
| Owner switches direct or changes relay policy | Require a fresh public tunnel health observation only if **all three** hold: direct is enabled, this change disables direct or flips relay policy, and this is not a strict host-loopback request. A delegated CLI arriving over IPC still counts as remote. At least **one success in the latest completed window** (started within 60 s, same pairing and active connector) is sufficient. Enabling direct, changing the saved relay preference while direct is off, and strict host-loopback edits require no tunnel preflight. These are ordinary writes, not verification operations. Busy while another connector is taking over/draining or observation is paused; otherwise refuse missing, stale or unsuccessful evidence with `tunnel_unhealthy`. An HTTP request, Cloudflare header or connector metrics alone do not replace the baseline. An unenrolled relay write is refused first. Reserve the intent and send the final response body. For a non-local switch, allow about one second outside the locks for the old endpoint to forward the response. Recheck the reservation and gates, then write the setting and notify lifecycle. This grace period is not a delivery acknowledgement. Neither switch is provisional; no timeout or automatic re-opening. Direct off preserves the saved relay preference. | Accept an App on direct without a prior path change. On refusal no setting, admission or stream changes. After a lost response reread after reconnection; never replay an uncertain mutation. No claims about the route now in use. **Residual for the page next to direct:** a phone whose network cannot reach Cloudflare will disconnect when it turns off its working direct path, until it moves to a network that can reach Cloudflare. The instance cannot test that phone's network. |
| Public relay availability | Eligibility is host-controlled (`state/public-relay-host-enrollment.json`), separate from the saved `public_relay_trial` switch. Adopt a released host-only `true` once; no evidence in an old off value. Only the host CLI, with no invocation authority, can enroll. CLI off and Web off leave enrollment intact; no unenroll operation in this version. Eligibility belongs to the **current pairing**: use a domain-separated digest of the immutable instance ID keyed by the instance pairing credential (`instance_secret`), never the browser `session_secret`, URLs or the display prefix. Persist the one-time legacy adoption decision per installation, including a negative decision. Verify master off/on and prefix rename preserve eligibility; a new pairing (even with the old enabled bit still true) loses it and is never adopted a second time. Host CLI opt-in is required there. Web consults this eligibility for the relay switch. Since 2026-11-26 the lifecycle does not require it: the server's `public_traversal_allowed` and the user's explicit off decide the relay (`remote-direct-relay.md`), and the enrollment only tells an old unrecorded off on an enrolled pairing from the untouched default. | Without enrollment omit the relay row entirely and reject *either* value, even a no-op, with `403 relay_not_enrolled` before health or readiness checks (after authorization). No Web/automatic operation creates enrollment. On enrolled instances existing direct permission and compatible transport still apply. When enabled, **all direct admissions on that endpoint are Owner-only**, including non-relayed paths. |
| Other entry points | Existing remote master-off confirmation and legacy tunnel form semantics stay unchanged. Route optimisation and its profile remain immediate. Pure host-shell direct CLI remains immediate. Owner-authorized agent invocation of `remote direct on/off` is remote: ask the UI process on authenticated/trusted loopback to check its own health observation and record the mutation; never read health from a CLI-process global or treat failed IPC as evidence the service is gone. Verified absence of the UI lifecycle means no endpoint is live: allow and record. Relay enrollment CLI remains host-shell only. | Neither generic Web writes nor invocation CLI bypass enrollment. Simulate active UI / down tunnel, UI proven stopped, and ambiguous UI liveness separately. No operation here writes the total enabled setting, secrets, certificate configuration, tunnel request marker or pairing. |
| Crash, re-pair or competing edit | Persist old and new values, operation ID and pairing **before** effect. On startup repair interrupted tunnel verification before starting lifecycle workers. Never undo a switch. Compare the owned field and write generation while serialized with config writers, including legacy/CLI ABA. Own just the relevant fields; never restore a full snapshot. A stale worker cannot affect a new pairing or a superseding intent. | Restart before or after configuration write, promotion, probe, or restoration. An unresolved switch reservation can be abandoned before effect, or recognized as saved; no automatic reverse write. Unrelated settings survive. |
| Restore cannot complete | Use bounded attempts/backoff. Distinguish old value saved but runtime not restored (`saved_restored_runtime_pending`) from failing to restore storage. At the bound, after restoring storage, retire **only the positively identified failed-verification connector** if it is still current and requested. Never stop a newer generation or withdraw the request. Ordinary exited-connector recovery restarts with saved settings; the 180 s rule still applies. If retirement cannot be established, report failure and retain fenced recovery debt rather than claiming success. End the foreground operation, keep durable recovery evidence and allow an explicit new Owner change to this same setting to supersede it, including during recovery. After a rejected pin, a same-field change is busy until the old value is back on disk. Reaffirming the restored disk value does not cancel pending runtime repair. Never report “restored” just because old JSON was written. | Restart with an unavailable old interface or busy connector; slot does not stay busy forever, and late old work cannot overwrite the repair. Respect an explicit stop. |
| Fixed values, enabled/requested tunnel, continuous zero connections for 180 s | Count observed zero registrations or verified connector exit, not latency, incomplete HA or failed public probes. Starting or draining a connector does not itself interrupt the timer. Short gaps in active registration evidence (unknown PID or missing count) earn no time but preserve accumulated time; a gap longer than 2.5 sampling intervals discards it. This tolerates one missed tick plus scheduling jitter without counting the unobserved time. A positive registration on any managed connector ends the outage. An occupied connector lane defers an expired attempt without resetting the timer. Reset the window across success, sleep/gaps, new pins, stop, restart or re-pair. After 180 s, separate restoring access from changing settings. Follow the three phases below. Only failures observed against a registered working connector can justify releasing individual pins; a successful rescue alone is never evidence to change them. | One registered connection ends the outage. If the network has already recovered, the saved-pin attempt wins. Selective blocking can release a pin and change egress; complete loss of connectivity cannot on its own rewrite even the factory IPv4 pin (`edge_ip_version: "4"`). No credential, permission or direct/relay changes. Concurrent edits, requested-stop and generation changes cancel stale work. |

## Page API

`GET /api/devices/connection` is a no-store Owner projection. `PATCH` there accepts exactly `{setting,to}`; settings are `protocol`, `ipFamily`, `outbound`, `direct`, `relay`, `autoRecovery`, `profile`. The server owns all evidence, previous values, results and times. For operations requiring background work, `202` means **accepted, not applied**. A no-op or immediate save returns `200`. No browser-bound action, countdown, device identity or challenge. A switch can retire the direct stream before the phone receives the response. The page must treat a missing or truncated response as **outcome unknown**, not as a failed change. Once the connection is re-established over the tunnel, read `GET /api/devices/connection`; if the operation is pending, continue reads only. Never replay the `PATCH`. On page reopen, likewise read state. After authorization, absent enrollment is checked even before checking for a relay no-op.

- `settings`: tunnel settings; `direct`: `off` when disabled; `ready` for enabled/running; `denied` for waiting-permission/permission_denied; otherwise `awaiting-permission` for waiting-permission; `awaiting-certificate` for waiting-certificate. All other enabled states are `not-running`, including installing, starting, stopping, missing transport and errors. Readiness is not evidence a request traveled over that path.
- `relay` (enrolled Owner only): `{enabled, connected, canEnable, unavailableReason, ownerOnlyDirectWhenEnabled:true}`. Map only a current-generation observed relay publication to `connected`; enabled does not mean connected. Tell the Owner the effect on members **before** enabling. No grant, enrollment or URL choice is provided on this page.
- `operation`: null or `{id,setting,from,to,state}` (`applying`, `verifying`, `restoring`). No action and no promised number of seconds. `outcome`: latest `{id,setting,from,to,result,reason,at}` for the pairing; `applied`, `restored`, `failed` or `superseded`. Render success or restoration as a single line; distinguish failed/incomplete restoration from success. `returnedToAutomatic` is independent: `{at,reason:"tunnel_unreachable",changes:[{setting,from,to}]}` or null. Do not expose secrets, raw host identifiers, socket addresses or process metadata.
- `400 invalid_connection_change`; `401` unauthenticated; `403 connection_owner_required` or `relay_not_enrolled`; `409 connection_change_busy` for competing/paused work, `tunnel_unhealthy` only for a missing required switch baseline. Relay enable on an active direct endpoint may return `direct_permission_required` (no fresh direct permission) or `relay_transport_unavailable` (no verified compatible pin). A change which never reached a settings write or connector promotion reports `failed` (`candidate_not_ready`, `connection_change_busy`, or `settings_not_applied`), not `restored`. A candidate not becoming ready is not a failed public probe. Recovery failures carry reason `saved_restored_runtime_pending` or `storage_restore_failed`; a completed restoration can carry `verification_failed` (baseline had worked) or `verification_unavailable` (no healthy baseline). `503 connection_state_unavailable` when storage or observation cannot be trusted. Rejection is before mutation. Terminal failure after 202 is read from state, not a second HTTP response.

## Residual limits

- One edge registration is enough to end an outage, promote a saved-pin/automatic recovery candidate, or confirm a matching connector during repair; an unknown count never proves recovery. A user-requested live switchover instead requires a ready candidate with at least four HA connections before retiring the old connector, then a successful public check. A route with only one to three registrations is therefore degraded, not disconnected: automatic fallback does not run, and a replacement that also lacks full HA is not promoted. From the host or an independent working path, stop the tunnel, save the new pin, then start it again. Do not stop the only remote path.
- A running instance that can never reach its own public address cannot positively verify a new pin. From a surviving path or the host, stop the tunnel, save the setting, then start; do not recommend stopping the user's only connection remotely.
- Verification excludes other *managed* connectors. Another, unmanaged connector on the same tunnel token can answer and hide a failure; this is the same deployment limit as route optimisation.
- The legacy `/api/remote-access/settings` retains its existing unverified Member-capable tunnel write in this version. Remove that route with the old page in the cleanup PR; it cannot change either exposure switch.

## Fixed-setting recovery: restore access before attributing a failure

1. **Find a working route.** Freeze the first transport from the pinned protocol, the startup preference, the last observed protocol, or HTTP/2, in that order. Try it and its explicit opposite with all saved egress constraints. If those both fail, try the same pair without the outbound address, retaining the saved IP family. Only then remove the IP-family pin too. Skip duplicate tiers: a protocol pin alone needs two windows, one egress pin at most four, both egress pins at most six. Each registration window is 30 s after the initial 180 s; the three-minute maximum is registration wait, not a bound including process cleanup. Do not try changing the family while keeping a bound address: the address determines the family ([Cloudflare Tunnel run parameters, `edge-bind-address`](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/cloudflared-parameters/run-parameters/#edge-bind-address)). An unknown result ends the search without saving anything. Promote the first registered candidate without rewriting the saved settings.
2. **Compare while the working connector stays active.** For each difference from the saved pins, start a replica of the working combination with just that field restored. Retain the field if the comparison registers. Count failure only with evidence that the working generation is still registered. An indeterminate observation stops all attribution: keep the temporary route, keep disk unchanged. A comparison never replaces or stops the active connector. All registered replicas may carry traffic to the same local origin ([Cloudflare Tunnel replicas](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-availability/)). Stop a comparison as soon as it registers or the result is known. Unix uses the existing graceful stop with a 35 s grace period. Windows terminates the process first and waits for exit; this is **not** a drain. Requests on that replica may be interrupted and need to reconnect or retry. Graceful Windows shutdown for all handovers is a separate follow-up, not exercised here.
3. **Verify the combined result.** Apply only individually supported releases. Before saving **any** release, require a fresh registration of the combined result, even when the current connector already serves with exactly those settings. A surviving session does not prove that new connections still work. If the combination differs, switch only after registration; if it matches, stop the test replica and leave the active connector alone. On missing or failed confirmation, keep the working connector and do not save. This can add one 30 s window **after** access is back; it brings the samples closer in time, not absolute proof of causality. A transport preference change in automatic mode is not a change to a setting. Record `returnedToAutomatic.changes` only for fields actually released. `temporaryRoute` is `null` unless the active process generation matches the recovery record. Otherwise it reports `phase`, the explicit running `protocol`, and `differences` (setting names, not the write result). An otherwise unchanged start keeps the identified temporary generation when the registration count is positive or cannot be read. A confirmed zero permits replacement. This exception never substitutes for positive registration evidence when attributing a failure or saving settings. A fresh UI process discards transient attribution and reconciles from saved settings. It schedules retirement of a leftover comparison on the monitor thread rather than waiting before listening. **Known limitation:** that thread can still hold the connector lifecycle lock for 35 s (up to 70 s if termination must escalate); a start, stop or page change may answer busy during retirement. A genuine Owner change to the field under comparison takes priority. The page waits up to 75 s for the cancelled replica to retire. For any page network change whose resulting protocol is automatic, try the preferred transport, then fall back to the explicit opposite. If there is no preference, choose the last observed transport, otherwise HTTP/2, for the first trial. After the promoted generation passes public verification, remember its actual explicit transport for later starts; a failed or unverified candidate sets no preference. If an Owner edit ends without a write or promotion, or a failed promotion leaves the old settings back on disk and the same temporary generation online, start a fresh comparison only after checking the pairing, start request, saved pins and positive registration. A busy lifecycle lock may defer this check, but not the failed edit's outcome. An effective Owner change does not requeue comparisons. The cancelled writer never regains authority.

## Release and evidence

| Budget | What the measurements establish |
| --- | --- |
| 30 s to register a recovery candidate | In three account-free IPv4 quick tunnels with UDP/7844 blocked and TCP available, explicit HTTP/2 registered in 6.379–8.030 s. Literal `auto` registered in 94.049–130.789 s: each run logged nine QUIC dial failures (including the first dial), followed by an HTTP/2 fallback and registration. The totals include temporary-tunnel allocation. This tests transport selection, not paired Owner access or IPv6 failover. |
| 8 s to obtain full HA on preferred-transport startup | First registration is not four ready connections. In the paired switchover exercise, first observing a candidate to observing promotion took 4.317 s for HTTP/2 and 4.162 s for QUIC. Those intervals include polling and promotion; neither measures cold-start time to four connections. The deadline tests model that boundary, not a guarantee. |
| 35 s stop grace on Unix; Windows terminates first | In the paired HTTP/2 and QUIC changes, promotion to observed old-process exit took 0.345 s and 4.037 s. The 35 s Unix budget is for graceful stop before escalation, not an upper bound on the whole operation. Windows stop behavior follows the implementation; not measured on Windows. |
| 12 s for public verification after drain | A controlled Incus HTTP origin returned success on attempt three at 10.821 s; at 12.006 s the check failed. In the paired exercise, drain-record removal to verified took 0.571–0.693 s including bookkeeping, not a measurement of any individual public request. |

The paired recheck must distinguish automatic recovery **while the UDP fault remains** from reconnection after removal. Separately exercise a promoted, drained connector whose own public check fails, and verify restoration without blocking the Owner's independent path. IPv4-to-IPv6 fallback remains unmeasured on an IPv4-only guest.
