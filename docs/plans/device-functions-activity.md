# Device functions and activity: backend contract for the Devices page

Status: rule table incorporating the build lead's decisions; pending independent rule review. No routes shipped by this document. Base: registry #4080 (`daeb126b3`); views compared at `c5e703e18` (#4084). Scope: instance-local routes/stores, no page wiring, native UI or control-plane changes.

## Proposed wire contract (not implemented)

* `GET /api/devices` keeps #4080's keys and adds `unlinked_health: UnlinkedHealth[]`. Unproven pairings are **not** functions of any device. `UnlinkedHealth` has `pairing_id` (opaque resource ID, never a code or credential), `device_name`, `platform:'ios'`, `last_seen_at` and `data` (synced kinds). An optional OS version comes only from the phone's manifest. Verify the current instance Health owner (personal and organization instances alike). Compute the split in one request from the same live registry snapshot as the device list: current binding, `cookie_exp > now`, `expires_at > now`, no revocation tombstone. `POST /api/devices/unlinked-health/{pairing_id}/revoke` repeats the same authorization and rechecks under the mutation lock that **no currently listed live device row reaches this pairing**, not merely that no historical link exists. It then purges only this pairing. Device sign-out cannot purge or promise to purge these rows. Preserve #4080's existing `capabilities.push_enabled`; add `functions: DeviceCapability[]` for the new container. Locale-neutral entries: `{kind:'notifications',on}`, `{kind:'health',on,data:HealthData[],syncedAt?:ISO8601}`, `{kind:'schedule',on}`, `{kind:'computerUse',on:boolean|null,fixed:true,status:'ready'|'needs_permission'|'off'|'unavailable'}`. `on` for computer use means verified opt-in, not necessarily readiness. Don't synthesize unsupported functions. Unproven Health association is not evidence that a phone has never synced.
* `PUT /api/devices/{id}/notifications`, `PUT /api/devices/{id}/schedule`: JSON `{on:boolean}`; return effective `function`. `GET /api/devices/{id}/health` returns only the Health entry; `POST /api/devices/{id}/health/revoke` returns the disconnected Health entry. No Health enable and no Computer Use write. Use existing CSRF and role policy; `404` for invisible/nonexistent target, `403` for a visible non-owned target, `409` when on-device enrollment/proof is needed. Typed errors only.
* `GET /api/devices/activity?limit=&cursor=&device_id=` and `GET /api/devices/{id}/health/reads?limit=&cursor=` return `{items,next_cursor}` with the same auth and order (suggest default 25, max 100). Each entry: `{id,at,device_id,kind,...}`; `at` UTC ISO, IDs opaque. `signedIn`; `signedOut` with nullable `actor_device_id`; `healthRead` with `data`, `from_day`, `to_day` and policy-dependent optional `task`; `alarmCreated`/`reminderCreated` with `confirmed` and device-owner-only optional `label` (never a system identifier); `remoteAccessOn`/`remoteAccessOff` with actor device but no host address. No backfilled invented events.

## Native Health binding ticket (iOS wire contract)

1. Native sends `POST /api/mobile/device/v1/binding-ticket` over its existing Health transport with its normal `Authorization: Bearer …`, `Content-Type: application/json`, body `{}`. No cookies, caller-selected pairing ID, account or installation. `200 {"health_binding_ticket":"<opaque base64url>","expires_at":"<UTC RFC3339 instant>"}`; `Cache-Control: no-store`. The ticket is 32 random bytes, unpadded (43 ASCII base64url characters), valid for **120 seconds** from issuance. Persist SHA-256 only, scoped to the authenticated active pairing, instance and binding. At most one outstanding per pairing: a later successful issue supersedes the preceding ticket. At most one issue every 30 seconds per pairing; `429 binding_ticket_rate_limited` with `Retry-After: 30`; a rate-limited request does not replace an outstanding ticket. Existing device API error envelope `{ok:false,code,error}` with fixed codes: `401 device_unauthorized`, `403 device_revoked|instance_not_eligible`, `413 invalid_payload`, `422 invalid_payload`, `503 instance_eligibility_unavailable|private_storage_unavailable`; no echo of Bearer, ticket, IDs, owner, metrics or submitted fields. An old tunneled instance may answer `401 {"ok":false,"error":"remote_access_login_required"}` without `code`: its cookie gate does not know this native path. Other old routes/proxies may return 404/405/503. All are a missing ticket only.
2. Only explicit `device.describe({health_binding:true})` may request proof; an argumentless call returns normal metadata immediately and makes no ticket request. The reporting page alone opts in, takes the ticket out of the response before ordinary metadata caching, submits it once and forgets it. Native budget: one request, at most three seconds, verify expiry and recheck the active foreground WebView, pairing, instance and account after the await. Native treats **every** binding-ticket error, including 401/403, as “no ticket this time”. Issuance cannot trigger local disconnect or change sync state/backoff; Health's own sync requests discover revocation. Never retry automatically. A 404 suppresses further issuance attempts for this instance for this process lifetime. Native may return `health_binding_ticket` **only** in a foreground `device.describe` reply to the trusted same-instance, same-current-account WebView while Health is connected. Hold ephemeral ticket in memory; do not persist, emit on bridge broadcasts, send to the control plane, put in a URL, telemetry or logs. Never return the Health credential. Omit the property on account switch, disconnect, unavailability or expiry (not `null`).
3. WebView sends the ordinary #4080 `POST /api/devices/self` same-origin JSON + session + CSRF; the only extra property is optional `health_binding_ticket: string` for `kind:'iphone_app'`. No separate client-selected target: derive the logical device from signed binding, signed subject and the description's installation ID. Without the property behavior/response stays unchanged. With it: `200 {"ok":true}` only after validating the live session, same current Health owner + instance/binding, active pairing, unexpired unused ticket, and no competing association. Atomically consume the ticket and bind only to this installation. A fresh ticket for the same device may succeed; an existing association is never moved. An orphaned association stays individually disconnectable under `unlinked_health`. Check current remote owner role, verified session email against pairing owner, and session instance ID against pairing instance ID; redemption does not invoke live control-plane Health policy or its bulk-revoke side effect. A failed redemption does not promote the session or change any association. Concurrent redemption may succeed once only. An old server rejecting the optional property as `400 invalid_device_description` can receive an ordinary **ticketless** description once; no Health attachment is inferred.
4. Browser errors `{error:code}` (existing auth/CSRF errors unchanged): malformed description or ticket syntax `400 invalid_device_description`; missing remote session `403 remote_session_required`; unknown, expired, spent, superseded, mismatched or already-linked-elsewhere proof `403 health_binding_not_accepted` (one indistinguishable refusal); unenrolled/stale target `404 device_not_found`; changed installation `409 installation_mismatch`; normal changed-description debounce `429 device_report_rate_limited`; ticket checks limited to five per minute per live SID `429 health_binding_rate_limited` (`Retry-After: 60`); storage unavailable `503 health_binding_unavailable`. No IP-based counters. On `403 health_binding_not_accepted` a client may submit the ordinary description once **without the ticket** (optional, distinct from retrying proof); never retry a failed token automatically. Report-level 404/409/429 leave the ticket unconsumed. An identical description with a fresh ticket is not throttled by metadata debounce. No title, OS diagnostics, pairing ID or health content in the exchange.

## Integration constraints and decisions

1. Published #4080 aliases are **explicitly not ownership evidence**, and no shipping client on master calls `/api/devices/self`. Existing Health device records have private `id`, `installation_hash`, instance ID and **owner email**; preexisting `accesses` rows have **no mobile device ID, subject or binding**. Record the actual private mobile ID in the original Health read audit transaction. Never infer it from pairing lifetime: the pairing timestamp can precede acquisition of its write transaction while a read still selects the previous phone. Existing and rollback-written audit records lack proof and are never assigned retrospectively. The unlinked list and individual disconnect are the upgrade path; there is no guessed match. The native binding-ticket protocol above is the only legacy attachment path; no web challenge or signing with the credential hash. App integration, including the WebView report opt-in, one-shot ticket forwarding and ticketless fallback, belongs to the iOS lane after #4086. Keep targeted revoke from deleting unrelated pending codes; all-device revoke retains its blanket deletion. Cancel scoped outstanding requests at sign-out. The main registry DB (revision 0095) owns ticket hashes, throttle counters and authoritative associations. Redeem, revalidate the live session, update its reported installation and persist the association in one main-DB transaction; the private store supplies current pairing state, never a cross-database commit. A concurrent private revoke wins: an association cannot make a revoked pairing active. The private DB stays at `user_version=1`. Under its existing migration lock, idempotently add only nullable `accesses.device_id`; predecessor `_audit` uses explicit columns, leaving this field null. Exercise v1 → current → actual v1 read/write/cleanup and new installations. Health connection is owner-only; normally there is one pairing, but the CLI's separate status and creation transactions do not guarantee that under concurrency. Account for every eligible active pairing.
2. Schedule `create_operation()` has no target, `claim_next()` binds the first eligible phone using its submitted installation ID; operation rows have no account/registry key. No source can definitively enumerate every future eligible phone. Enforce at claim, not creation. Do not add a target to the Agent contract. Use known schedule-capable, authenticated devices to explain all-off in Agent status; an unseen future device is not grounds to reject creation.
3. #4084 uses a capability array, #4080 uses an existing object. The page adapter must map the additional `functions` field. `computerUse.on` alone cannot express missing permission vs unavailable; views also lack `remoteAccessOff`, `reminderCreated`, sign-out actor, exact Health range, and expect alarm labels/remote host strings. `healthConnected` and `directOn` are not requested backend events. Do not emit fabricated events, a location/host, synthetic labels or a fake boolean. The page lane will use structured kinds and the title privacy rule above.
4. `enabled=0` covers signed-out, invalid, replaced, manually unregistered and superseded registrations. The notification switch does **not** write that field. Current delivery = valid, enabled subscription and no matching per-device pause.
