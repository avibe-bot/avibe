# Device functions and activity: backend contract for the Devices page

Status: rule table incorporating the build lead's decisions; pending independent rule review. No routes shipped by this document. Base: registry #4080 (`daeb126b3`); views compared at `c5e703e18` (#4084). Scope: instance-local routes/stores, no page wiring, native UI or control-plane changes.

| Actor / action | What would be lost or disclosed | Rule | Acceptance check |
|---|---|---|---|
| Remote person lists rows, reads status or changes a switch | Another person's device state | Use the registry's current binding, authenticated subject, live session and current role; recheck under the write lock. Members see only `mine`. Owners can inspect `others`, **not** change functions there. Unattributed rows are never theirs. Direct paired loopback has no signed subject; the registry's owner-at-login display grouping is not current ownership proof. Allow remote-device switches there only with independent current-owner proof; otherwise require a signed session. No mutation from setup LAN. | Two subjects in the same binding, same reported aliases/name; separate binding with same subject. Direct lookup, list, projected activity, cursor, and mutation must agree. Demoted Owner has no stale access. Owner can still use the distinct sign-out action. |
| Person switches notifications on own device | New delivery stops; sign-out and provider invalidation must not be undone | Off pauses only verified subscriptions for that logical device, and stays off across normal sync/rotation; on resumes only still-valid registrations paused by that switch. It cannot grant OS permission, recreate an endpoint, or revive a registration separately revoked/superseded. Return a typed reason if enrollment on-device is needed. Preserve disabled-but-resumable proven push-only row as an own visible target. | Disable A while B receives; refresh/rotate A while off; enable and list; invalidate or sign out A while off and check that on cannot restore the old subscription. Every enabled subscription remains reachable, including owner-only legacy buckets. |

Expose only connected, consented kinds, latest successful sync; no enable route. Canary values/errors never enter these routes/logs. A member cannot adopt the Owner's phone via self-report. |

Binding-scoped owner sees instance transitions; member sees events on own devices. No cross-account actor details for members (redacted actor ref when necessary). | Idempotent retry, single/bulk/self, owner ending a member’s session, remote access restart without a state change. ## Proposed wire contract (not implemented)

* `GET /api/devices` keeps #4080's keys and adds `unlinked_health: UnlinkedHealth[]`. Unproven pairings are **not** functions of any device. `UnlinkedHealth` has `pairing_id` (opaque resource ID, never a code or credential), `device_name`, `platform:'ios'`, `last_seen_at` and `data` (synced kinds). The private store does not record the OS version; don't synthesize one. Show these only after current personal-instance Health owner verification. `POST /api/devices/unlinked-health/{pairing_id}/revoke` repeats the same authorization and revalidates that this pairing remains unlinked, then purges only it. Device sign-out cannot purge or promise to purge these rows. Preserve #4080's existing `capabilities.push_enabled`; add `functions: DeviceCapability[]` for the new container. Locale-neutral entries: `{kind:'notifications',on}`, `{kind:'health',on,data:HealthData[],syncedAt?:ISO8601}`, `{kind:'schedule',on}`, `{kind:'computerUse',on:boolean|null,fixed:true,status:'ready'|'needs_permission'|'off'|'unavailable'}`. `on` for computer use means verified opt-in, not necessarily readiness. Don't synthesize unsupported functions. Unproven Health association is not evidence that a phone has never synced.
* `PUT /api/devices/{id}/notifications`, `PUT /api/devices/{id}/schedule`: JSON `{on:boolean}`; return effective `function`. `GET /api/devices/{id}/health` returns only the Health entry; `POST /api/devices/{id}/health/revoke` returns the disconnected Health entry. No Health enable and no Computer Use write. Use existing CSRF and role policy; `404` for invisible/nonexistent target, `403` for a visible non-owned target, `409` when on-device enrollment/proof is needed. Typed errors only.
* `GET /api/devices/activity?limit=&cursor=&device_id=` and `GET /api/devices/{id}/health/reads?limit=&cursor=` return `{items,next_cursor}` with the same auth and order (suggest default 25, max 100). Each entry: `{id,at,device_id,kind,...}`; `at` UTC ISO, IDs opaque. `signedIn`; `signedOut` with nullable `actor_device_id`; `healthRead` with `data`, `from_day`, `to_day` and policy-dependent optional `task`; `alarmCreated`/`reminderCreated` with `confirmed` and device-owner-only optional `label` (never a system identifier); `remoteAccessOn`/`remoteAccessOff` with actor device but no host address. No backfilled invented events.

## Integration constraints and decisions

1. Published #4080 aliases are **explicitly not ownership evidence**, and no shipping client on master calls `/api/devices/self`. Existing Health device records have private `id`, `installation_hash`, instance ID and **owner email**; preexisting `accesses` rows have **no mobile device ID, subject or binding**. True historical attribution and guaranteed targeted sign-out of existing pairs cannot both be delivered by a read-only projection. Propose recording scoped link at pairing issuance/redemption and `device_id` on future read audit writes, and a credential-backed authenticated attachment on-device for existing pairs. Unproven legacy history stays absent when binding/subject cannot be proven. The unlinked list and individual disconnect are the upgrade path; there is no guessed match. For native proof, a signed-in iPhone asks for a short-lived, one-use challenge tied server-side to its exact session, binding, subject and logical device. Only native code uses the existing authenticated Health-device channel to redeem that nonce for its active pairing, never disclosing its Health credential to the WebView or to any registry route. Recheck that the same session remains live and the association is still unclaimed; deny cross-binding, replay and signed-out challenges. App integration is a separate lane. Targeted `MobileStore.revoke(device_id=…)` currently deletes *all* pending pairing codes; narrow only the targeted path and keep CLI-wide revoke intact. Private schema `user_version>1` currently fails on downgrade; design additive nullable columns with explicit upgrade/rollback tests.
2. Schedule `create_operation()` has no target, `claim_next()` binds the first eligible phone using its submitted installation ID; operation rows have no account/registry key. No source can definitively enumerate every future eligible phone. Enforce at claim, not creation. Do not add a target to the Agent contract. Use known schedule-capable, authenticated devices to explain all-off in Agent status; an unseen future device is not grounds to reject creation.
3. #4084 uses a capability array, #4080 uses an existing object. The page adapter must map the additional `functions` field. `computerUse.on` alone cannot express missing permission vs unavailable; views also lack `remoteAccessOff`, `reminderCreated`, sign-out actor, exact Health range, and expect alarm labels/remote host strings. `healthConnected` and `directOn` are not requested backend events. Do not emit fabricated events, a location/host, synthetic labels or a fake boolean. The page lane will use structured kinds and the title privacy rule above.
4. Turning on notifications needs proof that an otherwise usable registration was paused by this switch; `enabled=0` alone also covers signed-out, replaced, manually unregistered and superseded registrations. No enable-by-flipping-all-disabled-rows. For server-side resumption distinguish switch pause from independent invalidation and keep proven paused rows addressable.
