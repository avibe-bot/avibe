# Instance device registry

One visible device can represent several signed sessions. A session belongs to one cookie-signing instance binding and one signed subject. Group by a reported installation ID, else a linked push device ID, else the session. Neither a name, kind, user agent, IP address nor an email identifies a device for authorization.

| Actor and action | Rule / what would be lost |
| --- | --- |
| Direct loopback lists or signs out devices | A paired instance trusts direct loopback, never a forwarded request or LAN setup, as its owner. With no account, group host and owner-at-login devices as mine. For an older cookie the role is only known at first verified enrollment, not at original login. Unpaired loopback/setup LAN lists only host and has no mutation. |
| Remote user lists or signs out devices | Use **current** authorization: owner within its binding, all others within their signed subject. A login-time owner role must not let a demoted member sign out the owner. Host is synthetic, never a session. |
| Client supplies device metadata | OAuth supplies only the user agent. The authenticated self-report can promote its own session to installation scope. An untrusted report can affect grouping only within that binding and subject, never grant a role, select another subject, or authorize a Health/schedule resource. Reported aliases are matching hints, not evidence of ownership. |
| An owner or member signs out one logical device | Target the opaque ID and revoke the whole matching group. Write existing SID tombstones to the absolute cap, then publish the existing event after commit. If the caller's SID is in the group, delete its cookie and suppress response renewal. |
| A remote caller signs out others; loopback signs out all remote devices | Remote preserves the calling SID and all other subjects. Direct loopback exempts no remote SID. Write per-SID tombstones for enrolled sessions through their absolute cap **and** a subject/instance cutoff to cover unregistered old cookies. A raced renewal cannot restore them. See rollback below. |
| A device has Push | Join enabled subscription by `(remote:<subject>, push_id)` learned on authenticated foreground subscription/sync. Explicit device sign-out disables associated subscriptions transactionally, unless a surviving session still shares one. A fenced registration cannot re-enable delivery. Subscriptions never linked to an enrolled session cannot be attributed to a target. |

## HTTP contract

- `GET /api/devices` → `{mine: Device[], others: Device[], bulk_action: "other_sessions" | "all_remote" | null}`. Host is first for owners. Fields: `id`, `kind`, `display_name`, `account: {subject,email,login_role}|null`, nullable `app_version`, `system_version`, `signed_in_at`, `last_active_at`, `current_path: {kind,family,rtt_ms}|null`, `current`, `capabilities: {push_enabled}`. Timestamps are Unix seconds. List eligibility and `revoked_sessions` use the most recently issued cookie's idle expiry; a browser's local deletion is unobservable. Raw session/installation/push IDs and aliases are not returned.
- `POST /api/devices/{id}/sign-out` and `POST /api/devices/sign-out-others` → `{ok:true, revoked_sessions:N}`. IDs can change at first stable identification: refetch on 404. These are instance-local operations, not account-service logout.
- `POST /api/devices/self` with normal same-origin session/CSRF and JSON `{kind,display_name,installation_id,aliases:[{source,id}],app_version,system_version}` → `{ok:true}`. App supplies an instance-scoped identifier, not a relay credential. Accepted `health` aliases are stored as SHA-256; `schedule` as an ID. Unknown sources ignored; unknown fields rejected. No capabilities are consumed or granted here. A missing enrolled row gives 404, a conflicting installation ID 409, and a changed report within 60 seconds of another change 429. An unchanged report is a no-op.

## Upgrade and rollback

The schema is additive and migration signs nobody out. A pre-upgrade cookie can be enrolled only after successful verification. On this version and successors the cutoff rejects old cookies even if unregistered at sign-out. On rollback to a predecessor that does not recognize the cutoff, enrolled SIDs remain tombstoned. Only pre-upgrade cookies **not successfully verified and enrolled at sign-out** can be accepted again, including cookies first presented after the cutoff and rejected. The first acceptance window is their original idle lifetime (Personal: 30 days; Organization: 7 days since last renewal). After one uninterrupted idle lifetime on the upgraded binary, no such usable cookie remains. After an earlier rollback, an admitted predecessor session may slide to its original absolute cap. This is not unconditional rollback enforcement.
