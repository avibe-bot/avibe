# Instance device registry

One visible device can represent several signed sessions. A session belongs to one cookie-signing instance binding and one signed subject. Group by a reported installation ID, else a linked push device ID, else the session. Neither a name, kind, user agent, IP address nor an email identifies a device for authorization.

| Actor and action | Rule / what would be lost |
| --- | --- |
| Direct loopback lists or signs out devices | A paired instance trusts direct loopback, never a forwarded request or LAN setup, as its owner. With no account, group host and owner-at-login devices as mine. For an older cookie the role is only known at first verified enrollment, not at original login. Unpaired setup LAN lists only host, with no mutation. Unpaired direct loopback can also list and individually disable a remaining push registration, never sign out host or perform a bulk action. |
| Remote user lists or signs out devices | Use **current** authorization: owner within its binding, all others within their signed subject. A login-time owner role must not let a demoted member sign out the owner. Host is synthetic, never a session. |
| Client supplies device metadata | OAuth supplies only the user agent. The authenticated self-report can promote its own session to installation scope. An untrusted report can affect grouping only within that binding and subject, never grant a role, select another subject, or authorize a Health/schedule resource. Reported aliases are matching hints, not evidence of ownership. |
| An owner or member signs out one logical device | Target the opaque ID and revoke the whole matching group. Write existing SID tombstones to the absolute cap, then publish the existing event after commit. If the caller's SID is in the group, delete its cookie and suppress response renewal. |
| The same browser signs in again | Only a successful fresh callback (both handshake paths, PKCE, nonce, new claims) may replace a session, and only the one its own session cookie on that request proves: verified with the current secret, current, same subject. Under the write lock, with the clock read after it, the binding must not be retired (else the login is refused, not downgraded), the cookie's own deadline (its `exp`, or `iat` + the organization limit) must not have passed, and that exact binding/subject/SID row must be live, untombstoned and unfenced; otherwise it is an ordinary new login. The new SID must be recorded under its own id and its account reference admitted, or nothing is issued. Then, in the same transaction, the new session takes the device fields (`device_id`, `identity_source`, `push_id`, `described_at`, Health and schedule aliases; reported name, kind and versions only from an installation report), the old SID's own proven push links (with this login's email and role; never another SID's or an unproven one; a stopped subscription stays stopped) and the Health ticket counters. The schedule principal, account reference and unused Health codes are not taken: the codes stay with the old SID and are queued codes-only, and a later full unpair of the device takes them too, never lowering a full intent. The old SID is tombstoned to its absolute cap and deleted; its revocation event is published after commit. No push stop, Health unpair, settings change, account sign-out or `signedOut` activity. Two callbacks carrying the same old cookie replace it once; the second is a new row. Native Desktop sign-in carries no old cookie and is not covered. |
| The owner signs out a session that has no account reference | A session signed in before this instance recorded account references (everything from 3.2.7) cannot have its avibe.bot sign-in ended at sign-out. The owner's own "sign out this device" (single or bulk, here or remote) marks each registered session it ends that has no account reference, beside its tombstone and for as long. At that browser's next sign-in, after the existing refusals (retired binding, handshake deadline) and only when avibe.bot vouches the account as this instance's owner (its reference is only issued for the owner), the registry write transaction uses the mark once, queues avibe.bot's sign-out of that exact account session (an existing job is never restarted; a refused pairing writes the digest without sending), records no session, and the callback answers the existing signed-out page and clears the cookie. The tombstone stays. Not a forced re-authentication: no mark, a used mark or a non-owner account is today's sign-in. Known limits: someone who signed in again by hand after the sign-out is refused once and that sign-in is ended; Desktop's native sign-in carries no old cookie; cleared or never-returning browsers simply expire. |
| A remote caller signs out others; loopback signs out all remote devices | Remote preserves the calling SID and all other subjects. Direct loopback exempts no remote SID. Write per-SID tombstones for enrolled sessions through their absolute cap **and** a subject/instance cutoff to cover unregistered old cookies. A raced renewal cannot restore them. See rollback below. |
| A device has Push | Every enabled subscription is reachable from a device row, even with no live cookie and beyond its absolute lifetime. Foreground registration/sync or authenticated rotation attests a specific subscription ID to the current binding and subject. A member can see/stop only attested registrations belonging to their subject. Local and legacy registrations without current proof are owner-only, even on a matching old user key; treating an old binding as a current identity could expose or disable another person's device. Group these separately by stored user key and push device ID, else by subscription row ID; no endpoint or key is returned. Sign-out disables applicable registrations transactionally unless a surviving session shares one. A registration that races sign-out cannot re-enable delivery. |

## HTTP contract

- `GET /api/devices` → `{mine: Device[], others: Device[], unattributed: Device[], bulk_action: "other_sessions" | "all_remote" | null}`. Host is first for owners. Fields: `id`, `group: "mine"|"others"|"unattributed"`, `kind`, `display_name`, `account: {subject,email,login_role}|null`, nullable `app_version`, `system_version`, `signed_in_at`, `last_active_at`, `current_path: {kind,family,rtt_ms}|null`, `push_only`, `current`, `capabilities: {push_enabled}`. For proven push-only rows, the attestation retains the signed account and its role at login/legacy enrollment even after the cookie expires. A push-only row without current binding proof has no account and is always `unattributed`, never a presumed owner's device. Unknown `display_name` is null; the client can label the kind in its own language. Timestamps are Unix seconds. Session visibility and `revoked_sessions` use the latest issued cookie's idle expiry; enabled push remains visible independently until disabled. Stopping push can succeed with zero revoked sessions. A browser's local deletion is unobservable. Raw session/installation/push IDs and aliases are not returned.
- `POST /api/devices/{id}/sign-out` and `POST /api/devices/sign-out-others` → `{ok:true, revoked_sessions:N}`, with the per-device results (including each one's `group`) described in [device sign-out and the account session](device-account-session-sign-out.md). IDs can change at first stable identification: refetch on 404. These are instance-local operations, not account-service logout.
- `POST /api/devices/self` with normal same-origin session/CSRF and JSON `{kind,display_name,installation_id,aliases:[{source,id}],app_version,system_version}` → `{ok:true}`. App supplies an instance-scoped identifier, not a relay credential. Accepted `health` aliases are stored as SHA-256; `schedule` as an ID. Unknown sources ignored; unknown fields rejected. No capabilities are consumed or granted here. A missing enrolled row gives 404, a conflicting installation ID 409, and a changed report within 60 seconds of another change 429. An unchanged report is a no-op.
- Desktop app (`desktop_app`): its native requests, the instance's `/auth/callback` included, carry `User-Agent: AvibeDesktop/<package version>`, which labels the sign-in at enrollment. Only the committed view of another computer's instance is described, and only while its top document is at one of the Workbench's own routes (`ui/src/lib/applicationRoutes.ts` without its catch-all); a candidate or retired view, an account page, a frame, a Show page, an app window or any other document of the instance gets nothing. The shell re-checks this whenever it publishes state to the view and when each of its documents loads, and the delivered script re-checks origin and route in the receiving document; it defines a frozen `window.__AVIBE_DESKTOP_DEVICE__` and fires `avibe:desktop-device`, so a Workbench mounted before the commit reports at publication. The description holds the computer's name, `installation_id` derived per instance origin from a random seed kept in the app's local data (not the credential store), app version, system version and `aliases: []`. The Web UI reports it through this endpoint, without a Health ticket, so every sign-in of one installation to the instance is listed as one computer. Sign-ins recorded before a report, and earlier unnamed browser rows, are not regrouped by name or User-Agent.

## Current path

`current_path` is a live observation, not a last-used route. A signed-in remote Workbench event stream observed outside direct ingress is evidence for `tunnel` (null family and RTT) only while subscribed. A selected direct connection takes precedence. IP paths report `lan` or `punched` with family `ipv4`/`ipv6`; a relayed connection reports `relay` with null family. RTT is in milliseconds when available. Without evidence the API returns null, including for host and push-only rows. A valid cookie or a recent request is not proof of a tunnel.

The authenticated rendezvous session associates a peer with an admission in memory. The registry joins observations only to visible, unrevoked sessions in the same pairing; no session key, peer ID or address is added to the device response. No database migration or disk write is required. Older sidecars keep their existing diagnostics and cannot populate a direct path.

## Observation protocol (instance and sidecar)

Only a negotiated v2 sidecar receives an `epoch` on its private admission notices. A positive epoch labels an unambiguous session association; zero means do not attribute. It is not an admission credential. Capture the epoch **once at connection admission** and echo that value on every observation for the connection, never the latest value for its peer. An overlapping nomination from a different session drops both sessions’ attribution for the rest of the continuous admission. Renewal never resolves the conflict, even after the first nominator’s deadline passes. Only after the key leaves admission can a fresh nomination receive a new positive epoch; delayed reports from an older grant, including opens and closes, cannot affect it.

A v2 observer must refresh even an unchanged selection at least every five seconds. A measurement expires ten seconds after receipt; renewing an admission does not refresh it. Loss of the diagnostic channel clears its observations without shutting down transport. The API can then show an independently observed tunnel, or null.

## Upgrade and rollback

The schema change is revision `20261120_0094`, following Live Activities (`20261120_0093`). It adds registry tables and indexes without changing existing Live Activity or Push subscription rows. The schema is additive and migration signs nobody out. A pre-upgrade cookie can be enrolled only after successful verification. On this version and successors the cutoff rejects old cookies even if unregistered at sign-out. On rollback to a predecessor that does not recognize the cutoff, enrolled SIDs remain tombstoned. Only pre-upgrade cookies **not successfully verified and enrolled at sign-out** can be accepted again, including cookies first presented after the cutoff and rejected. The first acceptance window is their original idle lifetime (Personal: 30 days; Organization: 7 days since last renewal). After one uninterrupted idle lifetime on the upgraded binary, no such usable cookie remains. After an earlier rollback, an admitted predecessor session may slide to its original absolute cap. This is not unconditional rollback enforcement.
