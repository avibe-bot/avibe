# Agents graph: what a history statement measures

Both views use the same `histories` phase **after** the visible session cap. In a slow server log, `history_statements` groups the original executions by fixed label: `statements` counts executions (including parameter batches with no hits); `batches` counts nonempty fetchmany results (up to 512 rows each); `rows` counts rows actually consumed, not cursor rowcount or a planner estimate. `execute_ms` clocks SQLAlchemy execute, `fetch_ms` clocks fetchmany, including its final empty fetch when exhausted. Neither clocks the Python consumer, includes an EXPLAIN, or executes a query again. Neither measures bytes or isolates disk latency. No SQL, binds, records, IDs, or filters in these fields. No per-statement metrics in the response. Labels with zero executions are absent.

## Reading the bounds

Let **V** be the number of visible sessions (normally ≤300), **T** the number of actual timeline entries (≤10V, normally ≤3,000), **R** the total retained runs of those sessions (unbounded), and **W** the number of nonempty visible lineage waves (≤V). Counts below sum over disjoint visible waves, except the one graph-wide totals query and cached schema probe. `b(x)` means ceil(x / min(2,000, available SQLite bind slots)), zero for an empty list; reserve slots for other predicates as indicated. For 300 sessions with exactly ten stored runs each, R=T=3,000. For 300 sessions *showing* ten each, R need not be 3,000. A miss can return zero and still do index/table work. Plans, not the counters, establish access paths; visits below describe the selected keys, not measured page counts.

| Fixed label | Returned columns and why | Executions and rows consumed | Index/table work, including misses |
|---|---|---|---|
| `run_totals` | session_id, raw status, count: exact total/running badges, normalized nonterminal status | `b(V)` statements; one row per distinct (session,status), ≤R, not bounded by a fixed status vocabulary | Covering session/status seek/group, **all R status keys** |
| `spawn_endpoints` | rowid, source_actor: parent→child existence, exact full-history count and winner | Each source batch × visible target batches per wave (usually 1 per wave); one per matching agent child, up to R | Covering `(source_kind,session_id,source_actor)` seeks, including misses; endpoint combinations can be V², even when few match |
| `callback_endpoints` | rowid, callback_session_id, callback_status: who can draw which callback; sent proves drawable without JSON | Same batching as spawn; up to R returned. Null/empty status not returned | Covering `(session_id,callback_session_id,callback_status)` seeks and status checks; a match need not be drawable |
| `all_timeline_times` | rowid, session_id, created_at: order timeline and edge evidence | All-short wave (each has ≤10 runs): `b(wave size)`, ≤10 per visible session | Covering session/created seek, all rows in these **short** histories |
| `timeline_bounds` | session ID, JSON array of **created_at only**: ten witnesses give a safe lower bound, not the chosen timeline | One statement per wave containing any long sessions; one result per long session (≤300), each with 10 raw strings (≤3,000 strings) | Correlated, bounded descending seek on session/created **inside one SQL**, no per-session round trips |
| `time_candidates` | rowid, session_id, created_at: exact parsed ranking, all boundary/raw-max ties, all visible endpoint times | One per mixed/long wave; returns all short-session rows plus distinct long-session keys meeting floor, nonstandard-spelling or endpoint predicate. Up to R, not 3,000 | Covering session/created index; **visits all time keys in these visible sessions**, not all table records. Internal JSON bind of matched endpoint rowids is linear in distinct endpoint runs, not bounded by V. No such values logged |
| `trigger_runs` | rowid, session_id, created_at, definition_id: exact in-window scheduled/watch counts and most recent fire per definition/session | `b(long sessions)` per wave, reserving one bind; only nonempty-definition scheduled/watch rows in the raw range returned (up to R); parsed cutoff then checked | Session/created **range** seek. Type and definition are not covered: can check the table for **every raw-window run in these sessions**, including human runs, even with zero hits. Does not hydrate their other fields |
| `trigger_exceptions` | rowid, definition_id: same evidence for unusual offsets/spellings below raw floor but parsed inside window | Rowid batches (3 slots reserved) of those exceptions in long sessions; 0 to number of candidates returned | One integer PK probe per such candidate. Short sessions already have all heads |
| `callback_tie_ids` | rowid, id: descending real ID breaks equal parsed instants before any mode check | `b(tied candidates)` per wave; only ties not strictly older than newest known sent in pair; up to R | Integer PK probes of ID, not JSON/other header fields |
| `callback_modes` | rowid, `json_extract(metadata_json, '$.callback_mode')`: exclude failure-only notices unless sent | Per pending-pair round, `b(unsent in lookahead)` (one slot reserved); widths 1,2,4,…,64 across pairs. No mode query for sent. Up to R unsent rows if all must be disproved | Integer PK probes, but reading JSON can traverse table overflow. Stops at winner, subject to bounded lookahead. Does not return whole metadata |
| `run_headers` | rowid, id, status, run_type, definition_id: timeline fields, newest terminal outcome, edge identity and true trigger type | `b(union of needed rowids)` per wave. At exactly 3,000 stored/displayed: 3,000. Otherwise timeline + boundary ties, raw-max ties (legacy edge insertion order), newest spawn/trigger ties and drawable callback winners; ≤R, ties/definition count unbounded | Integer PK probes only on selected rows. No source_actor, session_id, created_at or callback columns read from this table projection |
| `timeline_index_probe` | literal 1: determine whether snapshot has the timestamp covering index | Once per request with any timeline rows, returns **0 or 1** | Schema catalog lookup/scan; no run rows. No DDL or retry |
| `timeline_timestamps_covered` | id, started_at, completed_at (including NULL): actual timeline entries, including old-writer changes | `b(timeline rows)` per wave; T returned (3,000 usually takes 2 statements in one wave) | Forced covering `ix_agent_runs_timeline_times` ID seeks. No table read; *already covering in rc15* |
| `timeline_timestamps_fallback` | Identical columns/semantics, only when probe misses | Same counts as covered; mutually exclusive for the snapshot | Unique ID index + table lookup; trailing timestamps can require overflow reads |
| `callback_delivery_ids` | rowid, callback_run_id: callback edge links to delivery run, falling back to source run ID if absent | `b(winners)` per wave, exactly one row per drawable pair, ≤min(R,V²), at most 90,000 at V=300 | Integer PK lookups; trailing field can require overflow even if NULL |

The table describes plans on the normal migrated schema. Neither long-session query requires the session/created index to exist: SQLite can choose a slower plan on a compatible snapshot without it, with the same ordered result. The timestamp query only forces its own covering index after checking presence in the same snapshot.

Endpoint source batches reserve one bind and at most half the remaining slots for source IDs; each target batch uses the remaining slots. There is no one-statement-per-node loop. The ten-row cap is **not** a cap on counts, historical pairs, distinct trigger definitions, retained equal instants, imported time spellings, failure-only callback evidence, or visited keys. Lineage discovery (including its own conditional callback predicate), candidate selection, trigger *definition* hydration and post-query assembly have separate stage accounting; they are not additional history SQL shapes.

## Why the time predicate is safe

Ten distinct witness rows imply at least ten parsed instants at or later than the least witness (parsing failures use the existing minimum sentinel). The query keeps the whole UTC second at the lower bound. Only the four fixed-width UTC writer spellings can be pruned below it. Other strings survive for Python's original parser. An invalid minimum witness disables the floor. A raw maximum was itself sampled (ties share its text), so it also survives. A tie is broken by ID only after the entire tie is retained. Endpoint times and in-window trigger evidence have separate admission paths. The visible session order between waves, raw-key order within a wave and per-session parsed-time/ID ordering are unchanged.

## Verification

`tests/test_graph_history_statement_reads.py` freezes unsorted serialized graph digests from base `1471236bd` in both views. Its fixture has sparse sessions, offset/precision conflicts, out-of-timeline triggers, repeated endpoints, a sent callback tied with an unreadable older notice, null timestamps and overflow-size synthetic stdout. Growing only the unrelated tail by 32 rows changes the exact count but not the new header/time candidate footprint. At the longer tail, the rc15 history assembly consumed 76 creation rows and 35 headers; the new assembly consumes 35 time candidates, one 10-witness row and 15 narrower headers. Active: 75/34 versus 34 candidates, one witness row and 14 headers. These are **not** total read counts or latency/byte attribution. Other labels, including trigger seeks, still do work. Real bound query plans (hits and misses) and migration/fallback are checked in tests only. Use a paired real assembly and whole-request I/O counters for performance comparison; use the request's own spans for attribution, not SQL replay.
